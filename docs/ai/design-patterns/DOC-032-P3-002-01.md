# DOC-032 — AI Design Pattern Catalog

## Part III — Interaction Patterns

# AI-PATTERN-002 — Copilot Pattern

## 002-01 Executive Summary

---

> **Status: Draft.** DOC-032-PART-III lists AI-PATTERN-002 as Copilot Pattern with Draft status. This summary is a working specification and does not imply pattern approval.

## 1. Purpose

본 문서는 Copilot Pattern의 핵심 목적과 적용 경계를 요약한다. 상세 문제 분석, 적용 맥락, 흐름 및 구현 지침은 후속 문서에서 정의한다.

## 2. Problem

사용자가 이미 제품 안에서 특정 작업을 수행하고 있을 때, 별도의 AI 대화로 이동해 작업을 다시 설명하고 결과를 원래 화면에 옮겨야 한다면 Context 전환과 수동 적용이 생길 수 있다. Copilot Pattern은 이 간극을 줄이면서도 AI가 사용자의 의도나 권한을 대신 결정하지 않도록 한다.

## 3. Context

Copilot Pattern은 사용자가 제품의 구체적인 Task를 진행 중이고, 그 작업과 직접 관련된 도움을 제품 안에서 제공할 수 있을 때 고려한다. 현재 화면이나 선택 항목은 가능한 Context의 출처일 뿐, 그 자체가 사용 목적이나 접근 권한을 자동으로 허가하지는 않는다.

## 4. When to Use

- 현재 Task를 바탕으로 설명, 제안, 초안 또는 검토 지원을 제공할 수 있다.
- 사용자가 제안을 확인하고 수정·적용·거절할 수 있다.
- Context 및 Action을 기존 권한과 제품 Policy 안에서 제한할 수 있다.

## 5. When NOT to Use

- 사용자의 목표가 열려 있어 먼저 대화로 탐색하는 편이 적합하면 Chat Interaction을 우선하거나 조합한다.
- 필수 정보를 정해진 순서로 수집해야 하면 Wizard 또는 Conversational Form을 고려한다.
- 적절한 권한, 필요한 Context 또는 사용자 통제가 마련되지 않은 상태에서 상태 변경을 수행하지 않는다.

## 6. Architecture

아래는 책임 경계만 나타내는 개념도이며, 구체적인 구성 요소와 정책은 후속 설계에서 정의한다.

```plain text
Current product task
        ↓
Relevant context and permission boundary
        ↓
Copilot assistance
        ↓
Suggestion or draft for user review
        ↓
User decision
        ↓
Authorized action, if requested
```

## 7. Sequence Flow

```plain text
User works in product
        ↓
User requests or opens task-related assistance
        ↓
Product resolves relevant context and permissions
        ↓
Copilot returns assistance for review
        ↓
User edits, accepts, or dismisses
        ↓
If accepted and authorized, product applies the action
```

## 8. Implementation Guideline

구현 시 현재 Task와 Context의 목적을 명시하고, 제안·초안 표시와 제품 상태 변경을 구분한다. 실행 권한, 확인 요건, 검증 및 복구 방식은 Action 위험과 제품 Policy에 따라 후속 설계에서 구체화한다. 이 요약은 특정 기술이나 자동화 정책을 규정하지 않는다.

## 9. Advantages

- 사용자가 현재 작업 흐름 안에서 관련 지원을 받을 수 있다.
- 작업 Context를 다시 설명하거나 결과를 수동으로 옮기는 단계를 줄일 가능성이 있다.
- 제안과 사용자 결정을 분리하는 설계를 명시적으로 다룬다.

## 10. Disadvantages

- Context가 부족하거나 잘못 연결되면 무관하거나 부정확한 제안이 될 수 있다.
- 제품 화면에 보조 UI를 추가하면 주 작업을 방해할 수 있다.
- 화면별 Context와 권한 경계를 설계하고 유지하는 비용이 생긴다.

## 11. Trade-offs

| 설계 선택 | 기대 효과 | 고려할 점 |
| --- | --- | --- |
| 현재 Task에 가까운 지원 | Context 전환 감소 가능성 | 화면 Context가 사용자의 의도를 보장하지 않음 |
| 빠른 적용 경로 | 반복 작업 감소 가능성 | 제안과 실제 변경의 구분 및 확인 필요 |
| 개인화된 Context | 작업 관련성 향상 가능성 | 최소 수집, 권한, 설명 가능성 필요 |

## 12. Metrics

후속 적용에서는 제안의 수정·적용·거절, 작업 완료와 재작업, 잘못된 Context 또는 권한 처리, 사용자 피드백을 함께 평가한다. 수락률만으로 품질이나 사용자 효용을 판단하지 않는다. 구체적인 지표와 수집 기준은 평가 문서에서 정의한다.

## 13. Checklist

- [ ] Copilot의 지원이 사용자의 현재 Task와 연결되어 있는가?
- [ ] 사용 Context의 관련성, 목적 및 권한이 확인되는가?
- [ ] 제안 또는 초안과 실제 상태 변경을 구분하는가?
- [ ] 사용자가 결과를 검토하고 적절히 수정·거절할 수 있는가?
- [ ] 실제 Action과 결과 확인 기준을 후속 설계에서 정의했는가?

## 14. Anti-pattern

- 사용자의 요청이나 권한 없이 작업 Context를 확대한다.
- 제안을 보여주는 것만으로 저장·공유 등 상태 변경을 수행한다.
- 사용자가 결과를 검토하거나 거절할 수 없도록 한다.
- 실행 여부와 결과를 확인하지 않고 성공했다고 알린다.

## 15. RoRo Example

사용자가 특정 Trip이나 Moment를 보며 여행 기록 초안을 요청하는 경우를 적용 후보로 생각할 수 있다. Copilot은 사용자가 선택한 범위와 접근 권한이 확인된 Context만 이용해 초안을 제공하고, 사용자는 이를 검토하거나 수정·폐기할 수 있다. 저장은 사용자의 선택과 제품 권한에 따르며, 저장 결과는 별도로 확인한다. 이는 후보 예시이며 RoRo에서 이미 구현된 기능을 의미하지 않는다.
