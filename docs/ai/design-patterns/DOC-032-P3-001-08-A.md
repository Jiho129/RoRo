# DOC-032 — AI Design Pattern Catalog
## Part III — Interaction Patterns
# AI-PATTERN-001 — Chat Interaction Pattern
## 001-08-A State Model & State Transition
### Part A — Core State Model
---
# 1. Purpose
본 문서는 AI-PATTERN-001 Chat Interaction Pattern의 Runtime State Model과 State Transition을 정의한다.
앞선 001-07 Interaction Flow가 User Request가 들어온 이후 어떤 순서로 처리되는지를 정의했다면, 본 문서는 그 Flow를 실제 System이 관리할 수 있도록 각 단계의 \*\*상태(State), 상태 전환(Transition), 전환 조건(Condition), 예외 상태(Exception), 종료 상태(Terminal State)\*\*를 정의한다.
본 문서가 답해야 하는 핵심 질문은 다음과 같다.
1. Chat Interaction에는 어떤 상태가 존재하는가?
2. 각 상태에서 System은 무엇을 해야 하는가?
3. 어떤 조건에서 다음 상태로 이동하는가?
4. User가 응답하지 않으면 어떻게 되는가?
5. Tool이 실패하면 상태는 어떻게 바뀌는가?
6. Confirmation이 필요한 경우 어떤 상태를 거치는가?
7. Cancellation은 어느 상태에서 가능한가?
8. Retry와 Recovery는 어떻게 처리하는가?
9. 하나의 Interaction이 언제 종료되는가?
핵심 원칙은 다음과 같다.
> **State는 System이 현재 무엇을 하고 있는지를 나타내며, Transition은 명확한 Event와 Condition에 의해 발생해야 한다.**
---
# 2. State Model Philosophy
AI Interaction을 단순히 다음과 같이 표현하지 않는다.
```plain text
Request
  ↓
Response
```
실제 AI Interaction은 여러 상태를 가진다.
```plain text
Request
  ↓
Understanding
  ↓
Context Resolution
  ↓
Decision
  ↓
Execution
  ↓
Validation
  ↓
Response
  ↓
Completion
```
각 State는 다음 네 가지를 가져야 한다.
```plain text
Entry Condition
Active Behavior
Exit Condition
Failure Path
```
---
# 3. State Definition
AI-PATTERN-001의 Core State는 다음과 같이 정의한다.
| State | 설명 |
| --- | --- |
| IDLE | 활성 Interaction이 없는 상태 |
| RECEIVED | User Request를 수신한 상태 |
| VALIDATING | Input의 기본 유효성을 확인하는 상태 |
| UNDERSTANDING | Intent를 분석하는 상태 |
| CONTEXT_RESOLVING | 필요한 Context를 확보하는 상태 |
| DECIDING | 처리 방법을 결정하는 상태 |
| CLARIFYING | User에게 추가 정보를 요청하는 상태 |
| PLANNING | 복잡한 Task의 실행 계획을 만드는 상태 |
| AWAITING_CONFIRMATION | User의 실행 승인을 기다리는 상태 |
| EXECUTING | Tool 또는 Action을 실행하는 상태 |
| VALIDATING_RESULT | 실행 결과를 검증하는 상태 |
| RESPONDING | User에게 결과를 구성하는 상태 |
| REVIEWING | User가 결과를 검토하는 상태 |
| COMPLETED | Interaction이 완료된 상태 |
| CANCELLED | User 또는 System에 의해 취소된 상태 |
| FAILED | 복구할 수 없는 실패 상태 |
| RECOVERING | Error를 복구하는 상태 |
---


```plain text
COMPLETED

FAILED
RECOVERING
```

# 5. State Machine Overview
전체 State Machine은 다음과 같다.
```plain text
┌─────────┐
│  IDLE   │
└────┬────┘
     │ USER_MESSAGE
     ▼
┌──────────┐
│ RECEIVED │
└────┬─────┘
     ▼
┌────────────┐
│ VALIDATING │
└─────┬──────┘
      ▼
┌──────────────┐
│ UNDERSTANDING│
└──────┬───────┘
       ▼
┌───────────────────┐
│ CONTEXT_RESOLVING │
└─────────┬─────────┘
          ▼
┌──────────┐
│ DECIDING │
└────┬─────┘
     │
┌────┼────────┬─────────────┐
│    │        │             │
▼    ▼        ▼             ▼
```
CLARIFY PLAN   EXECUTE       REJECT
│    │        │
│    ▼        │
│  CONFIRM    │
│    │        │
│    ▼        │
└──→ EXECUTING
│
▼
VALIDATING_RESULT
│
▼
RESPONDING
│
▼
REVIEWING
│     │
│     └──→ REGENERATE
│
▼
COMPLETED
Any Active State
│
├── CANCEL
▼
CANCELLED
Any Execution State
│
├── ERROR
▼
RECOVERING
│
├── RETRY → Previous State
├── FALLBACK → Alternative State
└── FAIL → FAILED

# 6. State: IDLE
## Definition
현재 활성 Interaction이 없는 기본 상태다.
## Entry
다음 조건에서 IDLE에 진입한다.
```plain text
New Session
Interaction Completed
Interaction Cancelled
Session Reset
```
## Active Behavior
System은 새로운 User Input을 대기한다.
## Exit Event
```plain text
USER_MESSAGE
```
## Next State
```plain text
RECEIVED
```
---
# 7. State: RECEIVED
User Message가 System에 정상적으로 수신된 상태다.
## Entry Condition
```plain text
USER_MESSAGE received
```
## State Data
최소한 다음 정보를 가진다.
```plain text
interaction_id
conversation_id
user_id
message_id
timestamp
input_type
```
## Active Behavior
```plain text
Persist Request Metadata
Resolve Session
Attach Conversation Context
```
## Exit
```plain text
→ VALIDATING
```
---
# 8. State: VALIDATING
Input이 처리 가능한지 확인한다.
## Validation
```plain text
Authentication
Session
Message Format
Attachment
File Type
Size
Rate Limit
Abuse Protection
```
## Success
```plain text
→ UNDERSTANDING
```
## Failure
```plain text
Recoverable
   → RECOVERING

Non-recoverable
   → FAILED
```
---
# 9. State: UNDERSTANDING
User의 의도를 해석하는 상태다.
## Input
```plain text
User Message
Conversation Context
User Preferences
Product Context
```
## Output
```plain text
Intent
Entities
Constraints
Confidence
```
예:
```plain text
User:
"오늘 바다 사진 찾아줘."

Intent:
SEARCH_PHOTO

Entity:
BEACH

Scope:
CURRENT_DAY
```
---
# 10. Intent Confidence
Intent Confidence는 다음과 같이 활용할 수 있다.
```plain text
HIGH
  ↓
Continue

MEDIUM
  ↓
Safe Default / Clarification

LOW
  ↓
Clarification
```
단, Confidence Score 자체를 User에게 직접 노출할 필요는 없다.
---
# 11. UNDERSTANDING Failure
Intent를 해석할 수 없는 경우:
```plain text
UNDERSTANDING
      ↓
LOW CONFIDENCE
      ↓
CLARIFYING
```
예:
> "그거 정리해줘."
Context에 "그거"가 명확하게 존재하면 Resolve할 수 있다.
존재하지 않으면 Clarification이 필요하다.
---
# 12. State: CONTEXT_RESOLVING
Intent를 실행하기 위해 필요한 Context를 확보한다.
## Context Types
```plain text
Current Trip
Current Date
User
Family
Memories
Photos
Schedule
Expenses
Previous Result
```
---
# 13. Context Resolution Example
User:
> "어제 찍은 사진 중 좋은 것만 보여줘."
System:
```plain text
"어제"
  ↓
Current Date - 1 Day

"찍은 사진"
  ↓
Photo Entity

"좋은 것"
  ↓
Photo Ranking Criteria
```
---
# 14. Context Resolution Success
필요한 Context가 모두 확보되면:
```plain text
CONTEXT_RESOLVING
       ↓
    DECIDING
```
---
# 15. Context Resolution Partial
일부 Context가 없는 경우:
```plain text
Context Available
     +
Context Missing
```
System은 Task를 계속할 수 있는지 판단한다.
## Continue
Missing Context가 결과에 중요한 영향을 주지 않는 경우.
## Clarify
Missing Context가 User Goal을 결정하는 경우.
## Fail
필수 Data가 존재하지 않는 경우.
---
# 16. State: DECIDING
System이 실행 전략을 선택하는 상태다.
Decision Output:
```plain text
ANSWER
RETRIEVE
GENERATE
CLARIFY
PLAN
EXECUTE
REJECT
FALLBACK
```
---
# 17. Decision Transition
```plain text
DECIDING
   │
   ├── ANSWER → RESPONDING
   │
   ├── RETRIEVE → EXECUTING
   │
   ├── GENERATE → EXECUTING
   │
   ├── CLARIFY → CLARIFYING
   │
   ├── PLAN → PLANNING
   │
   ├── EXECUTE → AWAITING_CONFIRMATION / EXECUTING
   │
   └── REJECT → RESPONDING
```
---
# 18. State: CLARIFYING
User에게 추가 정보가 필요한 상태다.
## Entry
```plain text
Intent Ambiguous
Required Context Missing
High-risk Action
Multiple Valid Targets
```
## Behavior
Question을 생성하고 User Input을 기다린다.
---
# 19. Clarification State Data
```plain text
clarification_id
original_intent
missing_parameter
question
options
timeout
fallback
```
---
# 20. Clarification Example
User:
> "여행일기 만들어줘."
System이 다음 정보를 필요로 한다.
```plain text
Scope
Style
Date
```
이미 Context에서 Scope와 Date가 확정되어 있다면 Style만 질문한다.
> "사진 중심으로 자연스럽게 쓸까요, 일정 중심으로 정리할까요?"
---
# 21. Clarification Response
User가 답하면:
```plain text
CLARIFYING
     ↓
USER_RESPONSE
     ↓
UNDERSTANDING / DECIDING
```
기존 Intent를 유지하면서 새 정보를 추가한다.
---
# 22. Clarification Timeout
User가 응답하지 않는 경우:
```plain text
CLARIFYING
     ↓
TIMEOUT
```
다음 중 하나를 선택한다.
```plain text
Resume with Default
Keep Pending
Cancel
Expire
```
MVP에서는 Pending 상태를 유지하는 것을 기본으로 할 수 있다.
---
# 23. State: PLANNING
복잡한 Task를 여러 Sub-task로 분해한다.
예:
```plain text
CREATE_DIARY
   ↓
Identify Trip
   ↓
Analyze Days
   ↓
Retrieve Photos
   ↓
Retrieve Schedule
   ↓
Generate Draft
```
---
# 24. Plan State Data
```plain text
plan_id
goal
steps
dependencies
current_step
estimated_cost
estimated_latency
```
---
# 25. Plan Validation
Plan 생성 후 다음을 확인한다.
```plain text
Goal Alignment
Tool Availability
Permission
Cost
Complexity
Safety
```
문제가 있으면:
```plain text
PLANNING
   ↓
DECIDING
```
또는:
```plain text
PLANNING
   ↓
FAILED
```
---
# 26. State: AWAITING_CONFIRMATION
실행 전에 User의 승인을 기다리는 상태다.
## Required For
```plain text
Delete
Share
Publish
Permission Change
External Communication
High-impact Write
```
---
# 27. Confirmation State
Confirmation에는 다음 정보가 포함되어야 한다.
```plain text
Action
Target
Scope
Impact
Optional Parameters
```
예:
> "‘샌디에이고 여행기’를 가족 공유 그룹에 공개합니다. 공유할까요?"
---
# 28. Confirmation Transition
```plain text
AWAITING_CONFIRMATION
      │
      ├── CONFIRM → EXECUTING
      │
      ├── REJECT → CANCELLED / RESPONDING
      │
      └── MODIFY → DECIDING
```
---
# 29. Confirmation Timeout
User가 응답하지 않는 경우:
```plain text
AWAITING_CONFIRMATION
      ↓
   TIMEOUT
      ↓
   PENDING
```
중요 Action은 자동 실행하지 않는다.
---
# 30. State: EXECUTING
Tool 또는 Product Action이 실행되는 상태다.
## Examples
```plain text
Search Photos
Get Schedule
Create Diary
Save Memory
Share Memory
Generate Video
```
---
# 31. Execution State Data
```plain text
execution_id
tool_name
input
start_time
timeout
retry_count
idempotency_key
```
---
# 32. Execution Transition
```plain text
EXECUTING
    │
    ├── SUCCESS → VALIDATING_RESULT
    │
    ├── PARTIAL → VALIDATING_RESULT
    │
    ├── TIMEOUT → RECOVERING
    │
    ├── RETRYABLE ERROR → RECOVERING
    │
    └── FATAL ERROR → FAILED
```
---
# 33. Parallel Execution State
복수 Tool을 병렬로 호출할 수 있다.
```plain text
EXECUTING
   │
   ├── Tool A
   ├── Tool B
   └── Tool C
         │
         ▼
     Aggregation
         │
         ▼
   VALIDATING_RESULT
```
모든 Tool이 종료되기 전까지 필요한 경우 EXECUTING 상태를 유지한다.
---
# 34. Partial Execution
일부 Tool만 성공할 수 있다.
예:
```plain text
Photo Search → SUCCESS
Schedule Search → FAILURE
```
State:
```plain text
EXECUTING
   ↓
PARTIAL
   ↓
VALIDATING_RESULT
```
AI는 Partial Result를 기반으로 계속 진행할 수 있는지 판단한다.
---
# 35. State: VALIDATING_RESULT
Tool Result가 실제 기대한 결과인지 검증한다.
## Validation
```plain text
Schema
Data Integrity
Product State
Permission
Business Rule
User Intent
```
---
# 36. Validation Example
AI가:
> "여행일기를 저장했습니다."
라고 응답하기 전에:
```plain text
memory_id exists
   AND
save_status = SUCCESS
   AND
persisted = TRUE
```
를 확인한다.
---
# 37. Validation Failure
결과가 예상과 다르면:
```plain text
VALIDATING_RESULT
      ↓
   RECOVERING
```
또는:
```plain text
VALIDATING_RESULT
      ↓
     FAILED
```
---
# 38. State: RESPONDING
검증된 결과를 User에게 전달한다.
## Response Types
```plain text
Text
Card
Gallery
Chart
Preview
Confirmation
Error
Progress
```

# 39. Response State
Response는 단순히 LLM Text Generation만 의미하지 않는다.
```plain text
Response Assembly
    ↓
UI Rendering
    ↓
Action Binding
    ↓
User Delivery
```
---
# 40. Response Validation
최종 Response는 다음을 확인한다.
```plain text
Factuality
Grounding
Policy
Formatting
Product State
User Intent
```
---
# 41. State: REVIEWING
AI가 만든 결과 또는 중요한 Action 결과를 User가 확인하는 상태다.
예:
```plain text
AI Diary Draft
   ↓
REVIEWING
```
User는:
```plain text
Accept
Edit
Regenerate
Reject
```
중 하나를 수행할 수 있다.
---
# 42. Review Transition
```plain text
REVIEWING
   │
   ├── ACCEPT → COMPLETED
   │
   ├── EDIT → REVIEWING
   │
   ├── REGENERATE → EXECUTING
   │
   └── REJECT → CANCELLED
```
---
# 43. State: COMPLETED
User Goal이 달성된 Terminal State다.
## Completion Conditions
```plain text
Goal Satisfied
Product State Verified
No Critical Pending Action
```
---
# 44. Completion Data
```plain text
interaction_id
completion_type
final_result
completed_at
```
Completion Type:
```plain text
FULL
PARTIAL
```
---
# 45. State: CANCELLED
User 또는 System이 Task를 중단한 상태다.
## Entry
```plain text
User Cancel
User Reject
Timeout Policy
Session End
Safety Policy
```
---
# 46. Cancellation Principle
Cancellation은 단순히 UI에서 Spinner를 제거하는 것이 아니다.
가능하면 실제 실행을 중단해야 한다.
```plain text
User Cancel
   ↓
Cancel Request
   ↓
Worker Stop
   ↓
Side Effect Check
   ↓
CANCELLED
```
---
# 47. State: RECOVERING
Error가 발생했지만 복구 가능성이 있는 상태다.
Recovery Strategy:
```plain text
Retry
Fallback
Replan
Partial Result
User Clarification
```
---
# 48. Recovery Decision
```plain text
RECOVERING
    │
    ├── RETRY
    │
    ├── FALLBACK
    │
    ├── REPLAN
    │
    ├── CLARIFY
    │
    └── FAIL
```
---
# 49. Retry Transition
Retry는 무한 반복하지 않는다.
```plain text
Retry Count
   ↓
Backoff
   ↓
Retry
   ↓
Success / Failure
```
Retry Budget:
```plain text
max_attempts
max_runtime
max_cost
```
---
# 50. State: FAILED
복구할 수 없는 오류가 발생한 상태다.
예:
```plain text
Required Data Missing
Permission Denied
Unsupported Action
Fatal Service Error
Policy Block
```
User에게는 원인과 가능한 다음 행동을 제공한다.
---
# 51. Failure Response
Bad:
> "오류가 발생했습니다."
Good:
> "여행 사진을 불러오지 못했습니다. 잠시 후 다시 시도해주세요."
가능한 경우:
```plain text
[다시 시도]
```
를 제공한다.
