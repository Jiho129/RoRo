# DOC-032 — AI Design Pattern Catalog

## Part III — Interaction Patterns

# AI-PATTERN-002 — Copilot Pattern

## 002-04 MVP Implementation Decisions

---

> **Status: Draft.** DOC-032-PART-III does not define a 002-04 title or roadmap. “MVP Implementation Decisions” is a proposed, narrow follow-up. This document records candidate MVP decisions and open items; it is not a complete implementation specification or an approved RoRo scope.

# 1. Purpose and Scope

본 문서는 앞 문서에서 정의한 Pattern 목적, 문제, Context 및 적용 기준을 반복하지 않고, Copilot MVP 구현에서 새로 결정해야 할 경계만 제안한다.

- 기본 Pattern 정의와 사용자 통제 원칙은 [DOC-032-P3-002-01 — Executive Summary](DOC-032-P3-002-01.md)을 따른다.
- 문제와 Chat Interaction과의 구분은 [DOC-032-P3-002-02 — Problem Statement & Motivation](DOC-032-P3-002-02.md)을 따른다.
- Context의 범위와 적용 판단은 [DOC-032-P3-002-03 — Context & Applicability](DOC-032-P3-002-03.md)을 따른다.
- 이 문서의 결정은 Draft이며, 제품 요구사항과 권한 모델 검토를 거쳐 확정해야 한다.

문서 제목과 순서는 제안이다. MVP 범위가 정해지면 아래 항목만으로 충분한지 검토하고, 추가 설계 문서는 실제로 해결되지 않은 결정을 중심으로 만든다.

# 2. Part II §11 Implementation Mapping

DOC-032-PART-II §11은 구현 지침에 Required Components, Dependency, Configuration, Interface, Error Handling을 포함하도록 요구한다. 아래 표는 각 항목의 잠정 MVP 결정, 보류 사항 및 기준 문서를 구분한다.

| Required topic | MVP decision (Draft) | Deferred or open | Authoritative basis |
| --- | --- | --- | --- |
| **Required Components** | 기존 제품 화면에서 시작해, 권한이 확인된 Task Context를 생성 지원에 전달하고 결과를 검토 가능한 Draft로 반환하는 최소 경계를 둔다. 저장/변경은 생성 응답과 분리한다. | 별도 Copilot 서비스, Agent Orchestrator, Context Adapter의 배포 단위 여부는 확정하지 않는다. 기존 RoRo 아키텍처 검토 후 결정한다. | DOC-032-P3-002-01의 책임 경계, DOC-032-P3-001-13 §3 Reference Implementation Architecture 참고 |
| **Dependency** | 사용자를 식별하고 요청한 Resource에 접근할 권한을 확인할 수 있어야 한다. 선택한 Resource의 최신 상태를 확인할 수 있어야 적용 단계로 진행한다. | Model Provider, 저장소, 검색 서비스 및 기타 외부 시스템의 선택·가용성 목표를 지정하지 않는다. 기술 설계와 보안 검토에 남긴다. | DOC-032-P3-001-11 Security, Privacy & Trust 및 RoRo 제품/권한 사양이 우선 |
| **Configuration** | MVP에서 Task 범위, 허용 Context 원천, 출력 형식, 요청 한도, timeout 및 기능 활성화 범위를 명시적으로 설정 가능하게 한다. | 구체적 Model/버전, Prompt, 임계값, 수치 한도, 배포 Flag, Secret 저장소는 결정하지 않는다. 값은 구현·운영 검증 후 별도 설정 사양으로 확정한다. | DOC-032-P3-001-13 §6 Configuration and Secrets, DOC-032-P3-001-14 Cost, Latency & Resource Management |
| **Interface** | 요청은 사용자 인증 정보(내부 참조), Task 종류, 사용자가 지정한 Resource 범위, 지시를 전달한다. 결과는 `draft/suggestion`과 상태를 구분해 반환하며, 생성 요청 자체가 제품 상태를 변경하지 않도록 한다. 적용은 명시적 사용자 선택과 별도 권한 검사 뒤 수행한다. | 구체적 API, Schema, 저장 계약, 버전 호환성, idempotency key는 제품 API 및 Data Model 설계에서 결정한다. | DOC-032-P3-001-13 §5 Interface and Schema Requirements, §8 State, Persistence and Idempotency |
| **Error Handling** | 권한 거부, 범위 불일치 또는 필수 Context 확인 실패 시 해당 데이터 처리와 상태 변경을 중단한다. 생성 실패는 성공으로 표현하지 않으며, 가능한 경우 사용자의 기존 입력/Draft를 보존한다. | 오류 코드, 재시도 횟수, fallback, 사용자 문구, 복구 SLA는 이 초안에서 정하지 않는다. | DOC-032-P3-001-10-A/B Error Handling & Recovery; 해당 정책과 제품 구현 사양을 기준으로 함 |

표의 구현 결정은 설계 제안이며, 상기 참조 문서의 구체 요건과 충돌하면 해당 표준 또는 제품 권한·보안 사양을 우선 검토한다.

# 3. MVP Decision Gate

MVP 구현 착수 전에 담당자는 표의 미결정 항목 중 실제로 필요한 항목만 확정한다. 최소한 다음 세 가지는 제품 사양에서 확인되어야 한다.

1. 지원할 단일 Task와 허용할 Resource 범위
2. 사용자의 기존 권한을 확인하고 적용 결과를 검증할 제품 경계
3. 생성 실패 또는 권한·Context 오류에서 보존할 상태와 사용자에게 안내할 다음 단계

세부 API Schema, Model 선택, 수치형 운영 한도 또는 별도 서비스 분리가 MVP 범위에 필요하지 않으면 이 문서에서 미리 결정하지 않는다.
