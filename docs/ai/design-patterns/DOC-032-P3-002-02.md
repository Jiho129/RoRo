# DOC-032 — AI Design Pattern Catalog

## Part III — Interaction Patterns

# AI-PATTERN-002 — Copilot Pattern

## 002-02 Problem Statement & Motivation

---

> **초안 상태:** DOC-032-PART-III에서 AI-PATTERN-002의 이름과 Draft 상태를 확인했다. 이 문서는 DOC-032-P3-002-01의 제목 및 문서 구조를 이어받은 작업 초안이며, 패턴 자체는 아직 승인된 표준으로 간주하지 않는다.

# 1. Problem Statement

## 1.1 Core Problem

사용자가 이미 제품 안에서 구체적인 작업을 수행하고 있어도, 그 작업을 더 쉽게 끝내는 데 필요한 AI 지원이 작업 흐름과 분리되어 있을 수 있다. 사용자는 화면의 현재 상태와 관련 자료를 다시 설명하고, 별도의 대화나 도구로 이동해 결과를 만든 뒤, 그 결과를 원래 작업으로 가져와 적용해야 할 수 있다.

이 분리는 다음과 같은 부담을 만든다.

- 현재 작업과 관련된 내용을 다시 설명하거나 선택해야 한다.
- 제품 상태와 대화 사이에 정보가 오가면서 누락되거나 잘못 연결될 수 있다.
- 생성된 결과를 원래 화면의 필드, 문서, 일정 또는 기록에 수동으로 옮겨야 한다.
- 제안이 실제 작업 상태에 적용되었는지 사용자가 별도로 확인해야 한다.
- 사용자의 현재 목표와 무관한 일반적인 답변이나 기능 안내를 받을 수 있다.

Copilot Pattern이 다루는 문제는 단순히 AI 답변을 제공하는 일이 아니다. **사용자가 진행 중인 제품 작업에서 필요한 도움을 맥락에 맞게 제공하고, 결과를 사용자가 판단하고 통제할 수 있는 방식으로 연결하는 것**이다.

## 1.2 Disconnected Assistance

독립된 대화형 인터페이스는 다양한 목표를 표현하고 탐색하기에 유용하다. 그러나 사용자가 이미 작업 중인 화면과 필요한 Context가 분리되어 있다면, 도움을 받기 위해 작업을 중단하고 배경을 다시 제공해야 할 수 있다.

```plain text
Current Product Task
        ↓
Leave the task context
        ↓
Explain the task and provide relevant information
        ↓
Receive a response or draft
        ↓
Return to the product and apply it manually
        ↓
Check the resulting product state
```

이 과정은 모든 제품이나 모든 작업에서 발생한다고 단정할 수는 없다. 다만 이러한 왕복이 존재하는 작업에서는 Context 전환과 수동 적용이 불필요한 비용이 될 수 있다.

Copilot Pattern은 AI 지원을 관련 작업 화면 또는 Workflow 안에 배치하여, 사용자가 작업을 이어가면서 설명·추천·초안·검토와 같은 도움을 받을 수 있도록 한다.

## 1.3 Context Resolution Problem

제품은 현재 선택된 항목, 화면, 편집 중인 콘텐츠, 사용자가 지정한 범위 등 작업 Context를 보유할 수 있다. 하지만 화면에 표시된 모든 정보가 현재 요청에 필요한 것은 아니며, 표시되거나 제품에 저장되어 있다는 이유만으로 AI가 이를 사용할 권한이 생기는 것도 아니다.

Copilot은 다음 질문을 해결해야 한다.

- 현재 Task는 무엇이며, 사용자는 어떤 결과를 원하고 있는가?
- 현재 선택과 제품 상태 중 요청에 필요한 Context는 무엇인가?
- 그 Context를 사용할 권한과 목적이 충족되는가?
- 정보가 부족하거나 모호하면 사용자에게 무엇을 확인해야 하는가?
- 사용한 Context와 생성된 제안을 사용자가 이해할 수 있는가?

관련성이나 권한을 확인하지 않은 채 넓은 제품 Data를 자동으로 끌어오면, 부정확한 제안과 개인정보 노출, 예상하지 못한 사용으로 이어질 수 있다. 따라서 Copilot의 Context는 현재 Task와 직접 연결되고, 필요한 최소 범위로 제한되며, 제품의 권한 및 Policy 검사를 거쳐야 한다.

## 1.4 Suggestion-to-Action Boundary

도움말, 제안, 생성된 Draft와 실제 제품 상태 변경은 서로 다른 결과다. 사용자가 제안을 본 것만으로 변경을 승인했다고 해석해서는 안 된다.

```plain text
Task Context
     ↓
AI assistance
     ↓
Suggestion / Draft / Explanation
     ↓
User reviews, edits, accepts, or dismisses
     ↓
Permission and action policy check
     ↓
Authorized product action, if requested
     ↓
Result verification
```

이 경계가 분명하지 않으면 사용자는 제안이 저장되었는지, 외부로 공유되었는지, 실제 데이터가 변경되었는지 알기 어렵다. Copilot은 제안의 표시와 실행을 구분하고, 변경의 영향과 범위에 맞는 사용자 확인 및 권한 검사를 적용해야 한다.

# 2. Why Existing Interaction Alone May Be Insufficient

## 2.1 Chat Interaction Pattern과의 관계

Chat Interaction Pattern은 사용자가 자연어로 목표를 표현하고, AI가 대화 Context를 바탕으로 목표를 해석해 응답하거나 적절한 기능으로 연결하는 유연한 대화 진입점을 제공한다. Copilot Pattern은 사용자가 이미 수행 중인 제품 Task를 기준으로 도움을 제공한다.

| 관점 | Chat Interaction Pattern | Copilot Pattern |
| --- | --- | --- |
| 시작점 | 사용자의 자연어 요청 또는 대화 | 제품 안의 현재 Task, 화면 또는 선택 항목 |
| 주된 역할 | 목표를 이해하고 응답 또는 기능으로 연결 | 현재 작업을 이어가도록 문맥에 맞는 지원 제공 |
| Context의 출발점 | 대화와 요청에서 필요한 정보를 해석 | 현재 Task와 관련된 제품 Context를 권한 범위에서 확인 |
| 일반적인 결과 | 설명, 응답, 추가 질문, 기능 연결 | 작업 중 제안, 초안, 검토, 허가된 작업 지원 |
| 사용자 제어 | 요청을 구체화하고 결과를 확인·수정 | 제안을 검토·수정·적용·거절하고 실행 범위를 통제 |

두 Pattern은 상호 배타적이지 않다. 사용자가 Copilot 안에서 더 넓은 질문을 하면 Chat식 대화가 필요할 수 있고, Chat이 사용자를 특정 제품 작업으로 안내할 수도 있다. 제품은 진입점과 작업 맥락에 맞는 Pattern을 조합할 수 있다.

핵심 구분은 UI가 채팅 모양인지 여부가 아니다. **상호작용의 주된 기준이 대화에서 표현된 목표인지, 현재 진행 중인 제품 Task인지**를 구분한다.

## 2.2 Context-Free Generic Assistance의 한계

일반적인 답변은 사용자의 작업 목표, 현재 선택, 기존 제품 상태를 반영하지 못할 수 있다. 반대로 현재 화면의 모든 정보를 무조건 사용하면 과도한 Context 접근이 될 수 있다.

따라서 Copilot은 제품 Context를 자동으로 소비하는 범용 답변기가 아니라, 현재 작업에 필요한 Context를 선별하고 권한을 확인해 지원을 제공하는 경계가 있는 Pattern이어야 한다.

## 2.3 Fully Autonomous Execution의 한계

작업 시간을 줄이기 위해 제안을 곧바로 실행하면, 사용자의 의도와 다른 편집·저장·공유가 발생할 수 있다. 제안의 유용성만으로 실행 권한을 추론할 수 없으며, 사용자의 모호한 요청이 제품의 권한이나 안전 정책을 대체할 수도 없다.

Copilot은 사용자 주도권을 유지한다. 위험이 낮고 사용자가 명시적으로 허용한 범위에서만 자동화를 고려하고, 의미 있는 상태 변경에는 목적·대상·결과가 드러나도록 하며, Policy가 요구하는 경우 실행 전에 명시적 확인을 받는다.

# 3. Motivation

Copilot Pattern을 도입하는 동기는 AI 기능을 추가하는 것 자체가 아니라, 사용자가 현재 작업에서 겪는 불필요한 단계를 줄이면서 작업의 주도권을 보존하는 데 있다.

## 3.1 Preserve the User’s Workflow

도움이 현재 Task와 같은 흐름에서 제공되면, 사용자는 별도 도구로 이동하거나 작업 Context를 매번 다시 구성하지 않고 도움을 받을 수 있다. 이를 통해 작업 전환과 결과의 수동 전달을 줄일 가능성이 있다. 실제 효과는 제품과 Task에 따라 측정해야 한다.

## 3.2 Make Assistance Contextual and Relevant

현재 화면, 사용자의 명시적 선택, Task 상태처럼 목적에 맞고 권한이 확인된 Context를 활용하면 제안을 작업에 연결할 수 있다. Context의 출처나 범위가 사용자의 판단에 중요할 때는 이를 설명하고, 모르는 정보는 확인된 사실처럼 제시하지 않는다.

## 3.3 Keep the User in Control

Copilot은 사용자의 판단을 대체하지 않고 보조한다. 사용자는 제안과 Draft를 검토하고, 필요하면 수정하거나 거절할 수 있어야 한다. 저장, 삭제, 외부 공유 또는 다른 사람에게 영향을 주는 동작은 제안과 구별되며, 적절한 권한 및 확인 절차를 따라야 한다.

## 3.4 Connect Assistance to a Verifiable Outcome

제안을 보여주는 것으로 작업이 완료되었다고 간주하지 않는다. 사용자가 적용을 선택한 경우 허가된 제품 Action을 수행하고, 실제 상태가 의도한 대로 바뀌었는지 확인해야 한다. 실패하면 결과를 과장하지 않고 복구 또는 다음 단계를 안내한다.

# 4. Problem-to-Pattern Mapping

| 사용자 또는 제품의 문제 | Copilot Pattern이 제공하는 설계 대응 |
| --- | --- |
| 도움을 받으려면 Task를 떠나 다시 설명해야 함 | 관련 Task 화면이나 Workflow 안에서 지원 제공 |
| 어떤 Context를 AI가 사용했는지 불명확함 | Task에 필요한 최소 Context를 선택하고 권한 검사 |
| 제안과 실제 변경이 혼동됨 | 제안·Draft·실행을 UI와 시스템 동작에서 구분 |
| 사용자가 결과를 적용하거나 검증하기 어려움 | 검토·수정·적용·거절 경로와 결과 확인 제공 |
| 자동화가 사용자의 기대나 권한을 넘어갈 수 있음 | 사용자가 설정한 범위와 Policy에 맞게 실행 제한 |
| 불확실한 정보가 단정적으로 제시될 수 있음 | 불확실성을 표시하고 필요한 경우 사용자에게 확인 |

이 표는 문제를 다루기 위한 설계 방향이며, 특정 구현이나 사용자 성과가 이미 검증되었다는 주장은 아니다.

# 5. RoRo Motivation Example

RoRo에서 사용자가 특정 Trip, 날짜 또는 선택한 Moment를 보며 여행 기록 초안을 만들고 싶어 하는 상황을 생각할 수 있다. 이 예시는 제품의 현재 동작이나 확정된 기능을 기술하는 것이 아니라 Copilot Pattern을 적용할 수 있는 후보 흐름이다.

```plain text
User views a Trip, date, or selected Moment
        ↓
User requests help with the current travel-record task
        ↓
Copilot checks the selected scope and access permission
        ↓
Copilot prepares a draft using only relevant authorized context
        ↓
User reviews, edits, accepts, or dismisses the draft
        ↓
If requested and permitted, save the selected result
        ↓
Verify the saved state and report the outcome
```

이 흐름에서 Copilot은 사용자가 고르지 않은 Trip이나 Moment를 임의로 포함하지 않는다. 사진이 사용되더라도 사진만으로 확인되지 않는 인물의 정체, 감정 또는 사건을 사실처럼 단정하지 않는다. 여행 기록 생성과 외부 공유는 별개의 작업이며, 공유에는 별도의 대상·범위 확인과 권한 검사가 필요하다.

# 6. Design Questions for Review

Copilot을 특정 화면이나 기능에 적용하기 전에 다음 질문을 검토한다.

- 이 제품에서 사용자가 이미 수행 중인 Task는 무엇인가?
- 해당 Task 안에서 AI 지원이 실제로 줄여 줄 수 있는 단계는 무엇인가?
- 사용자가 명시적으로 선택하거나 요청한 Context는 무엇인가?
- 필요한 Context에 대한 목적과 접근 권한은 확인되는가?
- 제안, Draft, 저장 및 외부 Action을 사용자가 쉽게 구분할 수 있는가?
- 사용자가 수정·거절·취소할 수 있고, 가능한 변경을 되돌릴 수 있는가?
- 제안이 적용된 뒤 실제 결과를 검증할 수 있는가?
- 대화에서 시작하는 목표 탐색이 더 적합한 경우 Chat Interaction과 어떻게 연결되는가?
- 예상되는 편의성이 Context 노출, 방해, 오작동 위험을 정당화하는지 어떻게 평가할 것인가?

# 7. Section Conclusion

Copilot Pattern은 사용자의 현재 제품 작업과 AI 지원 사이의 단절을 줄이기 위한 Interaction Pattern이다. 동작의 중심은 AI의 자율성이 아니라 사용자의 Task다.

Copilot을 설계할 때는 다음 원칙을 함께 만족시켜야 한다.

1. 지원은 사용자의 현재 Task와 연결되어야 한다.
2. Context는 관련성과 권한을 확인한 최소 범위로 사용해야 한다.
3. 사용자는 제안과 실제 상태 변경의 차이를 이해하고 결과를 통제할 수 있어야 한다.
4. 적용한 결과는 제품 상태와 대조해 검증해야 한다.

이 문서는 문제와 설계 동기를 정리한 Draft다. 구체적 적용 기준, Architecture, Sequence Flow 및 구현 요건은 후속 문서에서 정의하고 검토해야 한다.
