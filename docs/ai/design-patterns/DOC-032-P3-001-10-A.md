# DOC-032 — AI Design Pattern Catalog

## Part III — Interaction Patterns

# AI-PATTERN-001 — Chat Interaction Pattern

## 001-10-A Error Handling & Recovery
### Part A — Error Philosophy, Classification, Detection & Recovery Architecture

---

# 1. Purpose

본 문서는 AI-PATTERN-001 Chat Interaction Pattern에서 발생할 수 있는 오류를 체계적으로 정의하고, 오류를 감지하고 분류하며, 적절한 Recovery Strategy를 선택하고, 최종적으로 User에게 안전하고 이해하기 쉬운 결과를 전달하기 위한 Error Handling & Recovery Architecture를 정의한다.

AI Interaction에서 Error는 단순히 API가 실패하는 경우만을 의미하지 않는다.

AI Product에서 발생할 수 있는 오류는 다음과 같이 다양하다.

    User Input Error
    Intent Recognition Error
    Context Retrieval Error
    Data Quality Error
    Permission Error
    Tool Error
    Network Error
    Timeout
    Model Error
    Validation Error
    State Error
    Business Rule Error
    Hallucination
    Unexpected Output
    User Correction

따라서 Error Handling은 다음 질문에 답할 수 있어야 한다.

1. 무엇이 실패했는가?
2. 왜 실패했는가?
3. 실패를 감지할 수 있는가?
4. 자동으로 복구할 수 있는가?
5. 다시 실행해야 하는가?
6. 다른 방법으로 처리해야 하는가?
7. User에게 질문해야 하는가?
8. User에게 실패 사실을 알려야 하는가?
9. 현재 State를 유지할 수 있는가?
10. 실패 이후에도 Data Integrity를 보장할 수 있는가?

---

# 2. Core Principle

AI-PATTERN-001의 Error Handling은 다음 원칙을 따른다.

> **오류를 숨기는 것이 아니라, 오류의 영향을 통제하고 User Goal을 가능한 한 안전하게 계속 수행한다.**

즉:

    Error
      ↓
    Detect
      ↓
    Classify
      ↓
    Assess Impact
      ↓
    Recover
      ↓
    Validate
      ↓
    Continue

가 기본 Flow다.

Recovery가 불가능한 경우에만:

    Fail Safely
      ↓
    Explain
      ↓
    Next Action

으로 전환한다.

---

# 3. Error Handling Philosophy

AI Product에서는 다음 두 극단을 피해야 한다.

## 3.1 Silent Failure

시스템에서 오류가 발생했지만 User에게 알리지 않는 방식.

예:

    User:
    "오늘 사진으로 일기 만들어줘."

    AI:
    "오늘은 즐거운 하루였습니다."

실제로 사진 조회가 실패했는데 AI가 일반적인 문장을 생성했다면 User는 시스템이 사진을 분석했다고 오해할 수 있다.

이는 위험한 Failure다.

---

## 3.2 Technical Failure Dump

반대로 Backend 오류를 그대로 User에게 보여주는 것도 좋지 않다.

예:

    ERROR 504:
    upstream request timeout
    request_id=abc123
    service=photo-search

User에게 필요한 것은 기술적 Stack Trace가 아니다.

User가 알아야 할 것은:

    무엇이 안 되었는가?
    지금 무엇을 할 수 있는가?

이다.

---

# 4. User-Centered Error Handling

Error Response는 다음 구조를 권장한다.

    What happened
        +
    What was preserved
        +
    What can be done next

예:

> 사진을 불러오지 못했어요.  
> 일정 정보는 확인했습니다. 사진을 다시 선택하거나, 일정만으로 먼저 작성할 수 있어요.

이 구조는 단순한 Error Message보다 훨씬 유용하다.

# 5. Error Taxonomy

AI-PATTERN-001의 Error는 다음 Category로 분류한다.

    E01 Input Error
    E02 Intent Error
    E03 Context Error
    E04 Retrieval Error
    E05 Permission Error
    E06 Tool Error
    E07 Network Error
    E08 Timeout Error
    E09 Model Error
    E10 Validation Error
    E11 State Error
    E12 Business Rule Error
    E13 Data Integrity Error
    E14 Content Safety Error
    E15 User Correction
    E16 Unknown Error

---

# 6. E01 — Input Error

User Input 자체를 처리하기 어려운 경우다.

예:

    Empty Message
    Unsupported File
    Corrupted Image
    Unsupported Format
    Invalid Input Size
    Missing Required Field

예:

> 사진을 올려주세요.

했지만 파일이 실제로 전달되지 않은 경우.

---

# 7. E02 — Intent Error

User의 의도를 충분히 파악하지 못한 경우다.

예:

> "그거 다시 해줘."

현재 Conversation Context가 충분하지 않으면 "그거"가 무엇인지 알 수 없다.

이 경우 AI가 임의로 추측하기보다는 Clarification을 수행해야 한다.

---

# 8. E03 — Context Error

필요한 Context가 없거나 충돌하는 경우다.

예:

    Current Trip
    = null

그런데 User가:

> "오늘 여행일기 만들어줘."

라고 요청한 경우.

System은:

    어떤 여행인지
    어떤 날짜인지

를 확인해야 할 수 있다.

---

# 9. E04 — Retrieval Error

필요한 Data를 검색하지 못한 경우다.

예:

    Photo Search
       ↓
    0 Results

가능한 원인:

    실제 사진 없음
    검색 조건 오류
    Index 오류
    Data Sync 문제
    Wrong Trip ID
    Wrong Date

"검색 실패"와 "Data가 존재하지 않음"은 구분해야 한다.

---

# 10. E05 — Permission Error

User에게 해당 Data를 사용할 권한이 없는 경우다.

예:

    Private Memory
    ↓
    Permission Check
    ↓
    DENIED

이 경우 AI가 다른 방식으로 접근을 시도해서는 안 된다.

Permission Denied는 Security Boundary다.

---

# 11. E06 — Tool Error

Tool 자체의 실행에 문제가 발생한 경우다.

예:

    Tool Not Found
    Invalid Parameters
    Tool Internal Error
    Tool Dependency Failure

Tool Error는 AI가 직접 해결할 수 있는 경우와 없는 경우를 구분해야 한다.

---

# 12. E07 — Network Error

Network Layer에서 발생하는 오류다.

예:

    Connection Failure
    DNS Failure
    Connection Reset
    Service Unavailable

일부 Network Error는 Retry가 가능하다.

---

# 13. E08 — Timeout Error

지정된 시간 내에 응답이 도착하지 않은 경우다.

예:

    Photo Search
    Timeout = 5 sec

5초 이내에 결과가 없으면:

    Timeout
       ↓
    Retry / Fallback / Fail

중 하나를 선택한다.

---

# 14. E09 — Model Error

AI Model 자체의 실행에서 발생하는 오류다.

예:

    Model Unavailable
    Token Limit
    Generation Failure
    Invalid Structured Output
    Unsupported Capability

Model Error와 Model Quality Issue는 구분한다.

---

# 15. E10 — Validation Error

결과가 Schema 또는 Business Rule을 만족하지 못하는 경우다.

예:

    Expected:
    {
      "title": "...",
      "summary": "..."
    }

    Actual:
    {
      "title": "...",
      "text": "..."
    }

Schema Validation Failure다.

---

# 16. E11 — State Error

현재 Application State와 요청이 일치하지 않는 경우다.

예:

    Current State:
    DIARY_FINALIZED

User:

> "초안 다시 수정해줘."

이미 Finalized 상태라면 일반적인 Draft Editing Flow와 다른 처리가 필요하다.

---

# 17. E12 — Business Rule Error

Technical API는 정상적으로 실행되었지만 Product Rule을 위반하는 경우다.

예:

    User tries to share
    ↓
    Trip not completed
    ↓
    Business Rule:
    Sharing unavailable

이것은 System Failure가 아니라 Business Rule에 따른 정상적인 거절일 수 있다.

---

# 18. E13 — Data Integrity Error

Data 간 관계가 깨진 경우다.

예:

    Trip ID = TRIP-001

그런데:

    Photo references TRIP-999

이런 상황은 단순한 Missing Data보다 심각하다.

Data Integrity Error는 AI가 임의로 보정해서는 안 된다.

---

# 19. E14 — Content Safety Error

AI가 생성하려는 Content가 Product Policy 또는 Safety Policy를 위반하는 경우다.

이 경우 일반적인 Retry보다:

    Block
    Refuse
    Safe Alternative

등의 처리가 필요하다.

---

# 20. E15 — User Correction

User가 AI 결과를 수정하는 경우도 Error Recovery Flow의 중요한 부분으로 본다.

예:

AI:

> "오늘은 라호야 코브에서 점심을 먹었어요."

User:

> "아니야. 점심은 다운타운에서 먹었어."

이 경우 User Correction은 다음 AI Step의 Context를 수정한다.

---

# 21. E16 — Unknown Error

예상하지 못한 오류다.

이 경우:

    Catch
      ↓
    Log
      ↓
    Trace
      ↓
    Safe Response

를 수행한다.

User에게 내부 구현 정보를 노출하지 않는다.

---

# 22. Error Severity

Error Severity는 다음과 같이 분류한다.

    S0 — Informational
    S1 — Recoverable
    S2 — Degraded
    S3 — Critical
    S4 — Security Critical

---

# 23. S0 — Informational

기능 수행에는 영향을 주지 않는 상태다.

예:

    Optional Recommendation unavailable

Main Task가 정상적으로 완료된다면 User에게 별도의 Error를 표시하지 않을 수도 있다.

---

# 24. S1 — Recoverable

자동 Retry 또는 Fallback으로 복구 가능한 오류다.

예:

    Temporary Timeout
    Network Retry
    Temporary Service Unavailable

Flow:

    Error
      ↓
    Retry
      ↓
    Success

---

# 25. S2 — Degraded

일부 기능은 실패했지만 User Goal을 부분적으로 수행할 수 있다.

예:

    Photo Search Failed
    Schedule Search Success

이 경우:

    Full Diary
       ↓
    Partial Diary

로 전환할 수 있다.

---

# 26. S3 — Critical

핵심 기능을 수행할 수 없는 상태다.

예:

    Current Trip Missing
    AI Generation Unavailable
    Required Data Corrupted

이 경우 User에게 명확하게 알려야 한다.

---

# 27. S4 — Security Critical

권한 침해 또는 개인정보 노출 위험이 있는 경우다.

예:

    Unauthorized Access
    Cross-user Data Exposure
    Permission Bypass

이 경우 자동 Retry를 수행하면 안 된다.

즉시 차단하고 Logging 및 Security Monitoring을 수행한다.

---

# 28. Error Detection

Error Detection은 가능한 한 Early Stage에서 수행한다.

예:

    Input
      ↓
    Validate
      ↓
    Intent
      ↓
    Context
      ↓
    Tool
      ↓
    Output
      ↓
    Final Validation

각 단계마다 Validation Point를 둔다.

---

# 29. Validation Boundary

권장 Validation Boundary:

    V1 Input Validation
    V2 Intent Validation
    V3 Context Validation
    V4 Tool Parameter Validation
    V5 Tool Result Validation
    V6 Model Output Validation
    V7 State Validation
    V8 Final Response Validation

---

# 30. Error Detection Principle

Error는 발생 이후에 발견하는 것보다 발생하기 전에 차단하는 것이 좋다.

Bad:

    Invalid Tool Parameter
       ↓
    Tool Call
       ↓
    Backend Error

Good:

    Invalid Tool Parameter
       ↓
    Pre-validation
       ↓
    Correct / Ask
       ↓
    Tool Call

---

# 31. Error Object

System 내부에서는 Error를 구조화된 Object로 관리한다.

예:

    {
      "error_code": "PHOTO_SEARCH_TIMEOUT",
      "category": "TIMEOUT",
      "severity": "S1",
      "retryable": true,
      "user_action_required": false,
      "source": "photo_search",
      "interaction_id": "INT-001",
      "timestamp": "2026-08-14T10:00:00Z"
    }

---

# 32. Error Code

Error Code는 사람이 읽기 쉬우면서 시스템에서 검색하기 쉬운 형태를 권장한다.

예:

    INPUT_EMPTY
    INPUT_UNSUPPORTED_FILE
    INTENT_AMBIGUOUS
    CONTEXT_MISSING_TRIP
    CONTEXT_CONFLICT
    PHOTO_NOT_FOUND
    PHOTO_SEARCH_TIMEOUT
    PERMISSION_DENIED
    TOOL_UNAVAILABLE
    MODEL_TIMEOUT
    OUTPUT_SCHEMA_INVALID
    STATE_INVALID
    BUSINESS_RULE_BLOCKED

---

# 33. Retryability

모든 Error를 Retry하면 안 된다.

Error를 다음과 같이 구분한다.

    Retryable
    Non-Retryable
    Conditional

예:

    Network Timeout
    → Retryable

    Permission Denied
    → Non-Retryable

    Validation Error
    → Conditional

---

# 34. Retry Policy

Retry는 제한적으로 수행한다.

기본 원칙:

    Maximum Retry Count
    Exponential Backoff
    Jitter
    Timeout Limit
    Idempotency

예:

    Attempt 1
       ↓
    500ms
       ↓
    Attempt 2
       ↓
    1s
       ↓
    Attempt 3
       ↓
    Fail

---

# 35. Exponential Backoff

Retry 간격을 점진적으로 증가시킨다.

예:

    Retry 1 → 0.5s
    Retry 2 → 1s
    Retry 3 → 2s

실제 값은 Product 및 Infrastructure 환경에 맞춰 조정한다.

---

# 36. Jitter

여러 Client가 동시에 Retry하는 상황을 방지하기 위해 Randomized Delay를 추가할 수 있다.

예:

    Base Delay
       +
    Random Jitter
       =
    Actual Retry Delay

이를 통해 Retry Storm을 완화한다.

---

# 37. Retry Limit

Retry는 무한정 수행하지 않는다.

예:

    max_retries = 2

이후:

    Retry
      ↓
    Retry
      ↓
    Fail / Fallback

으로 전환한다.

---

# 38. Idempotency

Retry가 가능한 Action인지 확인해야 한다.

Safe:

    Search Photos

주의 필요:

    Create Diary

더 위험:

    Send Share
    Payment
    Delete Data

예:

    Create Diary
       ↓
    Timeout

이때 실제로 생성은 완료됐지만 Response만 유실되었을 가능성이 있다.

무조건 재생성하면 Duplicate Diary가 발생할 수 있다.

따라서 Idempotency Key가 필요할 수 있다.

---

# 39. Fallback

Retry로 복구되지 않는 경우 Fallback을 사용한다.

예:

    Photo AI Search
       ↓
    Failure
       ↓
    Metadata Search
       ↓
    Success

또는:

    AI Diary Generation
       ↓
    Failure
       ↓
    Template Diary
       ↓
    User Edit

Fallback은 User Goal을 최대한 유지하는 방향으로 설계한다.

---

# 40. Graceful Degradation

전체 기능이 실패하지 않았다면 부분적인 기능을 제공한다.

예:

    Photos unavailable
    Schedule available

결과:

> 사진을 불러오지 못했지만 오늘 일정은 확인했어요. 일정 기준으로 먼저 초안을 만들어드릴까요?

이 방식은 완전 실패보다 User Experience가 좋다.

---

# 41. Clarification

AI가 충분한 정보를 가지고 있지 않은 경우 User에게 질문한다.

예:

    User:
    "그 사진으로 만들어줘."

현재 Context에 사진이 여러 개라면:

> 어떤 사진을 말씀하시나요? 오늘 선택한 사진 5장을 기준으로 만들까요?

Clarification은 추측보다 안전하다.

---

# 42. Clarification Trigger

다음 조건에서 Clarification을 고려한다.

    Required Entity Missing
    Multiple Candidate Entities
    Conflicting Context
    Ambiguous Intent
    High-impact Action
    Permission-sensitive Action

특히 External Side Effect가 있는 Action은 더욱 보수적으로 판단한다.

---

# 43. Recovery Decision Tree

전체 Recovery Decision은 다음과 같다.

    ERROR
      │
      ▼
    CLASSIFY
      │
      ▼
    RETRYABLE?
      │
    ┌─┴─┐
   YES  NO
    │    │
    ▼    ▼
  RETRY  FALLBACK?
    │      │
    │    ┌─┴─┐
    │   YES  NO
    │    │    │
    │    ▼    ▼
    │ FALLBACK CLARIFY?
    │         │
    │       ┌─┴─┐
    │      YES  NO
    │       │    │
    │       ▼    ▼
    │    ASK USER SAFE FAIL
    │
    ▼
  SUCCESS
    │
    ▼
  VALIDATE
    │
    ▼
  CONTINUE

# 44. Recovery Strategy Matrix

| Error | Retry | Fallback | Clarify | Fail |
|---|---:|---:|---:|---:|
| Network Timeout | O | O | X | △ |
| Permission Denied | X | X | △ | O |
| Missing Trip | X | X | O | △ |
| Photo Not Found | X | O | O | △ |
| Tool Unavailable | O | O | X | △ |
| Invalid Input | X | X | O | △ |
| Model Timeout | O | O | X | △ |
| Schema Error | O | O | X | O |
| State Conflict | X | X | O | O |
| Security Error | X | X | X | O |

# 45. Error Recovery State Machine

Error Handling은 별도의 State로 표현할 수 있다.

    NORMAL
       ↓
    ERROR_DETECTED
       ↓
    ERROR_CLASSIFIED
       ↓
    RECOVERY_DECISION
       │
       ├── RETRYING
       ├── FALLBACK
       ├── WAITING_USER
       └── FAILED
              │
              ▼
            RECOVERED

Recovery가 성공하면 정상 Flow로 돌아간다.

---

# 46. Error State Integrity

Error가 발생하더라도 Application State가 깨져서는 안 된다.

예:

    Diary Draft
       ↓
    Save
       ↓
    Network Error

이때:

    Draft Lost

가 되어서는 안 된다.

가능하면:

    Draft
       ↓
    Local / Temporary Save
       ↓
    Retry Sync

구조를 고려한다.

---

# 47. Partial State

일부 Step만 성공한 경우 Partial State를 명확히 유지한다.

예:

    Trip Loaded
    Schedule Loaded
    Photos Failed

State:

    CONTEXT_PARTIAL

이 상태에서 AI가:

    Photos Loaded

라고 판단하면 안 된다.

---

# 48. Error Context

Error도 Context로 관리한다.

예:

    {
      "current_state": "CONTEXT_PARTIAL",
      "completed": [
        "trip",
        "schedule"
      ],
      "failed": [
        "photos"
      ],
      "retryable": [
        "photos"
      ]
    }

이 Context는 Recovery Decision에 사용된다.

---

# 49. User-visible Error

User에게 보여주는 Error는 다음 원칙을 따른다.

    Short
    Clear
    Honest
    Actionable
    Non-technical

Bad:

> HTTP 503 upstream unavailable.

Good:

> 사진을 불러오지 못했어요. 잠시 후 다시 시도해주세요.

Better:

> 사진을 불러오지 못했어요. 다시 시도하거나 일정만으로 먼저 작성할 수 있어요.

---

# 50. Error Message Structure

권장 구조:

    [What Happened]

    [What is still available]

    [Next Action]

예:

> 사진을 불러오지 못했어요.  
> 오늘 일정은 정상적으로 확인했습니다.  
> 사진을 다시 불러오거나 일정만으로 일기를 만들 수 있어요.

---

# 51. Error Transparency

AI가 수행하지 않은 작업을 수행했다고 표현해서는 안 된다.

예:

    Photo Search Failed

그런데:

> "사진을 분석해서..."

라고 생성하면 안 된다.

이것은 단순한 UX 문제가 아니라 AI Trust 문제다.

---

# 52. Recovery Transparency

자동 Recovery가 수행된 경우 필요한 수준에서 User에게 알려줄 수 있다.

예:

> 사진 검색이 잠시 지연되어 다시 시도했어요. 이제 정상적으로 불러왔습니다.

모든 내부 Retry를 표시할 필요는 없지만, 결과에 영향을 주는 경우 적절히 설명한다.

---

# 53. Error Logging

Internal Logging에는 다음 Data를 포함할 수 있다.

    interaction_id
    user_id_hash
    session_id
    state
    error_code
    error_category
    severity
    tool
    model
    latency
    retry_count
    recovery_strategy
    result

민감정보는 Logging하지 않는다.

---

# 54. Error Trace

하나의 Interaction에서 여러 Error가 발생할 수 있다.

예:

    INT-001

    Photo Search
      → Timeout

    Retry
      → Timeout

    Fallback Metadata Search
      → Success

이 전체 Flow를 Trace로 추적할 수 있어야 한다.

---

# 55. Error Aggregation

개별 Error보다 Error Pattern이 더 중요할 수 있다.

예:

    PHOTO_SEARCH_TIMEOUT
        1%
        2%
        3%
        8%
        12%

갑자기 증가한다면 Infrastructure 문제일 가능성이 있다.

따라서 Error를 집계하고 Trend를 모니터링한다.

---

# 56. Error Budget

서비스 운영에서는 Error Budget을 설정할 수 있다.

예:

    Target Success Rate
    = 99.5%

Error Budget:

    0.5%

단순히 모든 Error를 0으로 만드는 것이 목표가 아니라, 허용 가능한 Failure 수준과 User Experience의 균형을 맞춘다.

---

# 57. Error Prevention

가장 좋은 Error Handling은 Error가 발생하지 않도록 만드는 것이다.

예:

    Invalid Date
       ↓
    UI Constraint

    Invalid Photo Format
       ↓
    Upload Validation

    Missing Trip
       ↓
    Current Trip Selection

    Ambiguous Action
       ↓
    Confirmation UI

Prevention은 Recovery보다 우선한다.

---

# 58. Prevention → Detection → Recovery

전체 전략은 다음 3단계다.

    PREVENT
       ↓
    DETECT
       ↓
    RECOVER

각 단계는 독립적으로 필요하다.

Prevent만으로 모든 Error를 제거할 수 없고, Detect만으로는 User Experience를 보장할 수 없다.

---

# 59. AI-specific Error

AI Product에서는 전통적인 Software Error 외에 AI-specific Error가 존재한다.

대표적으로:

    Hallucination
    Wrong Intent
    Wrong Context
    Wrong Tool
    Tool Misuse
    Incorrect Reasoning
    Unsupported Claim
    Overconfident Answer
    Context Confusion

이들은 API가 정상적으로 응답했다는 이유만으로 Success로 판단하면 안 된다.

---

# 60. AI Success ≠ Technical Success

다음 두 개념을 분리한다.

    Technical Success
    = API returned 200

    AI Success
    = User Goal was correctly fulfilled

예:

    Model returned valid text
    ↓
    Technical Success

하지만 실제 User 요청과 다른 내용이라면:

    AI Failure

다.

---

# 61. Error Handling Quality Model

AI Interaction의 품질은 다음으로 평가할 수 있다.

    Error Detection
    +
    Error Classification
    +
    Recovery Success
    +
    State Integrity
    +
    User Transparency
    +
    Data Integrity

즉, Error Handling 자체도 Product Quality의 일부다.

---

# 62. Part A Summary

AI-PATTERN-001의 Error Handling은 다음 Pipeline으로 요약된다.

    ERROR
      ↓
    DETECT
      ↓
    CLASSIFY
      ↓
    SEVERITY
      ↓
    RETRYABLE?
      ↓
    RECOVERY STRATEGY
      │
      ├── RETRY
      ├── FALLBACK
      ├── CLARIFY
      ├── PARTIAL SUCCESS
      └── SAFE FAILURE
      ↓
    VALIDATE
      ↓
    RESTORE STATE
      ↓
    CONTINUE

핵심 원칙은 다음과 같다.

> **Error는 정상적인 AI Interaction의 예외가 아니라, 반드시 설계해야 하는 하나의 Interaction State다.**
