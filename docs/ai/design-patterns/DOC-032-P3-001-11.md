# DOC-032 — AI Design Pattern Catalog

## Part III — Interaction Patterns

# AI-PATTERN-001 — Chat Interaction Pattern

## 001-11 Security, Privacy & Trust

---

# 1. Purpose

본 문서는 AI-PATTERN-001 Chat Interaction에서 User, Conversation, Context, Memory, Tool 및 외부 Service를 보호하기 위한 Security, Privacy, Trust 원칙과 설계 기준을 정의한다.

Chat은 자연어 입력을 폭넓게 허용하므로 입력이 곧 명령이나 신뢰할 수 있는 사실을 의미하지 않는다. AI가 외부 데이터를 조회하거나 Tool을 실행할 때에는 대화 내용, 사용자 권한, Product State, 외부 결과를 분리하여 검증해야 한다.

본 문서는 보안 통제를 AI Interaction에 적용하는 Pattern 수준의 기준이다. 구체적인 암호화 알고리즘, 법률 준수 해석, Infrastructure 구성은 각 Product의 Security Architecture와 Privacy Policy에서 별도로 규정한다.

# 2. Core Principle

> **AI의 유용성은 User Data와 권한 경계를 침해하지 않는 범위에서만 확장한다.**

다음 원칙을 우선한다.

1. **Least privilege** — 요청을 수행하는 데 필요한 최소 권한만 사용한다.
2. **Data minimization** — 목적에 필요한 데이터만 조회하고 전달한다.
3. **Explicit authority** — 대화 문구만으로 권한이나 동의를 추정하지 않는다.
4. **Trust separation** — User Input, Retrieved Content, Tool Result, System Policy를 구분한다.
5. **User control** — 민감 데이터 사용과 외부 공유의 목적 및 범위를 사용자가 이해하고 통제할 수 있어야 한다.
6. **Verifiable claims** — 보호나 삭제가 완료되었다는 주장은 실제 상태로 확인한다.

# 3. Security and Privacy Boundary

Chat Interaction은 다음 경계를 유지한다.

```plain text
Untrusted User / External Content
              ↓ parse and classify
Conversation Orchestrator
              ↓ authorize per action
Policy and Permission Layer
              ↓ minimize and scope
Context and Tool Layer
              ↓ validate output and side effects
Product Data / External Service
```

LLM은 권한 부여자나 정책 저장소가 아니다. 권한 판단은 신뢰 가능한 Application Layer에서 수행한다. Model이 권한을 허용했다고 해서 실제 접근 권한이 생기지 않는다.

# 4. Threat Model

위협 검토는 다음 자산과 경로를 포함한다.

| Asset | 주요 위험 | 기본 통제 |
| --- | --- | --- |
| 계정 및 인증 정보 | 탈취, 노출, 재사용 | Secret을 Prompt와 Log에 넣지 않고 권한을 분리한다 |
| 개인 Data와 Memory | 과잉 조회, 노출, 잘못된 보존 | 목적 제한, 최소 조회, retention 제어 |
| Conversation | Prompt Injection, 악성 링크, 민감 입력 | 입력을 명령이 아닌 Data로 취급하고 경계를 표시한다 |
| Tool과 외부 API | 권한 오용, 무단 변경, SSRF 또는 부적절한 호출 | Allowlist, Server-side authorization, 입력 검증 |
| 검색된 문서와 웹 콘텐츠 | 지시문 위장, 출처 오염, 오래된 정보 | 출처 및 신뢰 수준을 보존하고 정책으로 승격하지 않는다 |
| 생성 결과 | 개인정보 재노출, 허위 보안 보장 | 출력 검사, 근거 검증, 안전한 표현 |
| Audit 정보 | 과도한 기록 또는 추적 불가 | 목적에 맞는 최소 로그와 접근 통제 |

위협에는 Prompt Injection, Context Poisoning, 계정 간 Data 혼합, 권한 상승, Tool misuse, 민감 정보 유출, 동의 범위 초과, 불필요한 보존, 잘못된 삭제 완료 주장, 외부 Service에 대한 의도하지 않은 공유가 포함된다.

# 5. Trust Classification

모든 Context는 출처와 권한을 잃지 않도록 분류한다.

| Class | Examples | 처리 기준 |
| --- | --- | --- |
| Policy | System Policy, 승인된 Product Rule | 높은 신뢰. 버전과 출처를 확인한다 |
| Authenticated Product Data | 권한 검사를 통과한 Trip, Moment, Photo | 해당 User와 목적 범위에서 사용한다 |
| User-provided Data | 입력 메시지, 업로드 파일, 사용자 수정 | 사용자의 주장 또는 Data로 취급한다. 정책 지시로 승격하지 않는다 |
| Retrieved External Data | 웹 페이지, 가져온 문서, 외부 Tool 응답 | 기본적으로 untrusted. 인용과 검증에 사용하되 명령으로 실행하지 않는다 |
| Model-generated Content | 요약, 추론, 추천, 생성 텍스트 | 검증 전에는 사실 또는 영속 Data로 취급하지 않는다 |

저장된 User Content라도 System Policy보다 높은 권한을 갖지 않는다. 인용문이나 검색 결과 안의 지시문은 Tool 권한을 부여하지 않는다.

# 6. Identity, Authorization & Consent

1. 인증된 User ID를 각 조회와 변경의 기준으로 사용한다.
2. 대화에 포함된 이메일, 이름, Trip ID만으로 대상 소유권을 인정하지 않는다.
3. 매 Tool 실행 직전에 대상 Resource, Action, User, 목적을 확인한다.
4. Read 권한과 Write, Share, Delete 권한을 구분한다.
5. 동의는 목적, Data 범위, 수신 대상, 보존 기간이 달라지면 다시 평가한다.
6. 이전 동의나 과거 대화는 새로운 외부 공유에 대한 무기한 동의로 간주하지 않는다.
7. 권한 또는 동의 상태를 확인할 수 없으면 민감 조회와 Side Effect를 중단하고 필요한 확인을 요청한다.

# 7. Data Minimization and Context Construction

Context Builder는 관련성만으로 모든 Data를 가져오지 않는다. 요청 목적과 권한을 함께 적용한다.

```plain text
User Goal
   ↓
Purpose and Resource Scope
   ↓
Authorization Check
   ↓
Minimum Required Data Selection
   ↓
Sensitive Data Filtering
   ↓
Source / Trust Labels
   ↓
Model Context
```

- 필요하지 않은 식별자, 위치, 연락처, 결제 정보는 Context에서 제외한다.
- User 간 데이터 경계를 강제하고 Cache Key에도 tenant 또는 User scope를 포함한다.
- 요약이나 Embedding을 만들 때 원문보다 민감 정보가 불필요하게 오래 남지 않도록 한다.
- 검색 결과는 출처, 시점, 소유권, 신뢰 수준과 함께 전달한다.
- 목적이 끝난 Context는 Session 범위 밖에서 재사용하지 않는다.

# 8. Prompt Injection and Tool Safety

Prompt Injection 방어는 Prompt 문구만으로 완료되지 않는다. Tool과 Data Layer에서 권한을 강제한다.

1. User와 외부 문서의 텍스트는 instruction이 아닌 untrusted content로 전달한다.
2. Model이 제안한 Tool Call은 Schema, Allowlist, 정책, 현재 User 권한을 검증한 뒤 실행한다.
3. Tool은 최소 권한의 좁은 기능으로 나누고 임의 URL, 임의 Query, 임의 코드 실행을 제공하지 않는다.
4. 읽기 결과에 포함된 지시문이 추가 Tool Call의 권한이 되지 않도록 한다.
5. 외부 전송, 공개 공유, 삭제, 결제와 같은 consequential Action은 정책상 필요한 확인과 승인 절차를 거친다.
6. Tool Result는 요청한 범위와 일치하는지 검사한 후 Model에 전달한다.
7. 재시도는 권한 검사를 생략하지 않는다.

# 9. Sensitive Data Handling

민감 Data의 처리에는 다음을 적용한다.

- Sensitive Data를 필요 이상의 Prompt, Analytics Event, Error Log, Support Trace에 복제하지 않는다.
- Redaction은 표시 Layer뿐 아니라 저장과 전송 경계에서 수행한다.
- 사용자 간 응답, 대화, Memory, Attachment가 섞이지 않도록 각 경계에서 소유권을 검사한다.
- Photo와 Location은 요청 목적에 필요한 범위와 정확도로만 사용한다.
- 데이터 삭제나 Export 요청은 적용 범위와 연관된 파생 Data를 정의된 Policy에 따라 처리한다.
- 모델 제공자 또는 외부 Service로 Data를 보내는 경우, 사전에 설정된 처리 조건과 동의 범위를 확인한다.

법률상 민감 정보의 정의와 보존 의무는 배포 지역 및 Data Category에 따라 별도 Privacy Policy에서 관리한다.

# 10. Memory, Retention and Deletion

Conversation History, 사용자 작성 기록, AI가 만든 Memory, 운영 Log는 서로 다른 Data Lifecycle을 가진다.

| Data | 기본 관리 기준 |
| --- | --- |
| Conversation History | 제품에서 고지한 대화 보존 정책에 따른다 |
| User-authored Moment | User 소유의 원본 기록으로 유지하고 수정 이력을 보호한다 |
| AI-generated Memory | 생성 출처와 User 수정 여부를 구분하고 정정·삭제 경로를 제공한다 |
| Operational Log | 목적, 접근 권한, 보존 기간을 제한하고 민감 내용은 최소화한다 |
| Temporary Context / Cache | 목적 종료 또는 만료 시 제거하며 사용자 간 재사용하지 않는다 |

삭제 요청을 받으면 시스템은 대상과 결과를 확인한다. 실제로 제거되지 않은 Backup, Legal Hold, 파생 Data가 있다면 삭제 완료로 단정하지 않고 적용 범위와 남은 상태를 정확히 설명한다.

# 11. Output Safety and Trust Communication

AI 응답은 Data 처리와 보안 상태를 오해하게 해서는 안 된다.

- 조회하지 않은 내용을 비공개 또는 안전하다고 주장하지 않는다.
- 권한이 없어 거절하는 경우 다른 User의 Data 존재 여부를 드러내지 않는다.
- 생성된 요약, Memory, 추론을 검증된 원본 사실과 명확히 구분한다.
- 사용자가 수정한 내용과 AI가 추론한 내용을 가능한 범위에서 구분한다.
- 보안상 상세 설명이 악용 위험을 높일 수 있으면 내부 방어 방법은 노출하지 않고 사용자에게 필요한 영향과 안전한 다음 행동만 전달한다.
- 개인정보를 응답에 반복 표시할 필요가 없으면 마스킹하거나 생략한다.

# 12. Security Logging and Incident Response

Audit Log는 누가, 어떤 목적과 권한으로, 어떤 종류의 Resource에 접근하거나 변경했는지 추적할 수 있어야 한다. 단, 대화 전문이나 민감 Data를 무조건 저장하지 않는다.

최소 권장 항목:

    interaction_id
    pseudonymous user / tenant reference
    policy and permission decision
    tool name and scoped action
    source and result status
    timestamp and correlation id
    confirmation state for consequential action

의심스러운 권한 상승, cross-user data exposure, 비인가 외부 전송이 감지되면 영향을 받는 Action을 차단하고 Incident Response 절차로 전환한다. 복구 과정에서 증거를 보존하되, 조사 권한과 Data 접근 범위를 제한한다.

# 13. RoRo Application

RoRo는 여행 기록에 Photo, Location, 일정, 지출, 개인 Memory를 연결할 수 있으므로 다음을 적용한다.

### Trip and Moment Retrieval

현재 User가 접근할 수 있는 Trip만 조회한다. 자연어에 등장한 동행인의 이름만으로 타인의 Trip이나 Moment를 검색하지 않는다.

### Photo and Location Context

일기 생성 요청에 필요한 Photo와 위치만 사용한다. 위치가 필요하지 않은 요청에서는 정밀 위치를 Context에 추가하지 않는다. 사진 속 인물이나 장소에 대한 추론은 확인된 Metadata와 구분한다.

### AI Diary and Memory

AI가 생성한 문장은 User의 원본 기록을 대체하지 않는다. Draft 상태로 제공하고, 저장이나 게시 전 사용자가 검토할 수 있게 한다. User가 수정한 서술을 AI 추론보다 우선한다.

### Sharing

Trip 또는 Story를 외부에 공유할 때 대상, 포함 Data, 공개 범위를 보여준다. 기존 대화의 “공유해도 돼”를 새 수신자나 다른 Data 범위에 대한 승인으로 확대하지 않는다.

### Expense and Payment-related Data

여행 지출 분석에 결제 상세 정보가 필요하지 않으면 원본 결제 식별 정보를 Context와 응답에서 제외한다. 외부 금융 Action은 본 Pattern만으로 수행 권한을 얻지 않는다.

# 14. Failure and Recovery

Security 또는 Privacy 검증에 실패하면 재시도나 일반 Fallback으로 우회하지 않는다.

```plain text
Policy / Permission Check Fails
             ↓
Block the affected retrieval or action
             ↓
Preserve unrelated safe work
             ↓
Avoid exposing protected resource details
             ↓
Explain the user-visible limitation
             ↓
Offer an authorized next step
```

불확실한 경우 권한을 넓게 추정하지 않는다. 안전한 비민감 작업만 계속할 수 있는지 확인하고, 필요한 경우 User에게 재인증이나 구체적인 동의를 요청한다.

# 15. Metrics

| Metric | 목적 |
| --- | --- |
| Unauthorized access blocked rate | 권한 우회가 차단되는지 평가 |
| Cross-user data isolation incidents | 사용자 간 Data 혼합 감지 |
| Sensitive data exposure rate | 응답·Log·외부 Tool의 과잉 노출 평가 |
| Consent scope mismatch rate | 목적·수신자·Data 범위가 동의와 일치하는지 평가 |
| Prompt injection tool-block rate | 비신뢰 입력으로부터 Tool이 보호되는지 평가 |
| Deletion request verification rate | 삭제 처리 결과가 실제 상태와 대조되는지 평가 |
| Security false-block rate | 안전한 요청을 과도하게 차단하는지 평가 |

Metric은 최소 Data로 집계하고, 특정 사용자의 민감한 내용이 분석 결과에 역으로 노출되지 않게 한다.

# 16. Review Checklist

- [ ] 각 Data Source의 소유권과 신뢰 수준이 유지되는가?
- [ ] 권한 검사가 Model 밖의 신뢰 가능한 Layer에서 수행되는가?
- [ ] Tool 권한이 목적과 Resource에 최소 범위로 제한되는가?
- [ ] Prompt Injection이 정책이나 권한을 바꿀 수 없는가?
- [ ] Context, Cache, Log에서 민감 Data를 최소화하는가?
- [ ] 사용자 동의가 목적, Data 범위, 수신자에 연결되는가?
- [ ] AI 생성 내용과 원본 기록, User 수정 내용이 구분되는가?
- [ ] Sharing, Delete 등 consequential Action에 적절한 확인이 있는가?
- [ ] 삭제·보존 결과를 실제 상태에 맞게 설명하는가?
- [ ] 보안 실패 시 권한 우회 없이 안전하게 중단하는가?
- [ ] Incident 조사에 필요한 증거를 최소한으로 기록하는가?
- [ ] RoRo의 Trip, Photo, Location, Diary, Memory Data 경계를 검증하는가?

# 17. Anti-patterns

1. **Prompt-only authorization** — Prompt에 “허용됨”이라고 써서 실제 권한 검사를 대체한다.
2. **Conversation as consent** — 과거 대화의 표현을 새로운 외부 공유에 대한 포괄 동의로 사용한다.
3. **Trust laundering** — 검색 결과 안의 지시문을 System Policy 또는 User 승인으로 취급한다.
4. **Context over-collection** — 언젠가 유용할 수 있다는 이유로 모든 User Data를 Model Context에 넣는다.
5. **Cross-user cache reuse** — 소유자 경계 없이 검색 결과나 Memory Cache를 재사용한다.
6. **Silent AI memory** — 사용자가 알지 못하는 상태에서 추론을 장기 Memory로 저장한다.
7. **False deletion assurance** — 일부 파생 Data가 남았는데 완전 삭제됐다고 응답한다.
8. **Retry around a security denial** — 권한 실패 뒤 다른 Tool이나 Identity로 같은 작업을 계속한다.
9. **Over-logging** — 문제 해결을 이유로 전체 대화와 민감 Data를 무기한 저장한다.
10. **Security through vague refusal** — 보호된 Data를 노출하지 않는다는 이유로 사용자에게 안전한 다음 행동조차 안내하지 않는다.
