# DOC-032 — AI Design Pattern Catalog

## Part III — Interaction Patterns

# AI-PATTERN-001 — Chat Interaction Pattern

## 001-12 Observability, Evaluation & Continuous Improvement

---

# 1. Purpose

본 문서는 AI-PATTERN-001 Chat Interaction의 운영 상태와 품질을 관측하고, 사용자 목표 달성 여부를 평가하며, 근거에 기반해 지속적으로 개선하는 기준을 정의한다.

AI Interaction의 품질은 HTTP 성공률이나 응답 속도만으로 설명할 수 없다. 시스템은 요청을 받았어도 의도를 잘못 이해하거나, 오래된 Context를 사용하거나, Tool 작업을 완료하지 못하거나, 불확실한 결과를 확신 있게 제시할 수 있다. 따라서 운영 관측은 기술 상태, User Goal, Data Integrity, Safety를 함께 다뤄야 한다.

# 2. Core Principle

> **측정 가능한 사실과 사용자 결과를 함께 관측하고, 불확실성을 감추지 않은 채 개선한다.**

운영 원칙:

1. **Outcome over activity** — Token 수와 메시지 수보다 User Goal의 안전한 달성을 측정한다.
2. **End-to-end traceability** — 한 요청에서 Retrieval, Model, Tool, Validation, Persistence까지 연결한다.
3. **Privacy by design** — 운영 가시성을 위해 대화 전문이나 민감 Data를 무분별하게 저장하지 않는다.
4. **Quality and safety together** — 유용성 향상이 권한, 사실성, 사용자 통제를 훼손하지 않는지 함께 평가한다.
5. **Evidence-led change** — 변경 전후를 비교할 평가 기준과 Rollback 조건을 둔다.

# 3. Observability Model

AI Interaction 운영은 세 가지 관측 신호를 결합한다.

| Signal | Answers | Examples |
| --- | --- | --- |
| Metrics | 얼마나 자주, 얼마나 오래, 어느 정도 비용과 품질로 동작하는가? | latency, tool failure rate, goal completion |
| Traces | 특정 요청에서 어떤 단계와 상태를 거쳤는가? | retrieval → model → tool → validation → save |
| Logs / Events | 특정 정책 판단이나 오류에 어떤 제한된 설명이 남았는가? | permission denied, fallback selected |

모든 신호는 공통 `interaction_id`와 단계 식별자를 사용한다. 민감 Data를 식별자로 쓰지 않는다. User별 분석이 필요하면 권한을 제한한 pseudonymous reference를 사용한다.

# 4. End-to-end Trace

```plain text
User Request
    ↓
Input and Policy Checks
    ↓
Intent / Context Resolution
    ↓
Model Generation
    ↓
Tool Calls and Results
    ↓
Output Validation
    ↓
Persistence / Delivery
    ↓
User Outcome and Feedback
```

각 단계는 시작·종료 시각, 상태, 시도 횟수, 선택된 경로, 제한된 오류 분류를 기록한다. Trace는 요청의 실제 순서를 보여야 하며, 실패하거나 생략된 단계를 성공으로 표시하지 않는다.

# 5. Measurement Layers

## 5.1 Reliability

- Request availability 및 timeout rate
- Model, Retrieval, Tool 별 성공률과 오류 분류
- Retry 횟수, 중복 Side Effect, 부분 성공 비율
- 사용자 데이터 저장 및 상태 전이 검증 실패율

## 5.2 Experience and Goal Outcomes

- Intent clarification rate 및 clarification 후 성공률
- Goal completion rate와 재시도 없는 완료율
- 사용자 수정, 취소, 재생성 비율
- 부분 완료 또는 불확실 상태를 적절히 설명한 비율
- User가 같은 목표를 반복해서 설명하는 비율

단일 지표를 최적화하여 질문을 억제하거나 무리한 완료를 유도하지 않는다. Clarification은 필요한 확인을 수행하는 정상 경로일 수 있다.

## 5.3 Quality and Grounding

- 사실 오류 및 unsupported claim 비율
- 근거가 필요한 응답의 source coverage
- Retrieval freshness와 provenance 보존율
- 생성 결과와 저장된 원본 Data 간 불일치율
- 사용자 correction 반영 성공률

자동 평가 점수는 품질의 증거 중 하나다. Gold Set, human review, 실제 사용자 correction과 함께 판단한다.

## 5.4 Safety and Trust

- 권한 위반 차단과 cross-user data leakage 사건
- 개인정보 과다 노출 및 consent scope mismatch
- Prompt injection에 의한 차단되지 않은 Tool Call
- 외부 공유 등 중요 작업의 확인·승인 기록 완전성
- 보안 실패 이후의 안전한 중단과 Incident 대응 시간

Security Event의 세부 지표와 대응은 DOC-032-P3-001-11 및 별도 Security Policy와 일치시킨다.

## 5.5 Performance and Cost

- End-to-end latency와 단계별 latency 분포
- Model, Retrieval, Tool별 Token 및 비용
- 목표 유형별 비용 대비 완료 품질
- Cache hit rate와 freshness / isolation 오류
- 긴 응답 생성, 재시도 폭증, 비정상 Tool 호출

평균값만으로 느린 사용자 경험을 숨기지 않도록 percentile과 사용자 영향 기준을 함께 본다.

# 6. Metric Definition and Governance

Metric Registry에는 다음을 기록한다.

| Field | Meaning |
| --- | --- |
| Name and owner | 측정 이름과 책임자 |
| User outcome | 어떤 사용자 결과를 나타내는가 |
| Numerator / denominator | 계산에 포함되는 사건과 제외 조건 |
| Data source | Event, trace 또는 평가 데이터의 출처 |
| Segments | 지원되는 비교 차원과 개인정보 제한 |
| Target / alert threshold | 목표치, 경보 기준, 근거 |
| Known limitations | 편향, 표본 부족, 해석 시 주의점 |

지표 정의나 집계 방식이 바뀌면 변경 이력을 남기며, 이전 기간과 직접 비교할 수 없는 경우 이를 표시한다.

# 7. Evaluation Strategy

## 7.1 Offline Evaluation

배포 전 대표적인 요청을 포함한 Versioned Evaluation Set으로 다음을 평가한다.

- 의도 분류와 Clarification 판단
- Context relevance, 권한 적용, 출처 보존
- Tool 선택, 입력 인자, 안전한 실패 경로
- 생성 결과의 사실성, 유용성, 형식 준수
- Prompt Injection, 개인정보, 교차 사용자 격리 사례
- RoRo Domain에 특화된 Trip, Day, Moment, Photo 흐름

Evaluation Set은 실제 사용자 대화를 원문 그대로 무제한 복사하지 않는다. 필요한 경우 비식별화, 합성 사례, 제한된 접근 및 retention을 적용한다.

## 7.2 Online Evaluation

운영에서는 집계된 결과와 동의를 받은 피드백을 사용한다. 실험은 사용자 영향, 안전성, 데이터 이용 조건을 사전 검토하고, 비교 기준과 중단 조건을 정의한다.

## 7.3 Human Review

사람의 Review가 필요한 표본은 개인정보와 위험도를 고려해 제한적으로 선정한다. Reviewer에게는 평가 목적에 필요한 최소 Context만 제공하며, 접근을 기록하고 보존 기간을 제한한다.

# 8. Feedback and Error Taxonomy

Feedback은 단순한 thumbs-up 또는 thumbs-down으로 끝내지 않는다. 오류 유형을 분류해 개선 책임과 연결한다.

    Intent misunderstanding
    Missing or stale context
    Incorrect source or grounding
    Tool selection or execution failure
    State / persistence mismatch
    Unsafe or unauthorized action
    Privacy or sharing concern
    Poor explanation or recovery
    Product expectation mismatch

사용자 피드백을 Model 개선, 제품 개인화, 운영 조사에 재사용하는 것은 서로 다른 목적이다. 각 목적은 별도 Data Policy와 적절한 동의 및 보존 기준을 따른다.

# 9. Alerting and Operational Response

Alert는 사용자 영향과 대응 가능한 조치를 기준으로 한다. 원시 오류 수가 많더라도 영향이 낮고 조치가 불가능하면 Paging 기준으로 삼지 않는다.

```plain text
Signal crosses threshold
          ↓
Check scope, trend, and affected flow
          ↓
Contain unsafe or data-integrity risk
          ↓
Mitigate / disable affected capability
          ↓
Verify recovery and user-visible state
          ↓
Record incident and follow-up action
```

### Severity Guidance

| Level | Example | Response |
| --- | --- | --- |
| Critical | cross-user data exposure, unauthorized consequential action | affected capability 차단, Incident Response 시작 |
| High | 주요 Flow의 광범위한 실패, 잘못된 저장 상태 | 담당자 호출, 안전한 대체 경로 적용 |
| Medium | 제한된 Tool 장애, 지연 증가 | 모니터링 및 단계적 완화 |
| Low | 소수 사용자에게 제한된 품질 저하 | backlog와 개선 분석에 등록 |

# 10. Release Evaluation and Rollback

새 Prompt, Model, Retrieval, Tool, Policy 변경은 변경 위험에 맞는 평가를 거친다.

1. 변경 목적과 영향 범위를 기록한다.
2. 사전 Evaluation Set 및 Security / Privacy 사례를 실행한다.
3. 핵심 지표와 중단 기준을 명시한다.
4. 가능한 경우 제한된 Cohort 또는 단계적 배포를 사용한다.
5. 품질, Safety, 비용, Latency 변화를 함께 관찰한다.
6. 중단 기준을 넘으면 이전 설정이나 안전한 대체 경로로 복구한다.
7. 배포 결과와 후속 조치를 기록한다.

Rollback은 Model만 되돌리는 것으로 끝나지 않을 수 있다. Prompt, Tool Schema, Context Policy, 저장 형식이 함께 변경되었다면 호환성과 Data 상태도 확인한다.

# 11. RoRo Operational Views

RoRo 운영 Dashboard는 최소한 다음을 분리해 보여준다.

### Diary Generation

요청부터 Draft 저장까지 단계별 성공, 사용된 Moment / Photo Source, 사용자 수정률, 근거 없는 서술 신고, 저장 상태 불일치를 본다.

### Photo and Context Retrieval

권한 검사 통과, 검색 누락, 오래된 Metadata, 잘못된 Trip 연결, 사용자 간 격리 실패를 본다. Photo 내용이나 정밀 위치는 Dashboard Label에 표시하지 않는다.

### Trip / Schedule / Expense Tools

조회와 변경을 구분하고, 읽기 실패와 상태 변경 실패를 별도 추적한다. 변경 결과는 Tool 응답뿐 아니라 최종 Product State로 확인한다.

### Sharing and Export

공유 대상, 사용자의 확인, 포함된 Data 범위, 결과 검증을 추적한다. Dashboard에는 공개 링크나 원본 개인 Data를 노출하지 않는다.

# 12. Privacy-preserving Telemetry

- 기본적으로 대화 전문을 Metric Label이나 일반 운영 Log에 넣지 않는다.
- 자유 형식 Text 대신 제한된 Error Code와 Action Category를 사용한다.
- 사용자별 세그먼트는 목적과 접근 권한이 승인된 경우에만 제공한다.
- 작은 Cohort의 결과는 재식별 위험이 있으면 억제하거나 묶어서 보여준다.
- 운영 Data의 조회, Export, 보존 만료를 통제한다.
- Debug Logging의 활성 기간과 대상 범위를 제한하고 종료를 확인한다.

# 13. Anti-patterns

1. **Success by HTTP 200** — 요청 전달 성공만으로 User Goal이 완료됐다고 본다.
2. **One score for quality** — 복합적인 유용성, 사실성, Safety를 하나의 평균 점수로 뭉갠다.
3. **Optimize acceptance** — 사용자의 수락률을 높이기 위해 불확실성을 숨기거나 확인 질문을 줄인다.
4. **Transcript-first observability** — 추적 편의를 위해 모든 대화 전문과 Tool Payload를 무기한 저장한다.
5. **Unreviewed automatic judge** — 자동 평가 Model을 독립적인 정답으로 취급한다.
6. **Silent metric changes** — 분모나 분류 기준을 바꾸면서 과거 값과 직접 비교한다.
7. **Alert fatigue** — 사용자 영향과 무관한 모든 오류를 긴급 경보로 보낸다.
8. **Deploy on average improvement** — 평균 품질이 올랐다는 이유로 Safety Regression을 허용한다.
9. **Feedback reuse by default** — 한 목적의 피드백을 별도 동의 없이 다른 목적으로 재사용한다.
10. **Dashboard as data dump** — 업무상 필요하지 않은 민감 Data를 운영자 Dashboard에 노출한다.

# 14. Review Checklist

- [ ] User Goal을 반영하는 Outcome Metric이 있는가?
- [ ] Model, Retrieval, Tool, Validation, Persistence를 연결하는 Trace가 있는가?
- [ ] Metric 정의, 분모, Data Source, 한계와 Owner가 기록되어 있는가?
- [ ] 사실성, 권한, Privacy, Data Integrity를 품질 평가에 포함했는가?
- [ ] 자동 평가를 Human Review와 실제 사용자 Correction으로 보완하는가?
- [ ] 사용자 Data와 운영 Telemetry의 목적 및 retention을 분리했는가?
- [ ] 경보 기준이 사용자 영향과 실행 가능한 대응에 연결되는가?
- [ ] 배포별 성공 기준과 Rollback 조건이 정의되어 있는가?
- [ ] RoRo의 Diary, Photo, Trip, Expense, Sharing Flow를 개별 검토하는가?
