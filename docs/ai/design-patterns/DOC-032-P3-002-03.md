# 1. Purpose

본 문서는 Copilot Pattern을 적용할 수 있는 제품·작업 맥락과 적용 여부를 판단하는 기준을 정의한다. 이는 보편적인 정책이나 특정 RoRo 기능의 확정 사양이 아니라, 제품별 설계를 검토하기 위한 기준 초안이다.

# 2. Pattern Context

## 2.1 User Is Already in a Product Task

Copilot Pattern의 출발점은 사용자가 제품에서 진행 중인 Task다. 사용자는 문서, 기록, 일정, 선택한 항목 또는 다른 제품 Resource를 보고 있거나 편집할 수 있다. Copilot은 그 작업의 다음 단계에 필요한 도움을 제공하도록 설계한다.

현재 화면은 사용자의 전체 의도와 같지 않을 수 있다. 사용자가 화면이나 항목을 열었다는 사실만으로 편집·저장·공유를 요청했다고 간주하지 않는다. Task가 불분명하면 범위를 물어보거나, 사용자가 명시적으로 선택하도록 한다.

## 2.2 Task Context and Data Context

설계 시 Task Context와 AI가 사용할 Data Context를 구분한다.

| Context | 의미 | 예시 |
| --- | --- | --- |
| Task Context | 사용자가 현재 하려는 일과 진행 상태 | 초안 작성, 선택한 기록 검토, 현재 입력 단계 |
| Data Context | 해당 Task를 위해 실제로 읽거나 처리할 수 있는 제품 정보 | 사용자가 선택한 문서, 날짜 범위, Trip 또는 Moment |
| Conversation Context | 사용자가 대화에서 명시한 지시와 추가 설명 | 원하는 길이, 말투, 포함하거나 제외할 내용 |

세 가지 Context는 일치하지 않을 수 있다. 예를 들어 현재 Trip 화면에 있더라도 사용자가 다른 Trip을 요청할 수 있고, 대화에서 지정한 범위가 화면의 기본 선택과 다를 수 있다. 충돌하거나 모호한 경우, 제품이 하나를 조용히 우선시하지 않도록 한다. 필요한 경우 사용자에게 확인한다.

## 2.3 Context Boundary

Copilot에 전달할 Context는 다음 순서로 결정하는 것을 권장한다.

```plain text
User's current task and request
        ↓
Candidate product context
        ↓
Relevance, purpose, and access check
        ↓
Minimum context needed for assistance
        ↓
Copilot response or draft
```

현재 화면에 보이는 정보, 저장된 사용자 Data, 다른 Resource, 외부 서비스 정보는 서로 다른 Context 원천이다. 어느 원천이든 사용 전에 Task와의 관련성, 목적, 사용 권한 및 제품 Policy를 확인해야 한다. UI의 근접성이나 기술적 접근 가능성은 단독으로 권한 근거가 되지 않는다.

## 2.4 Missing, Conflicting, or Stale Context

Context가 빠져 있거나 서로 충돌하거나 최신성을 확신할 수 없으면 Copilot은 다음 중 적절한 대응을 선택한다.

- 누락된 정보가 결과에 중요하지 않으면 확인된 범위만으로 응답하고 한계를 알린다.
- 모호함이 결과나 상태 변경에 큰 영향을 주면 사용자에게 선택을 요청한다.
- 권한 또는 데이터 범위가 불명확하면 해당 정보를 사용하지 않고 확인을 기다린다.
- Context가 오래되었거나 제품 상태와 일치하는지 확인할 수 없으면 적용 전에 최신 상태를 재확인한다.

구체적인 신뢰도 임계값이나 갱신 정책은 이 문서에서 정하지 않는다. 제품의 데이터 특성과 오류 영향에 맞춰 후속 설계에서 정의해야 한다.

# 3. Applicability

## 3.1 Good-Fit Conditions

다음 조건이 충족될수록 Copilot Pattern이 적합할 가능성이 높다.

- 사용자가 수행 중인 Task를 제품이 식별하거나 사용자가 명시할 수 있다.
- Task와 관련된 Context를 최소 범위로 결정할 수 있다.
- AI의 역할이 설명, 추천, 초안, 검토 또는 제한된 작업 보조로 표현될 수 있다.
- 사용자가 결과를 이해하고 검토·수정·거절할 수 있다.
- 상태를 변경하는 경우 권한, 확인, 취소 또는 복구 기준을 설계할 수 있다.
- 제품이 제안 이후의 결과를 검증하거나 실패를 분명히 알릴 수 있다.

이는 체크 가능한 후보 조건이지 적용 승인 기준은 아니다. 개인정보, 안전, 접근성, 성능 및 실제 사용자 효용은 제품 단위로 별도 평가한다.

## 3.2 Candidate Use Cases

Copilot Pattern을 검토할 수 있는 사례는 다음과 같다.

| 제품 Task | 가능한 보조 | 적용 시 확인할 경계 |
| --- | --- | --- |
| 사용자가 선택한 문서 편집 | 문장 제안, 요약, 재작성 초안 | 편집 대상과 반영 범위, 원문 보존 및 되돌리기 |
| 사용자가 열어 둔 일정 검토 | 일정 정리 제안, 충돌 후보 설명 | 일정 범위와 실제 변경 권한 |
| 사용자가 선택한 여행 기록 정리 | 선택된 Trip 또는 Moment로 기록 초안 생성 | 선택 범위, 데이터 출처, 초안과 저장의 구분 |
| 제품 데이터 검토 | 현재 보고 있는 결과의 설명 또는 요약 | 근거 Data의 범위와 최신성 |

사례는 Copilot 적용을 검토하기 위한 예시이며, 특정 제품에 해당 기능이 구현되었거나 반드시 구현해야 한다는 뜻은 아니다.

## 3.3 Poor-Fit Conditions and Pattern Combination

현재 Task가 불분명하거나 사용자가 아직 목표를 탐색 중이면 Chat Interaction Pattern이 더 적합한 시작점일 수 있다. 필수 정보를 순서대로 수집해야 하면 Wizard 또는 Conversational Form을 검토한다. 복수의 정해진 업무 단계를 안내해야 하면 Guided Workflow와 조합할 수 있다.

| 상황 | 검토할 방향 |
| --- | --- |
| 넓고 탐색적인 질문, 명확한 화면 Task 없음 | Chat Interaction으로 목표와 범위를 먼저 파악 |
| 필수 값을 빠짐없이 정해진 순서로 수집 | Wizard 또는 Conversational Form 사용·조합 |
| 여러 업무 단계를 정해진 조건으로 진행 | Guided Workflow와 조합하고 단계별 책임을 분리 |
| 사용자의 검토 없이 고위험 또는 되돌릴 수 없는 Action 수행 필요 | 자동 실행을 보류하고 별도 승인·인간 검토 설계 |
| 신뢰할 수 있는 Context 또는 권한을 확인할 수 없음 | 해당 Context를 사용하지 않거나 작업을 진행하지 않음 |

패턴은 함께 사용될 수 있다. 다만 각 패턴의 시작점, 책임, 사용자에게 보이는 전환을 설계해야 한다. Copilot을 사용한다는 이유로 대화형 탐색이나 구조화된 Workflow가 불필요해지는 것은 아니다.

# 4. Applicability Decision Guide

다음 질문으로 초기 적합성을 검토한다.

1. 사용자가 현재 제품에서 어떤 Task를 수행하고 있는가?
2. 해당 Task에 직접 연결된 도움을 제공할 구체적인 이유가 있는가?
3. 필요한 Context를 식별하고 사용 권한 및 목적을 확인할 수 있는가?
4. 사용자가 제안을 실행 결과와 구분해 검토할 수 있는가?
5. 상태 변경이 있다면 사용자 의사, 권한, 복구 및 결과 검증을 설계할 수 있는가?

```plain text
Identifiable product task?
        ├── No → Start with goal discovery or another interaction pattern
        └── Yes
              ↓
Relevant and authorized context available?
        ├── No → Ask, narrow the task, or decline the context
        └── Yes
              ↓
User can review the assistance and control the outcome?
        ├── No → Redesign the interaction or restrict the action
        └── Yes → Copilot may be a candidate; evaluate product risks
```

이 가이드는 기계적인 자동 분류가 아니다. 안전·프라이버시·제품 정책 검토를 대체하지 않는다.

# 5. RoRo Applicability Example

사용자가 특정 Trip 또는 Moment를 열어 두고 관련 여행 기록 초안을 요청하는 경우, Copilot Pattern을 검토할 수 있다. Task는 기록 초안 작성이고, Data Context 후보는 사용자가 선택한 Trip 또는 Moment다. 사용자의 요청과 제품 권한을 확인한 뒤 해당 범위 안에서만 초안을 만들고, 사용자가 검토하거나 수정할 수 있는지 설계한다.

이 예시만으로 RoRo의 현재 데이터 모델, 권한 체계, 저장 흐름 또는 화면이 확정되는 것은 아니다. 구현 가능성은 해당 제품 사양과 권한 규칙을 확인한 뒤 판단해야 한다. 사진이나 기록에서 확인할 수 없는 사실을 단정하지 않는 원칙도 유지한다.

# 6. Review Checklist

- [ ] 사용자가 수행 중인 Task가 식별되거나 명시적으로 지정되는가?
- [ ] Task Context, Data Context, Conversation Context를 구분하는가?
- [ ] 각 Context 원천의 목적, 관련성, 사용 권한을 확인하는가?
- [ ] 화면에 보인다는 이유만으로 데이터를 사용하지 않는가?
- [ ] Context 누락·충돌·최신성 문제에 대한 사용자 확인 또는 제한 처리가 있는가?
- [ ] 해당 Task에 Copilot이 필요한 이유와 기대 효과를 설명할 수 있는가?
- [ ] Chat, Wizard, Conversational Form 또는 Guided Workflow와의 경계가 명확한가?
- [ ] 사용자가 제안과 변경 결과를 구분하고 이를 검토할 수 있는가?
- [ ] RoRo 적용 예시를 구현된 사실이나 승인된 제품 요구사항으로 오해하지 않도록 표시했는가?

# 7. Section Conclusion

Copilot Pattern은 사용자가 진행 중인 제품 Task와 직접 연결된 도움을 제공할 때 검토한다. 적용 여부는 Context가 화면에 존재하는지만으로 정하지 않는다. Task 적합성, Context의 목적과 권한, 사용자 통제, 대안 Pattern과의 조합, 제품별 위험 평가를 함께 고려한다.

이 문서는 Context와 적용 기준을 제안하는 Draft다. 카탈로그의 후속 문서 제목 및 순서는 아직 Part III에서 확인되지 않았으므로, 002-03의 명칭과 전체 문서 로드맵은 검토 과정에서 확정해야 한다.
