## 001-10-B Error Handling & Recovery
### Part B — AI-specific Recovery, Transaction Safety, RoRo Flows & Operations

# 64. AI Hallucination Recovery

Hallucination 또는 근거가 없는 주장은 일반적인 Model Error와 다르게 처리한다. 응답 형식이 유효해도 사실 근거가 부족하면 Technical Success로 간주하지 않는다.

Detection signal:

    Source not found
    Retrieved data conflicts with generated claim
    Required evidence is missing
    Model confidence is below policy threshold
    User disputes a factual statement

Recovery Flow:

    Claim Detection
       ↓
    Evidence Check
       ↓
    Supported?
       ├── YES → Continue with source-aware wording
       └── NO  → Remove, qualify, or ask

AI는 근거가 없는 Trip, 장소, 시간, 인물, 비용 정보를 보완해서 만들어내면 안 된다. 사실을 검증할 수 없으면 불확실성을 밝히고, User에게 확인하거나 해당 주장을 생략한다.

예:

> 영수증에서 결제 금액을 확인하지 못했어요. 금액을 직접 입력해 주시겠어요?

이미 잘못된 내용을 사용자에게 전달했다면 다음을 수행한다.

1. 잘못된 주장과 영향을 확인한다.
2. 근거가 있는 정보만으로 정정한다.
3. 영향을 받은 Draft 또는 저장 Data가 있는지 확인한다.
4. 영구 Data가 변경되었다면 User에게 변경 상태를 알린다.
5. 원인과 Correction을 Interaction Trace에 남긴다.

# 65. Context Conflict Recovery

Context Conflict는 둘 이상의 유효해 보이는 Source가 서로 다른 값을 제시하는 상태다.

예:

    Photo timestamp: 12:30
    User correction: "이 사진은 저녁에 찍었어."
    Trip timezone: UTC+9
    Device timezone: UTC-7

Conflict Resolution 우선순위는 Data 종류에 따라 정한다. 일반적으로:

    Explicit current User correction
      >
    Verified Product record
      >
    Trusted tool result
      >
    Derived metadata
      >
    Model inference

단, User correction이 권한이나 Security Rule을 무효화하지는 않는다. Source와 신뢰 수준이 다른 Data를 조용히 덮어쓰지 않는다.

Recovery Flow:

    Conflict Detected
       ↓
    Identify fields and sources
       ↓
    Is there a deterministic policy?
       ├── YES → Apply policy and retain provenance
       └── NO  → Ask a focused clarification
       ↓
    Validate resolved context
       ↓
    Resume from the earliest affected step

질문은 충돌하는 항목만 좁혀서 묻는다.

> 일정에는 저녁 식사로 기록되어 있고 사진 시간은 점심 무렵이에요. 사진 시간을 기준으로 일기를 쓸까요, 일정을 기준으로 쓸까요?

# 66. Tool Failure Recovery

Tool Failure가 발생하면 Model이 Tool을 성공한 것처럼 설명하거나, 실패한 Tool의 결과를 추정해서는 안 된다.

Recovery 단계:

1. Tool 호출 전 입력과 권한을 검증한다.
2. Error Code, Retryability, Side Effect 여부를 확인한다.
3. Retryable한 경우 제한된 Retry Policy를 적용한다.
4. 대체 Tool 또는 Partial Result가 안전한지 확인한다.
5. 결과를 다시 검증한 뒤 Interaction State를 갱신한다.
6. 복구되지 않으면 User가 이해할 수 있는 다음 선택지를 제시한다.

Tool 결과를 받지 못한 Timeout은 작업 미수행을 뜻하지 않을 수 있다. 특히 Create, Save, Share, Delete와 같은 Action은 먼저 작업 상태를 조회하고 중복 실행을 방지한다.

# 67. Multi-tool Failure

하나의 User Goal이 여러 Tool에 의존하면 각 Tool의 상태를 독립적으로 추적한다.

예:

    Load Trip       → Success
    Load Schedule   → Success
    Search Photos   → Timeout
    Load Expenses   → Success

다음과 같은 상태 표현을 사용한다.

    completed: trip, schedule, expenses
    failed: photos
    unknown: none
    retryable: photos

모든 Tool을 처음부터 재실행하지 않는다. 실패한 Step만 Retry하고, 앞서 성공한 결과는 Freshness와 State Version이 유효한 동안 보존한다.

한 Tool의 결과가 다른 Tool의 입력을 바꾸면 그 하위 Step만 다시 계산한다.

    Trip context changed
       ↓
    Revalidate schedule and photo query
       ↓
    Preserve unrelated expense result

# 68. Partial Success

핵심 Goal의 일부만 완료된 경우 Partial Success로 처리한다. 완료된 항목과 실패한 항목을 분리해 표시하고, User에게 전체 실패처럼 알리거나 완전 성공처럼 표현하지 않는다.

예:

> 일정과 지출은 확인했지만 사진 검색이 끝나지 않았어요. 일정과 지출만 반영한 일기 초안을 만들거나 사진을 다시 불러올 수 있어요.

Partial Result를 저장하기 전에 다음을 확인한다.

- 누락된 Data가 결과 의미를 바꾸는가?
- Partial Result라는 사실이 저장물에도 남는가?
- User가 완성본으로 오해할 가능성이 있는가?
- 추가 Data를 받으면 안전하게 재개할 수 있는가?

결과에 영향을 주는 누락은 화면과 저장 Data 양쪽에 표시한다.

# 69. Offline / Network Recovery

Network 장애에서는 현재 보유한 Data의 Freshness와 작업 가능 범위를 확인한다.

    Network unavailable
       ↓
    Can this action run locally?
       ├── YES → Save local draft with pending-sync state
       └── NO  → Preserve input and offer retry

Local Draft를 지원하는 경우 다음 상태를 분리한다.

    saved_locally
    sync_pending
    synced
    sync_conflict
    sync_failed

Offline 상태에서 외부 Data를 조회한 것처럼 응답하지 않는다. Reconnect 후 Sync할 때 Version Conflict가 있으면 자동으로 한쪽 Data를 덮어쓰지 않고 Conflict Recovery를 실행한다.

Retry는 Network 복구만으로 자동 실행해도 되는 읽기 작업과 User Confirmation이 필요한 외부 변경 작업을 구분한다.

# 70. Draft Recovery

Draft는 Interaction 중 가장 먼저 보호해야 할 User Data다.

권장 Save Point:

    Input received
       ↓
    Draft created
       ↓
    Each meaningful edit checkpoint
       ↓
    Final validation
       ↓
    User-approved save

Generation이나 Network Error가 발생해도 마지막 유효 Draft를 유지한다. 새 결과가 실패했으면 기존 Draft를 빈 화면이나 오류 응답으로 대체하지 않는다.

복구 가능한 Draft에는 다음 정보를 연결한다.

    draft_id
    trip_id
    day_id
    version
    last_saved_at
    generation_status
    unsynced_changes

복구 후 User에게 필요할 때만 상태를 간결하게 알린다.

> 작성 중이던 초안을 복구했어요. 마지막 수정 내용부터 이어서 확인할 수 있습니다.

# 71. Transaction Recovery

여러 Data 변경이 하나의 논리적 작업을 구성하면 Transaction Boundary를 정의한다.

예: Expense 생성은 Expense Record와 Trip 합계 업데이트를 함께 다룬다.

    Validate receipt
       ↓
    Create expense
       ↓
    Update trip total
       ↓
    Confirm transaction

중간 Step이 실패하면 다음 중 하나를 적용한다.

- Atomic transaction: 전부 성공하거나 전부 취소한다.
- Saga: 완료된 Step을 보상 Action으로 되돌린다.
- Pending state: 완료 여부가 불명확한 상태를 보존하고 조회 후 재개한다.

외부 Service가 포함된 경우 분산 Transaction이 완전히 원자적이라고 가정하지 않는다. 사용자에게 최종 상태를 알리기 전에 관련 Record를 다시 확인한다.

# 72. Idempotency

Retry로 동일한 Action이 중복 생성되지 않도록 Idempotency를 적용한다.

권장 Key 구성:

    operation_type
    + user_id
    + resource_id
    + client_request_id

동일 Key의 중복 요청은 새로운 Side Effect를 만들지 않고 이전 결과나 현재 상태를 반환한다.

적용 우선순위가 높은 Action:

    Create Diary
    Create Expense
    Upload Photo
    Send Share Invitation
    Delete or Archive

Idempotency Key는 사용자의 Data를 식별할 수 있으므로 최소 범위로 생성하고 보존 기간을 제한한다.

---

# 73. Compensation

Rollback이 불가능한 외부 Action에는 Compensation을 사용한다.

예:

    Share invitation sent
       ↓
    User cancels sharing
       ↓
    Revoke invitation

Compensation은 원래 Action을 없던 일로 만드는 것과 같지 않다. 외부에 이미 전달된 정보나 알림은 되돌릴 수 없을 수 있다. 따라서:

- 가능한 보상 Action과 불가능한 영향 범위를 사전에 정의한다.
- 보상 결과를 확인한다.
- 사용자에게 남은 영향을 설명한다.
- 원본과 보상 Action을 모두 감사 기록에 남긴다.

---

# 74. Rollback

Rollback은 변경 전 State로 안전하게 복귀할 수 있을 때만 사용한다.

Rollback 전 확인:

    Is the operation reversible?
    Has another operation depended on the result?
    Is the previous version still valid?
    Will rollback remove user-authored data?

AI는 사용자가 만든 내용이나 이미 공유된 Data를 임의로 삭제해 Rollback하면 안 된다. 복구가 불가능하거나 Data Loss가 발생할 수 있다면 작업을 중단하고 User Confirmation을 요청한다.

Rollback 성공 후에는 State Version과 관련 집계를 다시 검증한다.

---

# 75. User Confirmation

Confirmation은 불확실성을 해결하기 위한 질문과 구분한다. Confirmation은 User가 이미 요청한 Action의 결과가 외부에 영향을 주거나 되돌리기 어려울 때 필요하다.

Confirmation 대상의 예:

    Share a diary with another person
    Delete a saved memory
    Replace an existing finalized diary
    Submit a payment or booking
    Apply a bulk change

Confirmation Prompt는 다음을 분명히 설명한다.

    Action
    Target
    Material consequence
    Reversibility
    Confirm / Cancel choices

확인 이후 Action을 실행하기 직전에 Target과 Data가 바뀌지 않았는지 재검증한다. 확인 시점과 실행 시점 사이에 중요한 변경이 생기면 다시 확인한다.

Low-impact, reversible한 Draft 수정에는 불필요한 Confirmation을 요구하지 않는다.

# 76. Safe Failure

Recovery가 안전하지 않거나 상태를 확인할 수 없으면 Fail Safely한다.

Safe Failure는 다음을 보장한다.

- 사용자 입력과 저장된 Data를 보존한다.
- 확인되지 않은 상태를 성공으로 표시하지 않는다.
- 권한 경계를 우회하지 않는다.
- 중복 Side Effect를 만들지 않는다.
- 내부 Stack Trace와 Secret을 노출하지 않는다.
- 사용자가 할 수 있는 다음 행동을 제공한다.

예:

> 저장 완료 여부를 확인하지 못했어요. 중복 저장을 막기 위해 다시 만들기 전에 저장 목록을 먼저 확인할게요.

Security Critical Error는 Retry나 Fallback보다 차단, 제한된 Logging, 운영자 알림을 우선한다.

# 77. RoRo Diary Error Flow

Daily Diary Generation의 대표 Flow:

    Select Trip and Day
       ↓
    Load schedule, moments, photos, expenses
       ↓
    Validate ownership, date, timezone, freshness
       ↓
    Generate Draft
       ↓
    Validate claims and source references
       ↓
    Save Draft with version
       ↓
    Present to User for review

Recovery examples:

| Failure | Recovery |
|---|---|
| Trip or day missing | 어떤 여행과 날짜인지 확인 |
| Photos unavailable, schedule available | 누락을 표시하고 일정 기반 Draft 선택지 제공 |
| Model output invalid | 제한된 재생성 후에도 실패하면 Draft를 보존하고 안전한 오류 안내 |
| Save timeout | 저장 상태 조회 후 Idempotency Key로 중복 방지 |
| User corrects a place or time | 해당 claim과 영향을 받은 문장만 다시 생성하고 수정 내용을 반영 |

User가 승인하기 전 Diary를 Finalized로 표시하거나 공유하지 않는다.

# 78. RoRo Photo Error Flow

Photo Flow는 Upload, Metadata Extraction, Association, AI Analysis를 별도 Step으로 추적한다.

    Upload
       ↓
    Validate file and permission
       ↓
    Store original
       ↓
    Extract metadata
       ↓
    Associate with trip/day
       ↓
    Optional AI analysis

한 Step의 실패가 원본 Photo를 삭제하지 않도록 한다. Metadata가 없거나 잘못된 경우 추정값과 확인된 값을 구분한다.

예:

- Upload 실패: 선택된 Photo와 입력 상태를 유지하고 Retry 제공.
- Trip 연결 실패: Photo를 미분류 상태로 보존하고 Trip 선택 요청.
- AI 분석 실패: 업로드 성공 상태는 유지하고 분석 기능만 재시도.
- 중복 업로드 의심: Hash 또는 Asset ID를 조회해 같은 Photo의 중복 Record를 방지.

# 79. RoRo Expense Error Flow

Expense는 금액, 통화, 결제일, 지불자, Trip 연결을 분리해 검증한다.

    Receipt or manual input
       ↓
    Extract candidate fields
       ↓
    Validate currency and amount
       ↓
    User review when uncertain
       ↓
    Save Expense idempotently
       ↓
    Recalculate trip total

OCR 또는 AI가 읽은 값은 후보값이다. 불확실한 금액이나 통화를 확인된 사실처럼 저장하지 않는다. Trip Total 업데이트가 실패하면 Expense 생성 상태를 조회한 뒤 집계를 재계산한다. 재시도 때 Expense Record를 중복 생성하지 않는다.

# 80. RoRo Sharing Error Flow

Sharing은 외부 Side Effect이므로 명시적 사용자 요청과 대상 확인을 요구한다.

    Prepare share preview
       ↓
    Confirm recipient and content
       ↓
    Check current permissions
       ↓
    Send once with idempotency key
       ↓
    Verify delivery state

Timeout이 발생하면 곧바로 다시 보내지 않는다. 먼저 전송 상태를 조회한다.

    sent      → 성공 상태와 시간 표시
    not_sent  → 재시도 선택지 제공
    unknown   → 중복 방지를 위해 상태 확인 중임을 설명

공유 취소 후에도 이미 전달된 사본을 회수할 수 없을 수 있다. 취소 Action의 실제 효과를 정확히 설명한다.

# 81. AI Retry Policy

Retry는 오류 유형, Action의 영향, Idempotency, 지연 한도를 함께 고려한다.

| Operation | Default retry behavior |
|---|---|
| Read-only retrieval | 일시적 Network/Timeout에서 제한적으로 자동 Retry |
| Model generation | 1회 이내의 제한된 재시도, Draft 보존 |
| Draft save | 상태 확인 및 Idempotency 후 재시도 |
| Create Expense or Diary | 상태 조회와 Idempotency 확인 후 재시도 |
| Share, payment, delete | 자동 재전송 금지; 상태 조회와 필요 시 User 확인 |

권장 Policy 항목:

    max_attempts
    per_attempt_timeout
    total_deadline
    backoff
    jitter
    idempotency_key
    retry_after_state_check

Retry Exhaustion 후에는 Partial Success, Fallback, Clarification, Safe Failure 중 하나를 선택하고 사용자가 같은 작업을 무한 반복하지 않도록 한다.

# 82. Recovery Metrics

Recovery 품질은 성공률뿐 아니라 Data와 User 영향으로 측정한다.

권장 Metric:

    recovery_success_rate
    retries_per_interaction
    duplicate_side_effect_rate
    draft_restore_rate
    partial_success_rate
    unknown_transaction_duration
    user_correction_rate
    recovery_abandonment_rate
    time_to_safe_resolution

Metric은 Error Code, Tool, App Version, State, Recovery Strategy 단위로 집계한다. User 개인을 식별할 수 있는 원문 Prompt나 여행 Data를 일반 분석 Log에 복사하지 않는다.

# 83. Error Observability

Observability는 한 Interaction의 전체 복구 경로를 재구성할 수 있어야 한다.

    interaction_id
       ├── validation events
       ├── tool attempts
       ├── model generation
       ├── state transitions
       ├── recovery decisions
       └── final outcome

기록할 항목:

    error_code
    operation_id
    state_before / state_after
    attempt_number
    recovery_strategy
    latency
    outcome

Logging에는 필요한 최소 정보만 남긴다. 원문 사진, 영수증, 일기 내용, Credential은 기본 Error Log에 넣지 않는다. Trace ID를 User가 Support에 제공할 수 있도록 하되 Secret이나 내부 경로는 노출하지 않는다.

# 84. Error UX

Error UX는 복구 상태를 사용자가 이해하고 다음 행동을 선택할 수 있게 한다.

권장 메시지 요소:

    What failed
    What was preserved
    What is uncertain
    What the user can do next

화면 상태는 작업 단위로 표시한다.

    사진 업로드 완료
    일정 조회 완료
    일기 초안 저장 대기
    공유 상태 확인 중

동일한 오류를 반복해서 표시하지 않고, Retry가 진행 중이면 상태와 예상 가능한 다음 단계를 보여준다. Error Message는 원인을 과장하거나 사용자 탓으로 돌리지 않는다.

---

# 85. Error Prevention

Recovery 설계와 함께 Failure 가능성을 줄인다.

    Typed schema and boundary validation
    Permission checks before retrieval
    Explicit State transitions
    Idempotency for Side Effects
    Autosave for user-authored drafts
    Version checks for concurrent updates
    Timezone-aware date handling
    Tool timeout and payload limits
    Dependency health checks
    User preview before irreversible actions

예방 규칙은 한 곳에만 두지 않는다. UI 제약, Service Validation, 권한 검사, 최종 저장 직전 Validation을 함께 둔다. 클라이언트 검증만으로 Data Integrity를 보장하지 않는다.

---

# 86. Final Recovery Architecture

전체 Error Handling & Recovery Architecture:

    User Request
       ↓
    Input and Permission Validation
       ↓
    Intent and Context Validation
       ↓
    State-aware Plan
       ↓
    Tool Execution with Trace and Idempotency
       ↓
    Result Validation and Evidence Check
       ├── Complete → Save / Continue
       ├── Partial  → Preserve completed results and disclose missing parts
       ├── Retryable → Bounded retry after state check
       ├── Ambiguous → Ask a focused clarification
       └── Unsafe / Unknown → Safe Failure
       ↓
    Verify persisted state
       ↓
    Explain outcome and next action

Recovery Handler는 재시도 횟수만 관리하는 공통 Catch Block이 아니다. Error Classification, Side Effect, Permission, State Integrity, Provenance를 함께 고려하는 Interaction Component다.

---

# 87. Design Principles

1. **Truth over apparent completion** — 확인하지 못한 작업을 성공했다고 말하지 않는다.
2. **Preserve before retry** — User 입력과 Draft를 먼저 보존한다.
3. **Retry only when safe** — Side Effect와 Idempotency를 확인한다.
4. **Recover the smallest failed unit** — 성공한 Step을 불필요하게 반복하지 않는다.
5. **Make partial state explicit** — 완료, 실패, 불확실 상태를 구분한다.
6. **Keep permission boundaries intact** — 오류 복구를 이유로 권한을 우회하지 않는다.
7. **Explain impact and next action** — 기술 오류보다 사용자 영향과 선택지를 설명한다.
8. **Validate after recovery** — 재시도 성공만으로 전체 작업 성공을 가정하지 않는다.
9. **Keep an auditable trace** — 복구 과정과 최종 결과를 최소한의 Data로 추적한다.
10. **Require confirmation for consequential changes** — 외부 공유와 되돌리기 어려운 작업을 보호한다.
