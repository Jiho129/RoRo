# DOC-032 — AI Design Pattern Catalog

## Part III — Interaction Patterns

# AI-PATTERN-001 — Chat Interaction Pattern

## 001-13 Implementation, Deployment & Lifecycle

---

# 1. Purpose

본 문서는 AI-PATTERN-001 Chat Interaction을 Product에 구현하고, 환경별로 배포하며, 안전하게 변경·중단·폐기하기 위한 구현 기준을 정의한다.

앞선 문서는 Interaction, State, Context, Error Recovery, Security 및 운영 평가 원칙을 정의했다. 이 문서는 그 원칙이 구현과 배포 과정에서 유지되도록 필요한 Component Boundary, Interface, Configuration, Change Control을 설명한다. 특정 Cloud, LLM Vendor, Framework를 강제하지 않는다.

# 2. Implementation Principles

1. **Policy outside the model** — 권한, Business Rule, State 변경은 신뢰 가능한 Application Layer에서 통제한다.
2. **Explicit interfaces** — Model, Tool, Retrieval, Persistence 간 입력과 출력을 Schema로 정의한다.
3. **Replaceable dependencies** — Model과 Vendor 종속 설정을 경계 뒤에 둔다.
4. **Fail safely** — 필수 검증이나 권한 서비스가 불가능하면 보호가 필요한 Action을 중단한다.
5. **Observable by design** — 주요 Component는 상관 관계가 있는 상태와 오류를 남긴다.
6. **Version every behavior change** — Prompt, Model, Tool Schema, Policy, Evaluation Set의 변경을 추적한다.

# 3. Reference Implementation Architecture

```plain text
Conversation UI
      ↓
Conversation API / Gateway
      ↓
Orchestrator
  ├── Identity and Policy Service
  ├── Context Builder / Retrieval
  ├── Model Adapter
  ├── Tool Gateway
  ├── Output Validator
  └── Conversation / Draft Store
      ↓
Telemetry and Evaluation Events
```

### Component Responsibilities

| Component | Responsibility | Must not do |
| --- | --- | --- |
| Conversation UI | 입력, 진행 상태, 결과와 오류 표시 | 권한 결정을 단독 수행 |
| API / Gateway | 인증, 요청 검증, rate limit, correlation id | Model 응답을 검증 없이 영속화 |
| Orchestrator | 단계 순서, timeout, cancellation, partial result 관리 | 정책 검사를 건너뛰어 성공 처리 |
| Policy Service | User, Resource, Action별 권한과 정책 결정 | Model이 반환한 텍스트를 승인 근거로 사용 |
| Context Builder | 목적에 맞는 최소 Context 구성과 provenance 부여 | 서로 다른 User의 Context 병합 |
| Model Adapter | Vendor API와 표준 내부 Interface 변환 | Secret 또는 권한 자체를 소유 |
| Tool Gateway | 허용된 Tool 실행, 인자 검증, 결과 정규화 | 임의 코드나 무제한 네트워크 접근 제공 |
| Output Validator | Schema, Policy, 근거, 민감 정보 검증 | 모든 생성 문장을 사실로 간주 |
| Store | Conversation, Draft, 상태의 일관성 있는 저장 | 권한 검사 없이 타 사용자 Data 반환 |

# 4. Request Lifecycle

```plain text
1. Authenticate and validate request
2. Create interaction_id and establish deadlines
3. Resolve user goal and required context
4. Authorize each retrieval and tool action
5. Build minimum scoped context with source labels
6. Invoke the configured model adapter
7. Validate structured output and proposed actions
8. Execute approved, authorized tools
9. Verify resulting product state
10. Persist or present result according to user intent
11. Emit privacy-preserving operational events
```

각 단계는 실패 결과를 명시한다. 성공한 Step만으로 후속 단계의 성공을 추정하지 않는다. Request cancellation과 timeout은 가능한 경우 실행 중 Tool에도 전파한다.

# 5. Interface and Schema Requirements

내부 Interface는 최소한 다음 공통 필드를 전달한다.

    interaction_id
    authenticated_user_reference
    tenant_or_workspace_scope (when applicable)
    request_goal / intent
    policy_context
    data_sources with provenance and trust class
    deadline / cancellation signal
    result status and error classification

Tool Schema에는 이름, 목적, 입력 형식, 입력 제약, 필요 권한, 부작용, timeout, idempotency 지원 여부, 결과 형식, 오류 유형을 정의한다.

Model 출력은 가능한 경우 제한된 JSON Schema 또는 동등한 Typed Contract로 받는다. Parse 실패 시 자연어 응답을 Tool 입력으로 변환해 실행하지 않는다.

# 6. Configuration and Secrets

환경 설정은 코드에 고정하지 않고 승인된 Configuration Store에서 관리한다.

- Model name/version, timeout, output limit, temperature 등의 설정
- Tool allowlist와 Tool별 권한·제한
- Retrieval source, freshness 정책, maximum context size
- Retry budget, fallback 조건, circuit breaker 기준
- Feature flag, rollout cohort, emergency disable switch
- Evaluation version, alert threshold, cost limit

API Key와 Secret은 Secret Manager 또는 동등한 안전 저장소에서 관리한다. Secret을 Repository, Prompt, 일반 Log, User-facing 오류에 기록하지 않는다. 환경별 Secret은 분리하고 필요한 Service에만 부여한다.

# 7. Model and Vendor Adapter

Model Adapter는 Vendor별 요청·응답 차이를 내부 표준 Interface로 변환한다.

표준화할 항목:

- 응답 본문, 구조화 출력, finish reason
- Token usage와 비용 추정치
- timeout, rate limit, content filtering 오류
- Tool Call 제안과 schema validation 결과
- retry 가능 여부와 Vendor request id

Model 교체는 단순한 Endpoint 변경으로 간주하지 않는다. 출력 형식, 거절 동작, Context 처리, 품질·Safety·비용 결과를 평가한 후 활성화한다. Vendor 별 기능 차이를 명시하고 미지원 기능을 조용히 무시하지 않는다.

# 8. State, Persistence and Idempotency

- User-authored Draft와 AI-generated suggestion을 구분한다.
- 대화 상태 변경은 정의된 State Transition을 따른다.
- 영속화가 성공했는지 저장소 상태를 확인한 뒤 완료로 응답한다.
- 재전송될 수 있는 Request에는 적절한 idempotency key를 사용한다.
- 같은 interaction_id의 재실행이 중복 Diary, Share, Expense 변경을 만들지 않도록 Side Effect 경계를 둔다.
- Schema Migration은 이전 버전 Data의 읽기, 롤백, 복구 계획과 함께 배포한다.

# 9. Timeout, Retry and Resilience

각 외부 Dependency에 timeout과 전체 Request Deadline을 설정한다. Retry는 오류 분류와 Idempotency에 따라 제한하며, retry budget을 초과하면 명시적 partial result 또는 safe failure를 반환한다.

Fallback은 다음 우선순위를 따른다.

    validated cached/read-only result (when fresh and authorized)
       ↓
    reduced capability with explicit limitation
       ↓
    preserve draft and allow user to continue later
       ↓
    safe failure with next action

보안, 권한, Data Integrity 오류는 다른 Model이나 Tool로 자동 우회하지 않는다. Circuit Breaker는 장애가 있는 Dependency로의 반복 호출을 제한하고 복구 후 단계적으로 다시 연다.

# 10. Deployment Environments

Environment별로 Data, Secret, Access, External Integration을 분리한다.

| Environment | Use | Data controls |
| --- | --- | --- |
| Local development | 구현 및 개발자 검증 | 합성 또는 비식별 Data 우선 |
| Test / staging | 통합·회귀 검증 | Production User Data 복사 금지 또는 별도 승인·통제 |
| Production | 실제 User Interaction | 최소 권한, 모니터링, Incident 대응, 변경 이력 |

Production Data를 lower environment로 복제하는 것은 기본값으로 허용하지 않는다. 필요 시 목적, 범위, 비식별화, 접근, 삭제 시점을 명시한다.

# 11. Release and Rollout

배포 절차:

1. 변경된 Prompt, Model, Tool, Policy, Schema와 영향 Flow를 식별한다.
2. 관련 Evaluation Set에서 품질, Security, Privacy, Data Integrity를 검토한다.
3. Version과 rollback target을 기록한다.
4. Feature Flag 또는 단계적 Cohort로 노출을 제한한다.
5. User outcome, 오류, Safety, latency, 비용을 함께 관찰한다.
6. 중단 기준을 초과하면 영향 기능을 disable하거나 이전 안정 Version으로 되돌린다.
7. rollout 결과와 미해결 이슈를 기록한다.

Prompt-only 변경도 사용자 행동과 외부 Tool 호출을 바꿀 수 있으므로 변경 관리 대상이다.

# 12. Versioning and Change Management

각 Release에서 다음을 함께 고정 또는 참조한다.

    application build
    model identifier / version
    system prompt and policy version
    tool schema version
    context / retrieval configuration
    evaluation set and result
    feature flags and rollout cohort

Version은 변경 영향에 따라 적용한다. 권한, Data Contract, State Transition, Tool Side Effect의 호환되지 않는 변경은 Major 수준으로 취급한다. 설명과 한계가 바뀌는 변경도 기록한다.

# 13. Capacity, Cost and Rate Limits

- User, tenant, Tool, Model별 요청량과 동시 실행을 제한한다.
- Context 크기와 생성 길이에 상한을 둔다.
- 고비용 요청은 기능과 사용자 가치에 따라 예산과 경보를 설정한다.
- Rate limit 초과는 안전한 대기, 축소 기능 또는 명확한 재시도 안내로 처리한다.
- 비용 절감을 이유로 권한 검사, 결과 검증, Privacy 통제를 생략하지 않는다.

# 14. Operational Ownership

운영 가능한 구현은 다음 Ownership을 명시한다.

- Pattern 및 Prompt/Policy 변경 책임자
- Model과 외부 Vendor 관리 책임자
- Tool 및 Product Data Integration 책임자
- Security / Privacy Incident 대응자
- 품질 Evaluation 및 Rollback 판단자
- Alert 응답과 사용자 공지 책임자

소규모 팀에서는 한 사람이 여러 역할을 맡을 수 있지만, 각 역할과 대체 연락 경로는 분명해야 한다.

# 15. Deprecation and Retirement

Model, Tool, Prompt, Pattern Version을 폐기할 때에는 다음을 수행한다.

1. 사용 중인 Client와 Dependency를 확인한다.
2. 대체 경로와 마이그레이션 필요성을 정한다.
3. 사용자 Data와 저장 포맷 호환성을 확인한다.
4. 일정과 영향 범위를 사전에 알린다.
5. 단계적으로 비활성화하고 오류와 사용자 결과를 관찰한다.
6. 종료 후 더 이상 필요하지 않은 Secret, Integration, 임시 Data를 제거한다.
7. 폐기 Version과 남은 제한을 문서화한다.

# 16. RoRo Implementation Examples

### Diary Draft Generation

요청 인증, 현재 Trip 권한, 선택된 Moment와 Photo 범위를 확인하고, 제한된 Context로 Draft를 생성한다. Draft 저장 결과를 검증한 후 사용자에게 저장 완료 상태를 알린다. Model 오류 시 사용자 초안과 이미 선택한 Moment를 보존한다.

### Schedule Lookup

읽기 전용 Tool은 Trip Scope와 날짜를 검증한다. Timezone과 조회 시점을 응답에 반영하고, Tool 결과가 오래되었거나 불완전하면 그 범위를 표시한다.

### Sharing Action

공유 대상과 포함 Data를 구성하고 사용자 확인을 기록한 후, 권한이 있는 Share Tool만 호출한다. 생성된 Share 상태와 접근 범위를 확인해 결과를 보고한다.

# 17. Implementation Review Checklist

- [ ] 권한과 Business Rule이 Model 응답과 분리되어 있는가?
- [ ] Component Boundary와 Interface Schema가 문서화되었는가?
- [ ] Tool의 권한, 부작용, timeout, idempotency가 정의되었는가?
- [ ] Model 및 Vendor 변경을 Adapter 경계 안에서 평가할 수 있는가?
- [ ] Secret과 환경별 Data가 분리되어 있는가?
- [ ] Timeout, cancellation, bounded retry, safe fallback이 있는가?
- [ ] 저장 결과와 Side Effect의 실제 상태를 검증하는가?
- [ ] 평가 Version, Rollout, Rollback 절차가 있는가?
- [ ] 운영 Ownership과 Incident 경로가 있는가?
- [ ] RoRo의 Diary, Schedule, Share Flow가 권한 및 상태 규칙을 따르는가?

# 18. Anti-patterns

1. **Model as policy engine** — Model 문장만으로 권한이나 Business Rule을 강제한다.
2. **Vendor lock in the core** — Vendor 고유 응답 형식이 도메인 전체에 퍼진다.
3. **Unbounded agent loop** — 종료 조건, 비용 상한, cancellation 없는 반복 Tool Call을 허용한다.
4. **Retry every failure** — 권한 거부나 유효성 오류를 일시 장애처럼 재시도한다.
5. **Prompt as deployment artifact only** — Prompt Version과 변경 이력을 추적하지 않는다.
6. **Staging with copied user data** — 편의를 위해 Production 대화를 무통제 복제한다.
7. **Success before persistence** — 저장 완료를 확인하기 전에 사용자에게 완료를 알린다.
8. **Rollback without state compatibility** — 애플리케이션만 이전 버전으로 내리고 변경된 Data 상태를 확인하지 않는다.
9. **One shared secret** — 개발·테스트·운영에서 동일한 Secret과 권한을 사용한다.
10. **Cost control by removing safeguards** — 검증이나 권한 경계를 제거해 비용을 낮춘다.
