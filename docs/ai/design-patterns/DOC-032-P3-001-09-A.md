# DOC-032 — AI Design Pattern Catalog
## Part III — Interaction Patterns
# AI-PATTERN-001 — Chat Interaction Pattern
## 001-09-A Data Flow & Context Flow
### Part A — Data Model, Input Flow & Context Resolution
---
# 1. Purpose
본 문서는 AI-PATTERN-001 Chat Interaction Pattern에서 발생하는 **Data Flow와 Context Flow**를 정의한다.
AI Chat Interaction에서 User Message는 단순한 Text Input이 아니다.
하나의 User Request는 다음과 같은 여러 Data를 포함할 수 있다.
```plain text
User Message
Conversation History
User Identity
Current Session
Current Trip
Current Date
Memories
Photos
Schedule
Expenses
Permissions
Product State
Tool Results
```
따라서 AI가 정확한 결과를 만들기 위해서는 단순히 Prompt에 모든 정보를 넣는 방식이 아니라, **필요한 Context를 필요한 시점에 선택하고 조합하는 Data Flow**가 필요하다.
본 문서의 핵심 목표는 다음과 같다.
1. User Input이 어떻게 Data로 변환되는가?
2. 어떤 Data가 Context가 되는가?
3. Context는 어디에서 조회되는가?
4. 어떤 Context를 AI에게 전달해야 하는가?
5. Context가 너무 많을 경우 어떻게 줄이는가?
6. Tool Result는 어떻게 다시 Context에 반영되는가?
7. 최종 Response는 어떤 Data를 근거로 생성되는가?
---
# 2. Core Principle
AI-PATTERN-001의 Data Flow는 다음 원칙을 따른다.
> **모든 Data를 AI에게 전달하는 것이 아니라, User Goal을 해결하는 데 필요한 Context만 선택적으로 제공한다.**
즉:
```plain text
All Data
   ↓
Context Selection
   ↓
Relevant Data
   ↓
AI Processing
```
이다.
이는 다음 문제를 방지하기 위한 것이다.
```plain text
Context Overload
Irrelevant Information
Privacy Leakage
Token Waste
Latency Increase
Incorrect Reasoning
Stale Data Usage
```
---
# 3. Data Flow Overview
전체적인 Data Flow는 다음과 같다.
```plain text
USER
  │
  ▼
User Input
  │
  ▼
Input Normalization
  │
  ▼
Intent / Entity Extraction
  │
  ▼
Context Requirement Detection
  │
  ▼
Context Retrieval
  │
  ├── Conversation
  ├── User
  ├── Trip
  ├── Memory
  ├── Photo
  ├── Schedule
  ├── Expense
  └── Product State
  │
  ▼
Context Filtering
  │
  ▼
Context Assembly
  │
  ▼
AI Processing
  │
  ├── Reasoning
  ├── Retrieval
  ├── Generation
  └── Tool Selection
  │
  ▼
Tool Execution
  │
  ▼
Tool Result
  │
  ▼
Result Normalization
  │
  ▼
Context Update
  │
  ▼
Response Generation
  │
  ▼
User Response
```

# 4. Data Flow Layers
Data Flow는 크게 7개 Layer로 나눈다.
## Layer 1 — Input
User가 제공한 원본 정보.
```plain text
Text
Image
Voice
Button
Selection
File
UI Action
```
## Layer 2 — Interpretation
AI가 Input의 의미를 해석한다.
```plain text
Intent
Entity
Constraint
Goal
Preference
```
## Layer 3 — Context
현재 Task에 필요한 외부 및 내부 Data.
```plain text
User Context
Conversation Context
Product Context
Domain Context
```
## Layer 4 — Execution
Tool 및 Backend Data를 호출한다.
```plain text
Search
Retrieval
Database
AI Service
External API
```
## Layer 5 — Result
Tool에서 반환된 결과.
```plain text
Search Result
Retrieved Memory
Photo List
Schedule
Expense Data
Generated Content
```
## Layer 6 — Validation
Result의 유효성을 확인한다.
```plain text
Schema
Freshness
Permission
Consistency
Business Rule
```
## Layer 7 — Response
User에게 전달되는 최종 결과.
```plain text
Text
Card
Gallery
Timeline
Draft
Action Result
```
---
# 5. Raw Input
Raw Input은 User가 직접 전달한 원본 Data다.
예:
```plain text
"오늘 여행일기 만들어줘."
```
또는:
```plain text
"오늘 찍은 사진 중 좋은 것 5개만 골라줘."
```
Raw Input에는 일반적으로 다음 정보가 함께 존재한다.
```plain text
interaction_id
message_id
user_id
timestamp
input_type
raw_content
```
---
# 6. Input Normalization
Raw Input을 System에서 처리하기 쉬운 형태로 정규화한다.
예:
```plain text
Raw:
"오늘 사진 중 좋은 거 5개 골라줘"

Normalized:

intent_candidate:
PHOTO_SELECTION

date_reference:
TODAY

quantity:
5

selection_criteria:
GOOD
```
정규화는 아직 최종 Intent를 확정하는 단계가 아니다.
그보다는 다음 단계의 이해를 위한 중간 Data를 만드는 과정이다.
---
# 7. Input Types
AI-PATTERN-001은 다음 Input을 지원할 수 있다.
| Input Type | Example |
| --- | --- |
| TEXT | "오늘 일기 만들어줘" |
| IMAGE | 여행 사진 업로드 |
| VIDEO | 여행 영상 업로드 |
| AUDIO | 음성 메모 |
| FILE | 여행 일정표 |
| UI_ACTION | 사진 선택 |
| LOCATION | 현재 위치 |
| SYSTEM_EVENT | 귀가 감지 |
MVP에서는 Text + Image + UI Action을 우선 지원할 수 있다.
---
# 8. Intent Data
Normalized Input을 바탕으로 Intent를 추출한다.
예:
```plain text
User:
"오늘 여행일기 만들어줘."

Intent:
CREATE_DAILY_DIARY
```
Intent는 다음 정보를 가질 수 있다.
```plain text
intent_name
confidence
goal
action
scope
```
---
# 9. Entity Data
Intent와 함께 Entity를 추출한다.
예:
```plain text
"오늘 샌디에이고 사진으로 일기 만들어줘."
```
Entities:
```plain text
date = TODAY
location = SAN_DIEGO
content = PHOTO
output = DIARY
```
Entity는 Context Retrieval의 중요한 기준이 된다.
---
# 10. Constraint Data
User가 명시한 조건도 별도의 Data로 관리한다.
예:
> "사진 5장만 사용해서 짧게 만들어줘."
Constraints:
```plain text
photo_limit = 5
length = SHORT
```
또는:
> "가족에게 보여줄 거니까 편하게 써줘."
Constraints:
```plain text
audience = FAMILY
tone = CASUAL
```
---
# 11. User Goal
Intent보다 상위 개념으로 User Goal을 관리한다.
예:
```plain text
Intent:
CREATE_DIARY

Goal:
Create a readable daily travel diary
based on today's travel experience.
```
Goal은 AI가 여러 Tool과 Data를 조합해야 할 때 특히 중요하다.
---
# 12. Context Requirement Detection
Intent가 확정되면 System은 어떤 Context가 필요한지 결정한다.
예:
```plain text
Intent:
CREATE_DAILY_DIARY
```
필요한 Context:
```plain text
Current Trip
Current Date
Schedule
Photos
Memories
```
필요하지 않은 Context:
```plain text
Old unrelated trips
Unrelated expenses
Unrelated conversations
```
즉:
```plain text
Intent
  ↓
Context Requirement
  ↓
Context Retrieval
```
---
# 13. Context Categories
Context는 다음과 같이 분류한다.
## 13.1 Session Context
현재 Interaction에 대한 정보.
```plain text
interaction_id
current_state
active_goal
pending_action
```
## 13.2 Conversation Context
대화의 연속성을 위한 정보.
```plain text
Recent Messages
Previous Answers
User Corrections
Pending Questions
```
## 13.3 User Context
사용자에 관한 장기적인 Context.
```plain text
Preferences
Language
Output Style
Permissions
```
## 13.4 Domain Context
현재 Task의 Domain 정보.
```plain text
Trip
Location
Schedule
Expense
Memory
```
## 13.5 Product Context
현재 Product의 상태.
```plain text
Current Screen
Selected Item
Current Trip
Draft Status
```
---
# 14. Context Source
Context는 하나의 Database에서만 가져오지 않는다.
가능한 Source:
```plain text
Conversation Store
User Profile Store
Trip Store
Memory Store
Photo Store
Schedule Store
Expense Store
Product State Store
Search Index
External API
```
따라서 Context Flow는 단일 Data Pipeline이 아니라 여러 Source를 조합하는 구조다.
---
# 15. Context Retrieval
Context Retrieval은 다음 순서로 수행할 수 있다.
```plain text
Context Requirement
      ↓
Source Identification
      ↓
Query Construction
      ↓
Data Retrieval
      ↓
Permission Check
      ↓
Freshness Check
      ↓
Context Filtering
```
---
# 16. Context Freshness
모든 Context가 동일한 Freshness를 가지는 것은 아니다.
예:
```plain text
User Preference
→ Long-lived

Trip Schedule
→ Medium-lived

Current Location
→ Short-lived

Weather
→ Very Short-lived
```
따라서 Context마다 Freshness Policy가 필요하다.
---
# 17. Freshness Example
User:
> "지금 여기 날씨 어때?"
System은 오래된 Weather Context를 사용하면 안 된다.
```plain text
Cached Weather
     ↓
Check Timestamp
     ↓
Too Old
     ↓
Refresh
```
반면 User의 Writing Preference는 매번 다시 조회할 필요가 없을 수 있다.
---
# 18. Context Relevance
Context는 Relevance 기준으로 평가한다.
예:
User:
> "오늘 사진으로 일기 만들어줘."
Potential Context:
```plain text
Today's Photos → HIGH
Today's Schedule → HIGH
Current Trip → HIGH
Yesterday Photos → MEDIUM
Last Year's Trip → LOW
Old Expenses → LOW
```
AI Context에는 HIGH를 우선 포함한다.
---
# 19. Context Priority
Context Priority는 다음과 같이 정의할 수 있다.
```plain text
P0 — Required
P1 — Highly Relevant
P2 — Useful
P3 — Optional
P4 — Irrelevant
```
예:
```plain text
Current Date
→ P0

Current Trip
→ P0

Today's Photos
→ P0

User Writing Style
→ P1

Previous Diary Style
→ P2

Old Trip
→ P4
```
---
# 20. Context Budget
AI Context에는 제한이 있다.
따라서 Context Budget을 관리해야 한다.
예:
```plain text
Context Budget
   ↓
Required Context
   ↓
High Priority Context
   ↓
Optional Context
```
Budget을 초과하면 P3/P4 Context부터 제거한다.
---
# 21. Context Compression
Context가 지나치게 많을 경우 압축한다.
예:
```plain text
100 Conversation Messages
```
를 그대로 전달하는 대신:
```plain text
Conversation Summary
+
Recent 5 Messages
+
Relevant Historical Messages
```
형태로 구성할 수 있다.
---
# 22. Context Window Strategy
권장 구조:
```plain text
System Rules
   ↓
Current Goal
   ↓
Required Context
   ↓
Relevant History
   ↓
Recent Conversation
   ↓
Tool Result
   ↓
User Input
```
중요도가 낮은 Data는 가능한 한 뒤로 밀거나 제거한다.
---
# 23. Context Assembly
여러 Source에서 가져온 Data를 하나의 Context Object로 구성한다.
예:
```plain text
ContextObject {

    user
    session
    conversation
    trip
    schedule
    photos
    memories
    expenses
    permissions

}
```
하지만 모든 필드를 항상 채우는 것은 아니다.
Task에 따라 필요한 필드만 활성화한다.
---
# 24. Context Object Example
예:
```plain text
{
  "session": {
    "interaction_id": "INT-123",
    "current_state": "CONTEXT_RESOLVING"
  },

  "goal": {
    "intent": "CREATE_DAILY_DIARY",
    "date": "2026-08-06"
  },

  "trip": {
    "trip_id": "TRIP-001",
    "destination": "San Diego"
  },

  "schedule": {
    "items": [...]
  },

  "photos": {
    "items": [...]
  }
}
```
이 Object는 AI가 현재 Task를 처리하는 데 필요한 Context의 논리적 단위가 된다.
---
# 25. Context Isolation
Context는 Task별로 격리해야 한다.
예:
```plain text
Trip A
Photos
```
와
```plain text
Trip B
Photos
```
가 동시에 존재한다면 Current Trip 기준으로 Filtering해야 한다.
특히 여행 App에서는:
```plain text
Current Trip
Previous Trip
Future Trip
```
이 동시에 존재할 수 있으므로 Trip Boundary가 중요하다.
---
# 26. Context Boundary
Context Boundary는 다음을 기준으로 설정한다.
```plain text
User
Session
Trip
Date
Memory
Permission
Task
```
예:
```plain text
User A
  └── Trip 1
      └── Day 3
          └── Photos
```
다른 User의 Photo가 Context에 포함되어서는 안 된다.
---
# 27. Permission-aware Context
Context Retrieval 단계에서 Permission을 확인한다.
예:
```plain text
Photo
  ↓
Permission Check
  ↓
Allowed?
  │
  ├── YES → Context
  └── NO → Exclude
```
AI가 Context를 받은 후 Permission을 판단하는 구조보다, Retrieval 단계에서 먼저 제거하는 것이 안전하다.
---
# 28. Sensitive Context
다음 Data는 필요 이상으로 AI Context에 포함하지 않는다.
```plain text
Personal Identifiers
Private Messages
Payment Details
Authentication Data
Unrelated Personal Information
```
필요한 경우에도 최소한의 정보만 제공한다.
예:
```plain text
Full Credit Card Number
→ 금지

Payment Category
→ 필요 시 허용
```
---
# 29. Context Filtering
Retrieval된 Data는 그대로 AI에 전달하지 않는다.
Pipeline:
```plain text
Retrieved Data
   ↓
Permission Filter
   ↓
Relevance Filter
   ↓
Freshness Filter
   ↓
Privacy Filter
   ↓
Deduplication
   ↓
Context Budget
   ↓
AI Context
```
---
# 30. Deduplication
동일한 Data가 여러 Source에서 조회될 수 있다.
예:
```plain text
Photo Store
Search Index
Memory Store
```
에서 같은 Photo가 발견될 수 있다.
따라서:
```plain text
photo_id
```
를 기준으로 중복 제거할 수 있다.
---
# 31. Context Conflict
서로 다른 Source가 다른 값을 반환할 수 있다.
예:
```plain text
Schedule Store:
14:00 Beach

Cached Memory:
15:00 Beach
```
이 경우 AI가 임의로 선택해서는 안 된다.
Source Priority를 정의해야 한다.
예:
```plain text
Authoritative Source
   >
Recent Verified Data
   >
Cached Data
   >
Generated Summary
```
---
# 32. Source Authority
Data Source에는 Authority Level을 둘 수 있다.
```plain text
A — Authoritative
B — Verified
C — Derived
D — Generated
```
예:
```plain text
Original Schedule
→ A

User-confirmed Change
→ A

AI Summary
→ C

AI Guess
→ D
```
중요한 사실을 판단할 때는 가능한 한 높은 Authority의 Data를 우선한다.
---
# 33. Context Update
Tool 실행 이후 Context가 변경될 수 있다.
예:
```plain text
Current Context
   ↓
Save Diary
   ↓
Tool Success
   ↓
Diary Created
   ↓
Context Update
```
이후 Context에는:
```plain text
diary_id
diary_status
created_at
```
등이 추가된다.
---
# 34. Context Mutation
Context는 두 종류로 나눌 수 있다.
## Read Context
AI가 참고만 하는 Data.
```plain text
Photos
Schedule
Memories
```
## Mutable Context
Action에 의해 변경되는 Data.
```plain text
Diary Draft
Share Status
Selected Photos
Expense Category
```
Mutable Context는 변경 전후를 추적할 수 있어야 한다.
---
# 35. Data Provenance
AI가 사용하는 Data는 가능하면 출처를 추적할 수 있어야 한다.
예:
```plain text
Statement:
"오늘 오후에는 라호야 코브에 갔다."
```
Source:
```plain text
Schedule Item #32
Photo Metadata #122
Location Data #87
```
이렇게 하면 AI Response의 Grounding을 확인할 수 있다.
---
# 36. Provenance Object
예:
```plain text
{
  "claim": "La Jolla Cove",
  "sources": [
    {
      "type": "schedule",
      "id": "SCH-032"
    },
    {
      "type": "photo",
      "id": "PHOTO-122"
    }
  ]
}
```
Provenance는 향후 다음 기능에도 활용할 수 있다.
```plain text
Explainability
Debugging
Fact Checking
User Correction
AI Hallucination Detection
```
---
# 37. Context Correction
User가 AI의 Context를 수정할 수 있어야 한다.
예:
AI:
> "오늘은 라호야 코브에 다녀오셨네요."
User:
> "아니야. 어제 갔어."
이 경우 단순히 Response만 수정하는 것이 아니라 Context를 업데이트해야 한다.
```plain text
User Correction
   ↓
Context Update
   ↓
State Update
   ↓
Recompute
   ↓
Response
```
---
# 38. User Correction Priority
User가 명시적으로 수정한 정보는 높은 Priority를 갖는다.
예:
```plain text
External Data:
Location = A

User:
"실제로는 B였어."
```
→ Current Interaction에서는 User Correction을 우선한다.
단, Persistent Data까지 자동으로 변경할지는 별도의 정책이 필요하다.
---
# 39. Context Lifecycle
Context의 Lifecycle은 다음과 같다.
```plain text
Discover
   ↓
Retrieve
   ↓
Validate
   ↓
Filter
   ↓
Assemble
   ↓
Consume
   ↓
Update
   ↓
Expire
```
Context는 영구적으로 유지되는 것이 아니라 목적과 수명에 따라 관리된다.
---
# 40. Context Expiration
Context는 시간이 지나면 더 이상 유효하지 않을 수 있다.
예:
```plain text
Current Location
Weather
Current Screen
Temporary Selection
```
이런 Data는 짧은 TTL을 가진다.
반면:
```plain text
User Preference
Trip History
Saved Memory
```
는 상대적으로 긴 Lifecycle을 가진다.
---

# 42. Part A Summary
Data Flow와 Context Flow의 핵심은 다음과 같다.
> **AI에게 데이터를 많이 주는 것이 좋은 것이 아니라, 현재 User Goal에 필요한 정확한 Context를 적시에 제공하는 것이 중요하다.**
