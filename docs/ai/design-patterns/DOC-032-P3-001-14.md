# DOC-032 — AI Design Pattern Catalog

## Part III — Interaction Patterns

# AI-PATTERN-001 — Chat Interaction Pattern

## 001-14 Cost, Latency & Resource Management

---

# 1. Purpose

본 문서는 AI-PATTERN-001 Chat Interaction의 응답 시간, Model 및 Tool 비용, Retrieval 부하, 동시성, 할당량을 사용자 가치와 안전성에 맞게 관리하는 기준을 정의한다.

비용 최적화는 가장 작은 Model을 선택하거나 호출 수를 줄이는 것만을 뜻하지 않는다. 필요한 확인, 검증, 권한 검사, 복구 기능을 유지하면서 User Goal을 적절한 품질과 예측 가능한 시간 안에 달성해야 한다.

# 2. Core Principle

> **필요한 품질과 안전성을 충족하는 가장 효율적인 경로를 선택하고, 제한이 생기면 사용자에게 실제 영향을 알린다.**

원칙:

1. **Budget per goal** — 비용과 지연을 개별 요청의 목적과 복잡도에 맞춘다.
2. **Bounded execution** — Context, Token, Tool Call, Retry, 시간에 제한을 둔다.
3. **Quality floor** — 비용 절감으로 필수 품질, 권한, Privacy, 결과 검증을 낮추지 않는다.
4. **Graceful degradation** — 예산이나 용량 초과 시 안전한 기능 축소 경로를 제공한다.
5. **Measure end-to-end** — Model 단가뿐 아니라 전체 사용자 대기 시간과 완료 성공을 평가한다.

# 3. Resource Model

요청별 자원 소비는 다음을 포함한다.

    input and output tokens
    retrieval queries and indexed data
    model calls and model tier
    tool calls and external API usage
    storage, cache, and telemetry
    queueing and concurrent execution time
    retry and recovery work

비용 원장이나 할당량을 관리할 때 가능한 범위에서 `interaction_id`, 기능 범주, Model / Tool Version과 연결한다. 사용자 대화 전문을 비용 레코드에 복사하지 않는다.

# 4. Latency Budget

각 사용자 Flow에 목적별 end-to-end latency budget을 둔다. Budget은 서비스 품질 목표와 사용자 영향에 근거하며, 구현 전부터 제품 운영에서 측정하고 조정한다.

```plain text
Request received
    ↓ authentication / policy
    ↓ context retrieval
    ↓ model generation
    ↓ tool execution (if needed)
    ↓ output validation / persistence
Response delivered
```

각 단계에 deadline과 timeout을 지정한다. 남은 전체 시간보다 긴 작업을 시작하지 않는다. Streaming을 사용할 때는 부분 출력과 완료 상태를 구분하며, 아직 검증되지 않은 텍스트를 완료된 결과로 표시하지 않는다.

# 5. Model Routing and Quality Tiers

Model Routing은 User Goal의 복잡도, Data 민감도, 요구되는 출력 형식, 기능 성능을 기준으로 한다.

```plain text
Classify task and risk
        ↓
Select eligible model tier
        ↓
Enforce context and output budget
        ↓
Run evaluation-backed generation
        ↓
Validate quality and policy
```

- 고위험 또는 민감 작업은 낮은 비용만을 이유로 약한 검증 경로에 배정하지 않는다.
- 작은 Model이 요구된 Schema, 언어, 근거 품질을 충족하지 못하면 승인된 상위 Tier 또는 안전한 실패를 선택한다.
- 자동 재라우팅은 User Data 처리 조건과 Vendor 정책이 모두 허용될 때만 수행한다.
- Routing Rule은 Version 관리하며, 사용자 그룹별 예상치 못한 품질 격차를 점검한다.

# 6. Context and Token Budget

Context Builder는 관련성과 권한을 먼저 적용한 뒤 token budget을 관리한다.

우선순위:

1. System Policy와 안전 제약
2. 현재 User Goal에 필수인 최근 Context
3. 검증된 Product Data와 출처
4. 요청과 직접 관련된 과거 Conversation 또는 Memory
5. 필요한 경우의 추가 설명 정보

예산을 초과하면 무작위 절단 대신 중요도와 최신성을 기준으로 요약하거나 범위를 좁힌다. 원본 기록과 요약을 구분하고, 요약으로 권한·출처·시간 정보를 잃지 않는다. 필수 Context가 예산 안에 들어오지 않으면 추가 질문, 단계적 처리, 기능 축소 중 안전한 경로를 선택한다.

# 7. Tool and Retrieval Efficiency

- Tool을 호출하기 전에 조회 또는 실행이 User Goal에 필요한지 확인한다.
- 단일 Batch 호출이 독립 요청의 다중 호출보다 안전하고 효율적인지 평가한다.
- Read와 Write Tool을 구분하고, 불필요한 Write를 제거한다.
- Retrieval은 목적, User scope, 최신성, 데이터 크기로 범위를 제한한다.
- 결과가 불완전하거나 오래된 Cache를 최신 상태처럼 제공하지 않는다.
- 반복되는 순수 Read 결과는 격리와 freshness 조건을 만족할 때만 Cache한다.
- 재시도 및 Tool Loop는 별도 budget을 가지며 무한 반복할 수 없다.

# 8. Caching Policy

Cache는 비용과 지연을 낮출 수 있지만 정보 노출과 오래된 결과 위험을 만든다.

Cache Key에는 결과 접근 권한에 영향을 주는 User / tenant / Resource 범위, 요청 목적과 중요한 설정 Version을 반영한다. Cache TTL과 무효화 조건을 데이터 갱신, 권한 회수, 삭제 요청에 맞춰 정의한다.

다음 결과는 기본적으로 공유 Cache에 저장하지 않는다.

- User-specific Memory 또는 Conversation
- 인증 토큰과 Secret
- 민감한 Photo / Location 분석 결과
- 동의 범위와 무관하게 외부에 노출될 수 있는 개인화 응답

# 9. Concurrency, Queueing and Fairness

- 사용자, tenant, 기능별 동시성 제한과 Queue 정책을 정의한다.
- 긴 작업과 짧은 상호작용이 서로를 무기한 지연시키지 않게 한다.
- Queue에 대기 중인 요청은 취소와 중복 제출을 지원한다.
- 장시간 실행 작업은 진행 상태, 취소 방법, 예상되는 다음 단계를 알린다.
- 공정성 정책은 유료/무료 구분이나 대기 순서를 제품 정책에 따라 투명하게 정의한다.
- 용량 회복 후 재개되는 대량 작업도 시스템에 급격한 부하를 주지 않도록 제한한다.

# 10. Degradation and Quotas

| Condition | Safe response |
| --- | --- |
| Model quota reached | 대기, 승인된 대체 Tier, 또는 재시도 시점을 안내 |
| Retrieval overload | 범위를 축소하고 누락된 범위를 명시 |
| Tool rate limit | 제한된 재시도 후 미완료 상태를 보존 |
| Cost budget exceeded | 비용이 낮은 승인 경로가 없으면 작업을 중단하거나 나눈다 |
| Overall deadline near | Side Effect를 새로 시작하지 않고 저장된 결과와 상태를 점검 |
| Dependency outage | 검증 가능한 Read-only 결과나 Draft 보존을 제공 |

예산 초과가 권한 실패나 품질 실패처럼 보이지 않도록 오류 분류를 유지한다. 자동 downgrade는 품질, Data 처리, 사용자 정책을 통과한 경로만 사용한다.

# 11. Cost Attribution and Budgets

Cost Attribution은 요청 단위 비용을 기능 및 결과와 연결한다.

권장 Budget Category:

- User interaction budget
- Goal / workflow budget
- Tool and Retrieval budget
- Tenant or environment budget
- Evaluation / development budget

예산은 과금 한도와 Model 비용만이 아니라 재시도, 실패, 검증, 운영 비용을 포함해 설정한다. 특정 사용자의 작은 표본에서 발생한 비용으로 개인 특성을 추론하거나 부당하게 기능을 제한하지 않는다.

# 12. Performance and Cost Evaluation

최적화 후보는 다음 관점에서 전후 비교한다.

| Dimension | Example measure |
| --- | --- |
| User latency | End-to-end percentile, first useful response time |
| Goal quality | Task completion, correction, abandonment, grounding |
| Reliability | timeout, retry, partial result, save verification |
| Safety | permission block, leakage, confirmation integrity |
| Unit economics | cost per successfully completed goal |
| Resource stability | queue depth, concurrency saturation, cache efficiency |

비용/응답속도 개선을 주장할 때 평가 Set, Cohort, 기간, 변경 사항과 품질 차이를 기록한다. 평균 비용 절감이 특정 Flow의 큰 품질 저하를 가릴 수 있으므로 기능별·위험별 분석을 제공한다.

# 13. RoRo Workload Classes

RoRo의 작업을 대략 다음과 같이 구분하고 실제 측정값으로 조정한다.

### Lightweight Read

단순 Trip 상태나 일정 조회. 범위가 제한된 Read Tool과 짧은 Context를 사용하고 데이터 시점과 timezone을 보존한다.

### Synthesis

여러 Moment와 Photo를 이용한 Diary 초안 생성. User가 선택한 Data를 우선하고, 단계적 요약과 Source Tracking으로 Context 크기를 관리한다. Draft 생성 비용과 저장 완료를 구분한다.

### Multi-step Action

일정 수정, 공유, 여러 Tool에 걸친 작업. 계획 단계에서 필요한 호출과 Side Effect를 제한하고, 중요 단계 전에 적절한 확인을 거친다. 전체 시간이나 예산이 부족해지면 안전한 중간 상태를 보존한다.

### Background Work

긴 작업은 동기 응답을 무한히 유지하지 않고 Background Job으로 처리할 수 있다. Job의 소유자, 취소, 재시도, 결과 만료 및 재개 동작을 정의한다.

# 14. Anti-patterns

1. **Cheapest-model routing** — 품질·위험 요구를 확인하지 않고 최저 단가 Model만 사용한다.
2. **Unbounded context** — 대화와 검색 Data를 목적 구분 없이 모두 첨부한다.
3. **Silent truncation** — 필수 Context를 잘라낸 후 완전한 결과처럼 제시한다.
4. **Retry cost spiral** — 제한 없는 Retry와 Model fallback이 비용을 증폭한다.
5. **Unsafe cache sharing** — User 간 Cache를 재사용하거나 권한 변경 후에도 무효화하지 않는다.
6. **Latency by skipping validation** — 빠르게 응답하기 위해 권한, 사실, 저장 상태를 확인하지 않는다.
7. **Average hides tail** — 평균 latency만 보고 긴 지연과 사용자 포기를 숨긴다.
8. **Cost per message** — 사용자 목표 난이도가 다른 메시지를 같은 비용 기준으로만 평가한다.
9. **Opaque quota** — 요청이 제한된 이유와 가능한 다음 단계를 사용자에게 숨긴다.
10. **Background work without ownership** — 소유자, 취소, 만료, 재시도 조건 없는 Job을 계속 실행한다.

# 15. Review Checklist

- [ ] User Goal과 위험도에 맞춘 latency 및 cost budget이 있는가?
- [ ] Context, output, Tool Call, retry, concurrency에 상한이 있는가?
- [ ] Model routing 변경이 품질, Safety, Privacy를 통과하는가?
- [ ] Token 축소 후에도 provenance와 필수 지침을 보존하는가?
- [ ] Cache가 User scope, freshness, 권한 회수와 삭제를 반영하는가?
- [ ] 용량 제한 시 사용자에게 상태와 가능한 다음 행동을 설명하는가?
- [ ] 비용을 성공한 Goal과 실패 및 복구 비용까지 포함해 분석하는가?
- [ ] 평균뿐 아니라 tail latency와 사용자 포기를 측정하는가?
- [ ] RoRo의 Diary, Read, Multi-step, Background Flow별 정책이 있는가?
- [ ] 최적화가 검증과 권한 경계를 제거하지 않는가?
