# DOC-032 — AI Design Pattern Catalog
## Part III — Interaction Patterns
# AI-PATTERN-001 — Chat Interaction Pattern
## 001-09-B Data Flow & Context Flow
### Part B — Conversation, Retrieval, Tool Flow, RoRo Application & Architecture
---
# 43. Conversation Context Flow
Conversation Context는 현재 User와 AI가 진행하고 있는 대화의 연속성을 유지하기 위한 Data다.
예:
```plain text
User:
"오늘 여행일기 만들어줘."

AI:
"어떤 스타일로 작성할까요?"

User:
"사진 중심으로."
```
두 번째 User Message만 독립적으로 보면:
```plain text
"사진 중심으로."
```
는 완전한 Request가 아니다.
Conversation Context가 결합되면:
```plain text
Previous Goal:
CREATE_DAILY_DIARY

User Preference:
PHOTO_FOCUSED
```
로 해석할 수 있다.
따라서 Conversation Context는 단순한 Chat History가 아니라 현재 Interaction의 의미를 보완하는 Context다.
---
# 44. Short-term Context
Short-term Context는 현재 대화에서 가까운 시점에 생성된 Context다.
예:
```plain text
Last 5 Messages
Current Question
Current Tool Result
Current Selection
Pending Confirmation
```
Short-term Context는 일반적으로 높은 Relevance를 갖는다.
특히 User가:
```plain text
"그거"
"이것"
"아까 말한 것"
"그 사진"
```
등의 표현을 사용할 때 중요하다.
---
# 45. Long-term Context
Long-term Context는 여러 Session에 걸쳐 유지될 수 있는 User 또는 Product Context다.
예:
```plain text
User Writing Preference
Preferred Language
Trip History
Saved Memories
Favorite Content Style
```
그러나 Long-term Context는 무조건 현재 Prompt에 포함하면 안 된다.
다음 기준을 사용한다.
```plain text
Current Goal Relevance
User Permission
Freshness
Privacy
Context Budget
```
---
# 46. Memory Retrieval
AI가 과거 Memory를 필요로 하는 경우 Memory Retrieval을 수행한다.
예:
> "작년에 가족들과 갔던 런던 여행 스타일로 이번 여행기도 써줘."
필요한 Context:
```plain text
Current Trip
Previous London Trip
Previous Diary
User's Preferred Style
```
Retrieval Flow:
```plain text
User Request
   ↓
Intent
   ↓
Memory Requirement
   ↓
Memory Search
   ↓
Ranking
   ↓
Relevant Memories
   ↓
Context Assembly
```
---
# 47. Semantic Retrieval
Memory는 정확한 Keyword가 없어도 검색할 수 있어야 한다.
User:
> "작년에 가족끼리 유럽에서 갔던 여행."
Database에 저장된 표현:
```plain text
London
Paris
Family Trip
2025
```
Semantic Retrieval을 사용하면 서로 다른 표현이라도 관련 Memory를 찾을 수 있다.
핵심은:
```plain text
User Language
   ≠
Stored Metadata
```
일 수 있다는 점이다.
---
# 48. Structured Retrieval
Semantic Retrieval만으로 충분하지 않은 경우 Structured Query를 사용한다.
예:
```plain text
trip.destination = "London"
trip.year = 2025
trip.type = "family"
```
Structured Retrieval은 다음 Data에 적합하다.
```plain text
Date
Location
Category
ID
Status
User
Permission
```
---
# 49. Hybrid Retrieval
가장 강력한 방식은 Semantic + Structured Retrieval을 결합하는 것이다.
예:
```plain text
User:
"작년에 가족끼리 갔던 유럽여행 사진 찾아줘."
```
Structured:
```plain text
year = 2025
trip_type = FAMILY
region = EUROPE
```
Semantic:
```plain text
"family Europe trip"
```
결과:
```plain text
Structured Filter
    +
Semantic Ranking
    ↓
Relevant Photos
```
---
# 50. Retrieval Ranking
검색 결과가 여러 개라면 Ranking이 필요하다.
Ranking 기준 예:
```plain text
Relevance
Recency
Source Authority
User Preference
Context Match
Quality
```
예:
```plain text
Candidate A
Relevance = High
Recency = Medium

Candidate B
Relevance = Medium
Recency = High
```
현재 Task가 "과거 여행의 대표 사진"이라면 Relevance가 더 높은 A가 선택될 수 있다.
---
# 51. Context Assembly Strategy
Retrieval 결과를 모두 AI에게 전달하지 않는다.
다음 순서로 조합한다.
```plain text
Required Context
     ↓
High Relevance
     ↓
User Preference
     ↓
Recent Conversation
     ↓
Supporting Context
     ↓
Optional Context
```
예:
```plain text
Goal
Current Trip
Current Date
Selected Photos
Today's Schedule
Writing Style
Recent Conversation
```
순으로 구성할 수 있다.
---
# 52. Tool Input Flow
AI가 Tool을 호출할 때도 별도의 Data Flow가 존재한다.
예:
```plain text
User Request
    ↓
Intent
    ↓
Context
    ↓
Tool Selection
    ↓
Tool Parameter Construction
    ↓
Parameter Validation
    ↓
Permission Check
    ↓
Tool Execution
```
Tool Input에는 필요한 Data만 전달한다.
---
# 53. Tool Input Example
예:
```plain text
Tool:
photo_search
```
Input:
```plain text
{
  "trip_id": "TRIP-001",
  "date": "2026-08-06",
  "limit": 5,
  "sort": "quality"
}
```
불필요한 User Data:
```plain text
email
phone
unrelated_trip
unrelated_expense
```
등은 Tool에 전달하지 않는다.
---
# 54. Tool Output Flow
Tool 결과는 그대로 LLM에 전달하지 않는다.
```plain text
Tool
  ↓
Raw Result
  ↓
Schema Validation
  ↓
Normalize
  ↓
Filter
  ↓
Context Update
  ↓
AI
```
예:
```plain text
Raw Tool Result

{
  "photos": [...],
  "debug": {...},
  "internal_metadata": {...}
}
```
AI Context에는 필요한 정보만 포함한다.
---
# 55. Tool Result Normalization
Tool마다 Response Format이 다를 수 있다.
예:
```plain text
Photo API:
photos[]

Schedule API:
events[]

Memory API:
memories[]
```
AI Layer에서는 공통 구조로 변환할 수 있다.
```plain text
Result {
    type
    id
    timestamp
    relevance
    source
    data
}
```
이렇게 하면 AI Orchestrator가 Tool별 API 구조에 지나치게 종속되지 않는다.
---
# 56. Context Update After Tool Execution
Tool이 성공하면 Context를 업데이트한다.
예:
```plain text
EXECUTING
   ↓
photo_search
   ↓
SUCCESS
   ↓
Context Update
```
Context:
```plain text
selected_photos = [
    PHOTO-01,
    PHOTO-02,
    PHOTO-03
]
```
다음 AI Step에서는 이 Data를 활용할 수 있다.
---
# 57. Multi-tool Data Flow
하나의 User Request가 여러 Tool을 필요로 할 수 있다.
예:
> "오늘 사진으로 여행일기 만들어줘."
필요한 Tool:
```plain text
get_trip
get_schedule
search_photos
generate_diary
```
Flow:
```plain text
User
  ↓
Intent
  ↓
get_trip
  ↓
get_schedule
  ↓
search_photos
  ↓
generate_diary
  ↓
Validate
  ↓
Response
```
---
# 58. Parallel Data Flow
독립적인 Tool은 병렬 실행할 수 있다.
예:
```plain text
Current Trip
     │
     ├── get_schedule
     │
     └── search_photos
```
두 Tool이 서로 Dependency가 없다면 동시에 실행할 수 있다.
```plain text
┌── get_schedule ──┐
│                  │
├── search_photos ─┤
│                  │
└──────────────────┘
         ↓
    Aggregation
         ↓
  generate_diary
```
이를 통해 전체 Latency를 줄일 수 있다.
---
# 59. Sequential Data Flow
반대로 이전 Tool의 결과가 다음 Tool의 Input이 되는 경우 순차 실행이 필요하다.
예:
```plain text
Search Trip
   ↓
trip_id
   ↓
Search Photos
   ↓
photo_ids
   ↓
Generate Diary
```
이 경우 병렬화하면 안 된다.
Data Dependency가 존재하기 때문이다.
---
# 60. Data Dependency
Data Dependency를 명시적으로 관리한다.
예:
```plain text
generate_diary
    requires:
    trip_id
    schedule
    photos
```
그러면:
```plain text
get_trip
    → trip_id

get_schedule
    → schedule

search_photos
    → photos
```
가 먼저 완료되어야 한다.
이를 Graph로 표현할 수 있다.
```plain text
Trip
  │
  ├── Schedule
  │
  └── Photos
         │
         ▼
    Diary Generation
```
---
# 61. Context Dependency
Data Dependency와 Context Dependency는 구분해야 한다.
Data Dependency:
```plain text
Tool A의 결과가 Tool B의 Input
```
Context Dependency:
```plain text
AI가 현재 상황을 이해하기 위해 필요한 정보
```
예:
```plain text
Photo Search
→ Schedule이 직접 필요하지 않을 수 있음
```
하지만 Diary Generation에는:
```plain text
Schedule + Photos
```
가 모두 필요하다.
---
# 62. Error Data Flow
Tool이 실패하면 Error도 Data Flow의 일부로 처리한다.
```plain text
Tool
  ↓
Error
  ↓
Error Normalization
  ↓
Error Classification
  ↓
Recovery Decision
```
Error Type:
```plain text
RETRYABLE
NON_RETRYABLE
AUTH
PERMISSION
TIMEOUT
VALIDATION
NOT_FOUND
RATE_LIMIT
```
---
# 63. Recovery Data Flow
Recovery도 별도의 Flow를 가진다.
```plain text
ERROR
  ↓
CLASSIFY
  ↓
RECOVERY STRATEGY
  │
  ├── RETRY
  ├── FALLBACK
  ├── REPLAN
  ├── CLARIFY
  └── FAIL
```
예:
```plain text
Photo API Timeout

↓

Retry

↓

Success
```
또는:
```plain text
Retry
  ↓
Failure
  ↓
Fallback Search
```
---

사진 추천은 다음과 같다.

```plain text
    ↓

    ↓
Photo Storage
    ↓

    ↓
Quality / Relevance Score
    ↓
Photo Ranking
```

Photo Analysis에서 사용할 수 있는 정보:


# 66. RoRo Expense Data Flow
여행 지출 데이터는 다음 Flow를 가질 수 있다.
```plain text
Receipt / Card History
      ↓
Raw Expense
      ↓
OCR / Parsing
      ↓
Merchant
      ↓
Category
      ↓
Currency
      ↓
Amount
      ↓
Validation
      ↓
Expense DB
      ↓
Daily / Trip Summary
```
AI가 이를 활용할 경우:
```plain text
Expense DB
    ↓
Context Retrieval
    ↓
Daily Expense Context
    ↓
Diary / Summary
```
단, 비용 Data는 여행일기 생성에 항상 필요한 것은 아니다.
User가:
> "오늘 지출까지 포함해서 여행일기 만들어줘."
라고 요청했을 때만 높은 Priority로 포함할 수 있다.

# 68. AI Generated Data Flow
AI가 생성한 Data도 일반 Data와 동일하게 관리해야 한다.
예:
```plain text
AI Draft
  ↓
Generated Content
  ↓
Validation
  ↓
User Review
  ↓
User Edit
  ↓
Final Content
  ↓
Persist
```
AI가 생성했다는 이유만으로 즉시 Permanent Data로 저장해서는 안 된다.
특히 여행일기의 경우:
```plain text
AI Draft
≠
Final Diary
```
로 구분한다.

# 69. User Feedback Data Flow
User Feedback은 다음 AI 처리에 활용할 수 있다.
예:
AI:
> "오늘은 여유롭게 바닷가를 즐겼습니다."
User:
> "너무 감성적이야. 좀 더 담백하게 써줘."
Flow:
```plain text
AI Draft
   ↓
User Feedback
   ↓
Preference Signal
   ↓
Regeneration
   ↓
New Draft
```
Feedback은 현재 Interaction에만 적용할 수도 있고, 사용자가 명시적으로 선호를 저장하는 경우 Long-term Preference로 승격할 수 있다.
---
# 70. Context Feedback Loop
AI Interaction은 단방향 Flow가 아니다.
```plain text
Context
   ↓
AI
   ↓
Result
   ↓
User Feedback
   ↓
Context Update
   ↓
AI
```
이 Loop가 반복될 수 있다.
예:
```plain text
Draft 1
   ↓
User Correction
   ↓
Draft 2
   ↓
User Correction
   ↓
Final Draft
```
이 구조는 AI Product의 핵심 Interaction Loop가 될 수 있다.

```plain text

Memory Boundary

```

```plain text
   ↓
```

# 75. Data Minimization
AI에게 전달되는 Data는 최소화한다.
Bad:
```plain text
Entire User Profile
Entire Trip History
All Photos
All Expenses
All Conversations
```
Good:
```plain text
Current Trip
Current Day
Relevant Photos
Relevant Schedule
Current User Preference
```
이 원칙은 다음 효과를 가진다.
```plain text
Privacy ↑
Cost ↓
Latency ↓
Relevance ↑
Reasoning Quality ↑
```

# 76. Data Retention
모든 AI Interaction Data를 영구 보존할 필요는 없다.
Data를 다음과 같이 분류할 수 있다.
```plain text
Temporary
Session
Persistent
User-owned
Analytics-only
```
예:
```plain text
Temporary Tool Result
→ Short Retention

Final Diary
→ Persistent

Debug Trace
→ Policy-defined Retention
```
Retention은 Privacy와 Storage Cost를 함께 고려한다.

# 78. Design Principles
AI-PATTERN-001 Data Flow는 다음 원칙을 따른다.
## Principle 1 — Context is Selective
모든 Data를 Context에 포함하지 않는다.
## Principle 2 — Context is Goal-driven
현재 User Goal을 기준으로 필요한 Context를 결정한다.
## Principle 3 — Permission Before Exposure
AI Context에 들어오기 전에 Permission을 검증한다.
## Principle 4 — Freshness Matters
시간에 민감한 Data는 최신성을 확인한다.
## Principle 5 — Source Authority Matters
원본 또는 검증된 Source를 우선한다.
## Principle 6 — Data Must Be Traceable
가능하면 Data Provenance와 Lineage를 추적한다.
## Principle 7 — Tool Result Must Be Normalized
Tool별 Response를 공통 구조로 정규화한다.
## Principle 8 — AI Output is Not Automatically Final
AI Generated Data와 Final User Data를 구분한다.
## Principle 9 — User Correction is Valuable Context
User가 수정한 정보는 현재 Interaction의 중요한 Context다.
## Principle 10 — Privacy is a Data Flow Constraint
Privacy는 마지막 단계의 Filter가 아니라 Data Flow 전체에 적용되는 원칙이다.

# 79. Document Summary
AI-PATTERN-001의 Data Flow & Context Flow는 다음 구조로 요약된다.
```plain text
USER INPUT
     ↓
INTERPRETATION
     ↓
CONTEXT REQUIREMENT
     ↓
RETRIEVAL
     ↓
FILTERING
     ↓
CONTEXT ASSEMBLY
     ↓
AI PROCESSING
     ↓
TOOL EXECUTION
     ↓
RESULT NORMALIZATION
     ↓
VALIDATION
     ↓
CONTEXT UPDATE
     ↓
RESPONSE
     ↓
USER FEEDBACK
     ↓
CONTEXT FEEDBACK LOOP
```
핵심은 Data의 양이 아니라 Data의 적합성이다.
AI가 좋은 결과를 만들기 위해서는:
```plain text
Right Data
+
Right Context
+
Right Time
+
Right Permission
+
Right Source
```
가 필요하다.

# 80. Final Principle
AI Interaction의 품질은 Model 자체만으로 결정되지 않는다.
다음의 결합으로 결정된다.
```plain text
Model Quality
   +
Context Quality
   +
Data Quality
   +
Retrieval Quality
   +
Tool Quality
   +
State Control
   +
Validation
```
따라서 AI-PATTERN-001에서는 Data Flow를 단순한 Backend Pipeline으로 취급하지 않는다.
> **Context Flow는 AI가 User의 의도를 정확히 이해하고 실제 Product State와 연결하기 위한 핵심 Interaction Infrastructure다.**
특히 RoRo에서는:
```plain text
User
  ↓
Trip
  ↓
Day
  ↓
Moment
  ↓
Photo
  ↓
Schedule
  ↓
Expense
  ↓
Memory
  ↓
AI
```
의 관계를 명확히 유지해야 한다.
이 구조가 유지되어야 AI가 단순히 "그럴듯한 여행기"를 생성하는 것이 아니라, 실제 User의 여행 경험에 기반한 결과를 생성할 수 있다.
