# 010 Product Design Framework
# Part I - Product Design Philosophy
Version 1.0.0
Status: Draft
---
# 1. Purpose
본 문서는 Product Design의 철학과 운영 원칙을 정의한다.
RoRo에서 Design은 화면(UI)을 만드는 활동이 아니다.
Design는 사용자의 행동을 이해하고, 목표 달성을 더 쉽고 즐겁게 만들기 위해 제품 경험을 설계하는 과정이다.
좋은 Design은 아름다운 화면보다 올바른 행동을 자연스럽게 유도한다.
---
# 2. Product Design Philosophy
Product Design은 다음 원칙을 따른다.
```plain text
Understand

↓

Behavior

↓

Interaction

↓

Experience

↓

Outcome

↓

Learning
```
Design의 목적은 인터페이스가 아니라 사용자 경험의 변화이다.
---
# 3. Design Objectives
Product Design은 다음 목표를 가진다.
- User Goal 달성 지원
- Cognitive Load 감소
- User Confidence 향상
- Behavior Change 유도
- Delightful Experience 제공
- Accessibility 확보
- 지속적인 Product Learning 지원
---
# 4. Design Principles
## Principle 1
User Goals Before Features
---
## Principle 2
Behavior Before Interface
---
## Principle 3
Clarity Before Complexity
---
## Principle 4
Consistency Before Creativity
---
## Principle 5
Accessibility By Default
---
## Principle 6
Evidence-Based Design
---
## Principle 7
Design Never Stops
제품 출시 이후에도 Design은 사용자 행동을 학습하며 지속적으로 개선된다.
---
# 5. Design Operating Model
```plain text
User Research

↓

Behavior Analysis

↓

Experience Mapping

↓

Interaction Design

↓

Prototype

↓

Validation

↓

Iteration

↓

Release
```
Design은 Discovery와 Development를 연결하는 핵심 단계이다.
---
# 6. Design Inputs
Design는 다음 정보를 입력으로 활용한다.
- User Research
- Problem Statement
- Opportunity Assessment
- Product Strategy
- Product Metrics
- Accessibility Guidelines
- Technical Constraints
- Brand Principles
---
# 7. Design Outputs
Design 결과물은 다음을 포함한다.
- Experience Principles
- User Flow
- Information Architecture
- Wireframes
- High-fidelity Mockups
- Interactive Prototype
- Design Specifications
- Design Decision Log
---
# 8. Success Metrics
| KPI | Description |
| --- | --- |
| Task Success Rate | 목표 수행 성공률 |
| Time on Task | 과업 완료 시간 |
| Error Rate | 사용자 오류율 |
| User Satisfaction | 만족도 |
| Accessibility Score | 접근성 수준 |
| Design Consistency | 일관성 지수 |
| Adoption Rate | 기능 채택률 |
---
# 9. AI-assisted Product Design
AI는 다음 활동을 지원한다.
- User Flow Suggestion
- Wireframe Generation
- Copy Drafting
- Accessibility Review
- Design Consistency Check
- UX Pattern Recommendation
- Design Documentation
AI는 Design을 지원하지만 사용자 경험에 대한 최종 판단은 Product Team과 Design Team이 수행한다.
---
# 10. Design Anti Pattern
## Anti Pattern 1
예쁜 화면을 좋은 UX라고 착각한다.
---
## Anti Pattern 2
사용자 행동을 검증하지 않는다.
---
## Anti Pattern 3
기술 제약만 고려한다.
---
## Anti Pattern 4
일관성보다 독창성을 우선한다.
---
## Anti Pattern 5
접근성을 나중에 고려한다.
---
## Anti Pattern 6
사용자 피드백 없이 디자인을 확정한다.
---
## Anti Pattern 7
출시 이후 디자인 개선을 멈춘다.
---
# 11. Design Rules
## Rule DE-01
모든 Design은 사용자 목표와 연결되어야 한다.
---
## Rule DE-02
Behavior를 이해하기 전에는 Interface를 설계하지 않는다.
---
## Rule DE-03
Prototype은 Validation을 위한 도구이다.
---
## Rule DE-04
Design Decision은 문서화한다.
---
## Rule DE-05
Accessibility는 필수 요구사항이다.
---
## Rule DE-06
AI는 Design을 지원하지만 Experience는 사람이 설계한다.
---
## Rule DE-07
Design의 성공은 화면이 아니라 사용자 행동 변화로 측정한다.
---

# 010 Product Design Framework
# Part II - Experience Design Framework
Version 1.0.0
Status: Draft
---
# 1. Purpose
본 문서는 Product Experience를 설계하고 운영하기 위한 표준 체계를 정의한다.
RoRo에서 Experience는 하나의 화면이나 기능이 아니다.
Experience는 사용자가 제품을 처음 인지하는 순간부터 목표를 달성하고 지속적으로 사용하는 전 과정에서 형성되는 인식, 감정, 행동의 총합이다.
---
# 2. Experience Philosophy
좋은 Experience는 사용자가 인터페이스를 의식하지 않고 자신의 목표에 집중할 수 있도록 만든다.
Experience Design의 목적은 사용자를 통제하는 것이 아니라, 올바른 행동을 가장 적은 노력으로 수행할 수 있도록 지원하는 것이다.
---
# 3. Experience Principles
모든 Experience는 다음 원칙을 따른다.
- Goal-Oriented
- Context-Aware
- Simple by Default
- Consistent Across Touchpoints
- Inclusive by Design
- Evidence-Based
- Continuously Improved
---
# 4. Experience Operating Model
```plain text
User Goal

↓

Journey Mapping

↓

Touchpoint Analysis

↓

Pain Point Identification

↓

Experience Design

↓

Prototype

↓

Validation

↓

Measurement

↓

Continuous Improvement
```
Experience는 출시 후에도 지속적으로 개선된다.
---
# 5. Experience Layers
| Layer | Description |
| --- | --- |
| Functional | 사용자가 목표를 달성할 수 있는가 |
| Usability | 쉽게 사용할 수 있는가 |
| Emotional | 긍정적인 감정을 제공하는가 |
| Trust | 신뢰를 형성하는가 |
| Delight | 기대 이상의 가치를 제공하는가 |
모든 핵심 기능은 다섯 개 계층을 고려하여 설계한다.
---
# 6. Journey Mapping
Experience는 사용자 여정 단위로 설계한다.
표준 Journey 구성 요소
- Trigger
- Goal
- Actions
- Touchpoints
- Pain Points
- Opportunities
- Success Criteria
Journey는 기능 중심이 아니라 사용자 목표 중심으로 작성한다.
---
# 7. Experience Metrics
| KPI | Description |
| --- | --- |
| Task Success Rate | 과업 성공률 |
| Time to Value | 가치 도달 시간 |
| User Satisfaction (CSAT) | 사용자 만족도 |
| Net Promoter Score (NPS) | 추천 의향 |
| Retention Rate | 재사용률 |
| Drop-off Rate | 이탈률 |
| Customer Effort Score (CES) | 사용자 노력 수준 |
정량 지표와 정성 피드백을 함께 활용한다.
---
# 8. AI-assisted Experience Design
AI는 다음 활동을 지원할 수 있다.
- Journey Analysis
- UX Pattern Recommendation
- User Feedback Clustering
- Copywriting Support
- Accessibility Review
- Experience Gap Detection
- Personalization Suggestions
AI는 경험 설계를 지원하지만 최종 경험 품질은 Product Team과 Design Team이 책임진다.
---
# 9. Required Artifacts
모든 Experience Design은 다음 산출물을 생성한다.
- Journey Map
- Experience Principles
- Touchpoint Inventory
- Experience Flow
- UX Success Metrics
- Validation Report
- Improvement Backlog
---
# 10. Operational Checklist
□ 사용자 목표가 명확한가
□ Journey가 정의되었는가
□ 주요 Pain Point를 식별했는가
□ Experience Success Metric이 정의되었는가
□ Prototype 검증을 수행했는가
□ 개선 Backlog를 생성했는가
□ Experience Decision을 문서화했는가
---
# 11. Experience Anti Pattern
## Anti Pattern 1
화면 중심으로 경험을 설계한다.
---
## Anti Pattern 2
Journey 없이 기능만 설계한다.
---
## Anti Pattern 3
정량 데이터만 보고 경험을 평가한다.
---
## Anti Pattern 4
감정적 경험을 고려하지 않는다.
---
## Anti Pattern 5
출시 이후 개선을 중단한다.
---
## Anti Pattern 6
접점 간 일관성을 유지하지 않는다.
---
## Anti Pattern 7
사용자의 목표보다 내부 프로세스를 우선한다.
---
# 12. Experience Rules
## Rule XD-01
모든 Experience는 사용자 목표에서 시작한다.
---
## Rule XD-02
Journey 없이 Experience를 설계하지 않는다.
---
## Rule XD-03
Experience는 기능이 아니라 행동과 감정까지 포함한다.
---
## Rule XD-04
모든 Experience는 측정 가능해야 한다.
---
## Rule XD-05
Experience Decision은 문서화한다.
---
## Rule XD-06
Experience는 지속적으로 개선한다.
---
## Rule XD-07
Experience의 성공은 사용자의 목표 달성으로 평가한다.
---

# 010 Product Design Framework
# Part III - Information Architecture Framework
Version 1.0.0
Status: Draft
---
# 1. Purpose
본 문서는 Product Information Architecture(IA)의 설계 원칙과 운영 체계를 정의한다.
RoRo에서 IA는 메뉴 구조를 설계하는 작업이 아니다.
IA는 사용자가 정보를 이해하고 탐색하는 방식과 시스템이 데이터를 구성하는 방식을 일관성 있게 연결하는 구조적 설계 활동이다.
---
# 2. Information Architecture Philosophy
좋은 IA는 사용자가 "어디를 가야 할지" 고민하지 않도록 만든다.
정보는 시스템의 편의가 아니라 사용자의 사고 흐름에 맞추어 구성되어야 한다.
IA는 화면보다 먼저 설계되며, 화면은 IA를 표현하는 수단이다.
---
# 3. IA Objectives
Information Architecture는 다음 목표를 가진다.
- 정보 탐색 비용 최소화
- 사용자의 Mental Model과 시스템 Domain Model 정렬
- 일관된 Navigation 제공
- 확장 가능한 구조 확보
- 검색성과 발견 가능성 향상
- 콘텐츠 재사용성 확보
---
# 4. IA Principles
## Principle 1
User Mental Model First
---
## Principle 2
Consistency Across Navigation
---
## Principle 3
Progressive Disclosure
필요한 정보만 적절한 시점에 노출한다.
---
## Principle 4
Scalable Structure
새로운 기능이 추가되어도 기존 구조를 크게 변경하지 않는다.
---
## Principle 5
Single Source of Truth
동일한 정보는 하나의 기준 구조를 가진다.
---
## Principle 6
Findability Before Density
정보를 많이 보여주는 것보다 쉽게 찾을 수 있는 것이 중요하다.
---
## Principle 7
Domain-Driven Organization
정보 구조는 제품의 핵심 도메인 모델과 일치해야 한다.
---
# 5. IA Operating Model
```plain text
Domain Model

↓

Content Inventory

↓

Taxonomy Design

↓

Navigation Design

↓

Information Hierarchy

↓

Validation

↓

Iteration
```
---
# 6. Core Components
모든 IA는 다음 요소를 정의한다.
| Component | Description |
| --- | --- |
| Domain Model | 핵심 엔티티와 관계 |
| Taxonomy | 분류 체계 |
| Navigation | 이동 구조 |
| Hierarchy | 정보 계층 |
| Labeling | 명칭 규칙 |
| Search Strategy | 검색 전략 |
| Metadata | 정보 속성 |
---
# 7. Navigation Standards
Navigation은 다음 기준을 따른다.
- 예측 가능해야 한다.
- 깊이보다 명확성을 우선한다.
- 현재 위치를 항상 알 수 있어야 한다.
- 사용자의 주요 작업(Task)을 중심으로 구성한다.
- 동일한 패턴을 반복 사용한다.
---
# 8. Validation Methods
IA는 다음 방법으로 검증한다.
- Card Sorting
- Tree Testing
- Navigation Usability Test
- Search Analysis
- First Click Test
- Task Completion Analysis
정량 데이터와 정성 피드백을 함께 활용한다.
---
# 9. AI-assisted Information Architecture
AI는 다음 활동을 지원할 수 있다.
- Taxonomy Recommendation
- Duplicate Structure Detection
- Label Suggestion
- Search Query Analysis
- Navigation Optimization
- Metadata Generation
- IA Consistency Review
AI는 구조를 제안하지만 최종 정보 구조는 Product Team과 Design Team이 결정한다.
---
# 10. Required Artifacts
모든 IA는 다음 산출물을 생성한다.
- Domain Model
- Sitemap
- Navigation Map
- Taxonomy Definition
- Label Dictionary
- Metadata Specification
- IA Validation Report
---
# 11. Success Metrics
| KPI | Description |
| --- | --- |
| Navigation Success Rate | 탐색 성공률 |
| Time to Find Information | 정보 탐색 시간 |
| Search Success Rate | 검색 성공률 |
| First Click Accuracy | 첫 클릭 정확도 |
| Information Findability Score | 정보 발견 가능성 |
| IA Consistency Index | 구조 일관성 |
---
# 12. Operational Checklist
□ Domain Model이 정의되었는가
□ Taxonomy가 일관적인가
□ Navigation이 주요 사용자 Task를 지원하는가
□ Label이 명확한가
□ 검증(Card Sorting 등)을 수행했는가
□ Metadata가 정의되었는가
□ IA 변경 이력이 기록되었는가
---
# 13. Information Architecture Anti Pattern
## Anti Pattern 1
시스템 구조를 그대로 사용자에게 노출한다.
---
## Anti Pattern 2
메뉴 중심으로 IA를 설계한다.
---
## Anti Pattern 3
동일한 개념에 여러 이름을 사용한다.
---
## Anti Pattern 4
확장성을 고려하지 않는다.
---
## Anti Pattern 5
검색 경험을 설계하지 않는다.
---
## Anti Pattern 6
사용자 검증 없이 IA를 확정한다.
---
## Anti Pattern 7
도메인 모델과 IA가 서로 다르게 진화한다.
---
# 14. IA Rules
## Rule IA-01
IA는 사용자의 Mental Model을 우선한다.
---
## Rule IA-02
모든 Navigation은 주요 사용자 Task와 연결된다.
---
## Rule IA-03
동일한 개념에는 동일한 용어를 사용한다.
---
## Rule IA-04
모든 정보는 명확한 소속과 관계를 가진다.
---
## Rule IA-05
IA는 검증을 통해 지속적으로 개선한다.
---
## Rule IA-06
Metadata와 Taxonomy는 함께 관리한다.
---
## Rule IA-07
IA는 Domain Model과 일관성을 유지한다.
---

# 010 Product Design Framework
# Part IV - Interaction Design Framework
Version 1.0.0
Status: Draft
---
# 1. Purpose
본 문서는 사용자와 시스템 간의 상호작용(Interaction)을 설계하기 위한 표준 운영 체계를 정의한다.
RoRo에서 Interaction은 버튼을 누르거나 화면을 전환하는 행위가 아니다.
Interaction은 사용자의 의도(Intent)를 시스템이 이해하고, 적절한 피드백과 결과를 제공하며, 다음 행동으로 자연스럽게 이어지도록 만드는 대화의 흐름이다.
---
# 2. Interaction Philosophy
좋은 Interaction은 사용자가 시스템의 작동 방식을 배우도록 요구하지 않는다.
시스템이 사용자의 의도에 맞추어 자연스럽게 반응해야 한다.
Interaction은 조작(Action)이 아니라 **의도(Intent) → 시스템 반응(Response) → 사용자 이해(Understanding)** 의 순환이다.
---
# 3. Interaction Objectives
Interaction Design은 다음 목표를 가진다.
- 사용자 의도의 명확한 전달
- 즉각적이고 이해하기 쉬운 피드백 제공
- 오류 예방 및 복구 지원
- Cognitive Load 최소화
- 예측 가능한 동작 제공
- 행동 흐름의 연속성 유지
---
# 4. Interaction Model
```plain text
User Intent

↓

User Action

↓

System Interpretation

↓

System Response

↓

User Feedback

↓

Next Action

↓

Goal Completion
```
Interaction은 단일 이벤트가 아니라 연속적인 대화 흐름으로 설계한다.
---
# 5. Interaction Principles
## Principle 1
Intent Before Action
사용자의 행동보다 의도를 먼저 이해한다.
---
## Principle 2
Immediate Feedback
모든 Action은 적절한 피드백을 제공한다.
---
## Principle 3
Predictability
동일한 입력은 동일한 결과를 제공해야 한다.
---
## Principle 4
Error Prevention
실수를 방지하는 것이 복구보다 우선이다.
---
## Principle 5
Graceful Recovery
오류가 발생해도 사용자가 쉽게 복구할 수 있어야 한다.
---
## Principle 6
Progressive Guidance
복잡한 작업은 단계적으로 안내한다.
---
## Principle 7
Conversation over Commands
명령을 수행하게 하기보다 대화하듯 상호작용을 설계한다.
---
# 6. Interaction Patterns
RoRo는 다음 표준 패턴을 사용한다.
| Pattern | Purpose |
| --- | --- |
| Navigation | 이동 |
| Selection | 선택 |
| Creation | 생성 |
| Editing | 수정 |
| Confirmation | 확인 |
| Cancellation | 취소 |
| Search | 탐색 |
| Filter | 필터링 |
| Upload | 업로드 |
| Sharing | 공유 |
새로운 패턴은 기존 패턴과 일관성을 유지해야 한다.
---
# 7. Feedback Design
모든 Interaction은 다음 피드백을 고려한다.
- System Status
- Progress
- Success
- Warning
- Error
- Recovery Guidance
사용자는 현재 상태와 다음 행동을 항상 이해할 수 있어야 한다.
---
# 8. AI-assisted Interaction
AI는 다음 상호작용을 지원할 수 있다.
- Intent Recognition
- Smart Suggestions
- Context-aware Guidance
- Personalized Responses
- Error Prediction
- Conversational Assistance
- Adaptive Interaction
AI는 Interaction을 향상시키지만 사용자의 통제권을 대체하지 않는다.
---
# 9. Required Artifacts
모든 Interaction Design은 다음 산출물을 생성한다.
- Interaction Flow
- State Diagram
- Error Handling Specification
- Feedback Specification
- Interaction Pattern Library
- Prototype
- Validation Report
---
# 10. Success Metrics
| KPI | Description |
| --- | --- |
| Task Completion Rate | 과업 완료율 |
| Interaction Success Rate | 상호작용 성공률 |
| Error Recovery Rate | 오류 복구율 |
| Time to Complete Task | 과업 완료 시간 |
| User Confidence Score | 사용자 신뢰도 |
| Interaction Consistency Index | 상호작용 일관성 |
---
# 11. Operational Checklist
□ 사용자의 Intent가 정의되었는가
□ 모든 Action에 Feedback이 있는가
□ 오류 복구 경로가 정의되었는가
□ Interaction Pattern이 표준을 따르는가
□ Prototype으로 검증했는가
□ Interaction 변경 사항이 문서화되었는가
□ AI 지원 여부를 검토했는가
---
# 12. Interaction Anti Pattern
## Anti Pattern 1
사용자가 시스템의 내부 구조를 이해해야 한다.
---
## Anti Pattern 2
Action 이후 피드백이 없다.
---
## Anti Pattern 3
오류 메시지가 원인이나 해결 방법을 제공하지 않는다.
---
## Anti Pattern 4
동일한 Action이 화면마다 다르게 동작한다.
---
## Anti Pattern 5
복잡한 절차를 한 번에 요구한다.
---
## Anti Pattern 6
AI가 사용자 의도를 과도하게 추측하여 통제권을 빼앗는다.
---
## Anti Pattern 7
Interaction 변경 이력을 기록하지 않는다.
---
# 13. Interaction Rules
## Rule IN-01
모든 Interaction은 사용자 Intent에서 시작한다.
---
## Rule IN-02
모든 Action은 즉각적인 Feedback을 제공한다.
---
## Rule IN-03
오류는 예방을 우선하고, 발생 시 복구를 지원한다.
---
## Rule IN-04
Interaction은 예측 가능하고 일관되어야 한다.
---
## Rule IN-05
AI는 사용자를 보조하며, 최종 선택권은 사용자에게 있다.
---
## Rule IN-06
새로운 Interaction Pattern은 기존 Pattern Library와 일관성을 유지한다.
---
## Rule IN-07
Interaction의 품질은 화면 전환 수가 아니라 사용자 목표 달성으로 평가한다.
---

# Part VI - Accessibility Framework
Version 1.0.0
Status: Draft
---
# 1. Purpose
본 문서는 모든 사용자가 제품을 동등하게 이용할 수 있도록 접근성(Accessibility)의 원칙과 운영 체계를 정의한다.
RoRo에서 Accessibility는 기능의 추가가 아니다.
Accessibility는 제품 설계의 기본 품질이며, 다양한 능력과 환경을 가진 사용자가 동일한 목표를 달성할 수 있도록 지원하는 설계 원칙이다.
---
# 2. Accessibility Philosophy
좋은 접근성은 특정 사용자를 위한 예외가 아니다.
접근성은 모든 사용자가 자신의 상황에 맞는 방식으로 제품을 사용할 수 있도록 선택권을 제공하는 것이다.
포용성(Inclusiveness)은 설계 초기부터 고려되어야 하며, 출시 직전 보완하는 항목이 아니다.
---
# 3. Accessibility Objectives
Accessibility는 다음 목표를 가진다.
- 동등한 사용자 경험 제공
- 다양한 입력 방식 지원
- 다양한 출력 방식 지원
- 인지 부담 감소
- 오류 예방 및 복구 지원
- 국제 표준 준수
- 지속적인 접근성 개선
---
# 4. Accessibility Principles
RoRo는 다음 원칙을 따른다.
## Principle 1
Perceivable
정보는 누구나 인식할 수 있어야 한다.
---
## Principle 2
Operable
모든 핵심 기능은 다양한 입력 방식으로 조작 가능해야 한다.
---
## Principle 3
Understandable
사용자는 인터페이스와 시스템의 동작을 쉽게 이해할 수 있어야 한다.
---
## Principle 4
Robust
다양한 기기와 보조 기술에서도 안정적으로 동작해야 한다.
---
## Principle 5
Inclusive by Default
새로운 기능은 기본적으로 접근성을 고려하여 설계한다.
---
## Principle 6
Context Awareness
사용 환경(밝기, 소음, 이동 중 사용 등)을 고려한 경험을 제공한다.
---
## Principle 7
User Control
사용자가 자신의 필요에 맞게 경험을 조정할 수 있어야 한다.
---
# 5. Accessibility Scope
다음 영역을 포함한다.
| Domain | Description |
| --- | --- |
| Visual | 색상, 대비, 확대 |
| Auditory | 소리 및 자막 |
| Motor | 터치, 키보드, 음성 |
| Cognitive | 정보 구조, 언어, 복잡도 |
| Environmental | 조명, 이동 환경, 네트워크 |
---
# 6. Accessibility Standards
RoRo는 다음 기준을 준수한다.
- WCAG 2.2 AA 이상
- 플랫폼 접근성 가이드라인(iOS, Android, Web)
- 색상 대비 기준
- 키보드 탐색 지원
- 스크린 리더 호환
- 의미 있는 대체 텍스트 제공
프로젝트 특성에 따라 추가 기준을 적용할 수 있다.
---
# 7. Validation Methods
접근성은 다음 방법으로 검증한다.
- Accessibility Audit
- Keyboard Navigation Test
- Screen Reader Test
- Color Contrast Test
- Zoom Test
- Cognitive Walkthrough
- User Testing with Diverse Participants
자동 점검과 사용자 검증을 함께 수행한다.
---
# 8. AI-assisted Accessibility
AI는 다음 활동을 지원할 수 있다.
- Contrast Analysis
- Alt Text Suggestion
- Accessibility Review
- Language Simplification
- Accessibility Issue Detection
- Inclusive Copywriting
- Compliance Monitoring
AI는 접근성 개선을 지원하지만 최종 품질은 Product Team과 Design Team이 책임진다.
---
# 9. Required Artifacts
모든 제품은 다음 산출물을 유지한다.
- Accessibility Checklist
- Compliance Report
- Accessibility Test Results
- Accessibility Issue Log
- Remediation Plan
- Accessibility Decision Log
---
# 10. Success Metrics
| KPI | Description |
| --- | --- |
| WCAG Compliance Rate | WCAG 준수율 |
| Accessibility Issue Density | 접근성 이슈 밀도 |
| Accessibility Defect Resolution Time | 평균 해결 시간 |
| Inclusive Task Success Rate | 다양한 사용자 환경에서의 과업 성공률 |
| Screen Reader Compatibility | 스크린 리더 호환성 |
| Accessibility Review Coverage | 접근성 리뷰 범위 |
---
# 11. Operational Checklist
□ WCAG 기준을 충족하는가
□ 키보드만으로 주요 기능을 사용할 수 있는가
□ 스크린 리더에서 핵심 정보가 전달되는가
□ 색상만으로 정보를 구분하지 않는가
□ 대체 텍스트가 제공되는가
□ 다양한 환경에서 테스트했는가
□ 접근성 변경 사항을 기록했는가
---
# 12. Accessibility Anti Pattern
## Anti Pattern 1
접근성을 출시 직전 점검한다.
---
## Anti Pattern 2
색상만으로 상태를 전달한다.
---
## Anti Pattern 3
키보드 사용을 고려하지 않는다.
---
## Anti Pattern 4
스크린 리더 테스트를 생략한다.
---
## Anti Pattern 5
복잡한 문장을 그대로 사용한다.
---
## Anti Pattern 6
자동 검사만으로 접근성을 완료했다고 판단한다.
---
## Anti Pattern 7
접근성을 특정 사용자만의 문제로 인식한다.
---
# 13. Accessibility Rules
## Rule AC-01
모든 기능은 설계 초기부터 접근성을 고려한다.
---
## Rule AC-02
접근성은 기능 추가가 아니라 기본 품질이다.
---
## Rule AC-03
자동 검사와 사용자 검증을 함께 수행한다.
---
## Rule AC-04
모든 주요 기능은 다양한 입력 방식을 지원한다.
---
## Rule AC-05

# Part VII - Design Validation Framework

# 1. Purpose
본 문서는 Product Design의 품질과 효과를 검증하기 위한 표준 운영 체계를 정의한다.
RoRo에서 Validation은 디자인을 승인하는 절차가 아니다.
Validation은 디자인이 사용자의 목표 달성에 실제로 기여하는지를 객관적인 Evidence를 통해 검증하는 과정이다.
---
# 2. Validation Philosophy
모든 디자인은 가설이다.
가설은 검증되어야 한다.
디자인의 성공은 디자이너의 만족이 아니라 사용자의 성공으로 판단한다.
Validation은 출시 전 활동이 아니라 제품 생애주기 전체에서 반복되는 학습 과정이다.
---
# 3. Validation Objectives
Design Validation은 다음 목표를 가진다.
- 사용자 목표 달성 여부 확인
- 사용성 문제 조기 발견
- 디자인 의사결정 검증
- 구현 리스크 감소
- 개발 비용 절감
- 지속적인 사용자 경험 개선
---

```plain text

↓

Prototype

↓

Validation Plan

↓

User Evaluation

↓

Evidence Collection

↓

Analysis

↓

Decision

↓

Iteration
```

| Cognitive Walkthrough | 인지 흐름 검토 |
| Heuristic Evaluation | 전문가 리뷰 |
| Accessibility Validation | 접근성 검증 |
| A/B Testing | 대안 비교 |
| Beta Testing | 실제 환경 검증 |
복수의 검증 방법을 조합하는 것을 권장한다.

# 1. Purpose
본 문서는 Product Design의 품질, 일관성, 재사용성 및 지속적인 개선을 보장하기 위한 Governance 체계를 정의한다.
RoRo에서 Design Governance는 승인 절차가 아니다.
Design Governance는 모든 디자인 활동이 사용자 가치, 브랜드 원칙, Design System, 접근성 기준 및 Product Strategy와 일관되게 유지되도록 하는 운영 체계이다.
---
# 2. Governance Philosophy
좋은 Governance는 창의성을 제한하지 않는다.
좋은 Governance는 반복적인 문제를 줄이고 창의성이 필요한 영역에 더 많은 시간을 사용할 수 있도록 돕는다.
Governance의 목적은 통제가 아니라 품질과 지속 가능성이다.
---
# 3. Governance Objectives
Design Governance는 다음 목표를 가진다.
- 디자인 품질 유지
- Design System 일관성 확보
- 사용자 경험 표준 유지
- 접근성 준수
- 재사용성 향상
- Design-to-Code 정합성 확보
- 지속적인 조직 학습 지원
---

| Design Knowledge | 지식 축적 |

# 13. Design Governance Rules
## Rule DG-01
모든 핵심 디자인은 Review를 거친다.
---
## Rule DG-02
Design System을 우선 활용한다.
---
## Rule DG-03
접근성은 필수 품질 기준이다.
---
## Rule DG-04
Validation 결과는 설계에 반영한다.
---
## Rule DG-05
모든 변경은 추적 가능해야 한다.
---
## Rule DG-06
Design Knowledge는 지속적으로 축적한다.
---
## Rule DG-07
Governance의 성공은 통제가 아니라 사용자 경험 품질로 측정한다.
